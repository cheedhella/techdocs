How to scale consumers horizontally?
  • Increase Concurrency
    • Add this line to run 3 consumer threads in parallel: factory.setConcurrency(3);
    • Each thread will be assigned its own set of partitions.
    • Under the hood, it creates three separate threads (three Kafka Consumers). Management: When you call registry.getListenerContainer("orderListener").stop(), Spring will stop all three threads at once. Y
  • Horizontal Scaling (Multiple Servers/Instances)
    • Since you are using a fixed group.id (order-consumer-group), Kafka automatically handles scaling across multiple servers;
    • If you deploy this same WAR to Server A and Server B, they will join the same group;
    • Kafka will automatically rebalance and give, for example, partitions 0-1 to Server A and partitions 2-3 to Server B;
    • No code changes are required for this, just ensure the group.id remains the same in kafka.properties;
  • Increase Topic Partitions
    • You cannot have more active consumers than you have partitions;
    • If your topic has 3 partitions and you have 10 consumer threads, 7 threads will sit idle;
    • Check partition count: kafka-topics.sh --bootstrap-server 10.253.228.200:9092 --topic orders --describe
    • Scale up partition count: kafka-topics.sh --bootstrap-server 10.253.228.200:9092 --topic orders --alter --partitions 10
  • LISTENER_ID
    • If you run your application on Server A and Server B: Server A will have a LISTENER_ID called "orderListener". Server B will also have a LISTENER_ID called "orderListener". Is there a conflict? No. These are two different JVMs. When you send a /start request to Server A, it only starts its local "orderListener". It has no effect on Server B.
    • If you ever add a second consumer service (e.g., a ShippingConsumerService), you must give it a unique LISTENER_ID;

What is `client-id` in Kafka producer configuration?

A human-readable identifier for a Kafka producer/consumer instance used for logs (both client and broker logs), monitoring, and debugging. When Kafka logs an issue, it will include the client ID: `[SocketServer brokerId=1] Connection with client heartbeat-producer disconnected`. This lets you trace problems back to the exact producer/consumer instance; You can set it manually or kafka can auto-generate it;

What is `enable.idempotence = true`?

Set to true to avoid duplicates in case of retries. Defaults to true;

What is `max-in-flight-requests-per-connection`?

When the producer sends a batch to Kafka, it normally waits for the broker acknowledgment before sending the next batch to the same connection; But with multiple in-flight requests, the producer can send: multiple batches without waiting for the acks; This may cause out-of-order processing of batches; If a request fails and the producer retries it, earlier and later batches may get reordered on the broker; Use strict ordering, if You want to avoid reordering even during retries;

What is `retries` in Kafka producer configuration?

It specifies how many times to retry a batch, when send fails due to retriable error; Defaults to Integer.MAX_VALUE (effectively unlimited); This ensures the producer keeps retrying until `delivery.timeout.ms` is reached;

What is `retry.backoff.ms`?

It specifies pause (sleep time) between retrials; It prevents immediately hammering Kafka after a transient failure; It gives time for metadata refresh; Defaults to 100ms; If it is too low, faster retries but harder on Kafka; If it is too high, smoother retries but increases message delivery latency;

What is `request.timeout.ms` in Kafka producer configuration?

It specifies the maximum amount of time producer waits to get a response from the broker, before considering it as failed; Defaults to 30000 ms (30 seconds);

What is `delivery.timeout.ms`?

Before Kafka 2.1, people often misconfigured: retries, `retry.backoff.ms`, `request.timeout.ms`; Thus causing retries to outlive the application’s expectations (sometimes retrying for hours); To avoid that, kafka introduced `delivery.timeout.ms`; It defines maximum amount of time the producer will try to deliver a record including retries, before giving up and failing the send; It is the deadline for the batch; Default: 120,000 ms (2 minutes);

How does `delivery.timeout.ms` work?

When you send a record, producer

  • Buffer it (in `buffer.memory`)
  • Put it in a batch (controlled by `batch.size`, `linger.ms`)
  • Attempt to send the batch to the broker; Starts a timer;
  • If no response within `request.timeout.ms` → that attempt fails;
  • Waits `retry.backoff.ms` -> retry starts on retriable errors (network issues, leader changes, transient broker problems)
  • This loop continues until: the record is acknowledged (SUCCESS), or the total time > `delivery.timeout.ms` (FAILURE)
  • If time is exceeded → producer throws: `TimeoutException: Expiring record due to delivery timeout`;
What is `batch-size` in Kafka producer configuration?

When you call send (sync/async), producer groups all messages destined for a partition in the same batch; Once the batch reaches the configured `batch-size`, then messages are actually sent to broker immediately; Defaults to 16 KB; If `batch-size` is high, it increases throughput (as more messages are compressed at once); Note that, increasing `batch-size` alone doesn't increase latency, unless combined with `linger.ms`;

What is `linger.ms` in Kafka producer configuration?

It specifies how long the producer should wait to fill up a batch before sending it, even if the batch is not full; Default: 0 ms (send immediately);

What is `buffer-memory` in Kafka producer configuration?

All batches are stored in `buffer.memory` (default: 32MB); If the buffer is full (due to slower networks, brokers overloaded or batching too large etc), then producer will: block, for synchronous sends; throw `BufferExhaustedException` (in async mode);

How does Kafka producer batching work?

Messages accumulate in memory (`buffer-memory`); Messages targeting the same partition enter a batch; A background sender thread pushes those batches to the broker, when:

  • When `batch.size` is reached;
  • If the batch sits for more than `linger.ms`;
  • On `flush()` or `close()`;
  • If messages that need batching exceed buffer capacity → producer blocks or fails.

Before sending, producer compresses the batch of messages (not individual message) using the algorithm specified;

What is `request-timeout-ms` in Kafka producer configuration (revisited)?

It specifies how much time the producer will wait for a broker response, after sending the request; If producer doesn't get a response within `request-timeout.ms`, it considers the request as failed and it either retries (if `retries` > 0) OR throws a timeout exception; Defaults to 30000ms (30 seconds); If it is too low, and if brokers are slow or under load, it can cause unnecessary timeouts; If it is too high, producer may hang for too long waiting for Kafka;

metadata.max.age.ms
  • It specifies how often the producer forcibly refreshes the metadata;

Metadata includes: list of brokers in the cluster, detect leader changes, pick up new partitions, checking topic existence etc; It defaults to: 300,000 ms (5 minutes); If it is too low, producer reacts faster to metadata changes but it can cause more load on brokers; If it is too high, it is efficient but producer is slower to react to the metadata changes;

Headers: __KeyTypeId__, __TypeId__, __ContentTypeId__
  • __KeyTypeId__
    • It specifies the type of the message key;
    • If your key is simple (String, UUID, Integer), you often don’t care;
    • But for custom key objects (rare), this is useful;
  • __TypeId__
    • If you are sending Order, then set it to com.example.Order;
    • If you are sending ListOrder, then set it to java.util.ArrayList;
  • __ContentTypeId__
    • If you are sending a collection, it specifies the type of collection element;
    • If you are sending Order, then this header is of no use;
    • If you are sending ListOrder, then set it to com.example.Order;
  • These headers contain type metadata that allow Spring Kafka consumers to deserialize JSON into the correct Java classes;
  • Without these headers, consumers often deserialize the data into: LinkedHashMap, raw collections, incorrect types;
