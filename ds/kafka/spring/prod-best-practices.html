Best Practices, When writing a Producer:
    Mandatory
  • Idempotence - Ensure producer can create no duplicates, during retries;
  • Control Retry Duration - Retries are bound by time, not count;
  • Kafka retries are for only transport failures; Add retry support for application level errors(that are retriable only);
  • If you combine kafka internal retries with application level retries: ensure there are no duplicate sends, excessive latency, message reordering;
  • Fail fast on errors like authorization - no point in retrying;
  • Send permanent failures to DLQ or dead letter topic;
  • Use meaningful Key - Keys control partitioning, ordering, consumer scalability;
  • Avoid random keys - Use random keys only when you don't care about ordering;
  • Keep message size small - Kafka is optimized for small messages(less than 1MB) only; For large payloads, use large blobs in DB/S3 and send reference;
  • Graceful shutdown - Always flush before shutdown - producer.flush(); producer.close(); It prevents data loss;
  • Don't create a producer for each message; Create only one producer per application instance;
  • Internal Batching vs Application level batching - In case of application level batching, One bad event poisons the entire batch; breaks ordering; harder to implement partial batch retry handling;
  • Bottomline: Kafka guarantees delivery — not correctness; Correctness is your application’s responsibility;
