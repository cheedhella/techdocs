1. What is a Microservice?
  • It is a small, focused(it does only one specific business function) and independantly deployable service;
2. Core Principles of Microservices
  • Breaks complexapplication into autonomous services
    • It breaks complex application into smaller and more manageable services, each responsible for a specific business function;
  • Independent development and deployment
    • Each service can be developed and deployed independantly, without affecting the other services;
    • It speeds up development and reduces the time to market;
  • Loosely coupled and highly cohesive
    • Services are loosely coupled, meaning they are independent of each other;
    • Services are highly cohesive, meaning they are responsible for a single business capability;
  • Polygot Architecture
    • Each service can use a different technology; One servie can use Java, another can use Python etc;
  • Resilent and Scalable
    • If one service fails, it does not affect the other services;
    • You can scale only the services that are needed, instead of scaling the entire application;
  • Communication
    • Services communicate with each other using either synchronous protocols such as HTTP/REST, gRPC or asynchronous protocols such as AMQP;
3. Monolithic vs Microservices Architecture?
  • In case of monolithic architecture, entire application is built, deployed and scaled as a single unit; A change in one of the modules can only be brought into production, by bringing a new version of the entire application;
  • In case of microservices architecture, application is split into a collection of loosely coupled, independently deployable services; A change in one of the services can be brought into production, by deploying only that service;
4. Bottom line
  • Microservices are used to make large systems easier to build, scale, maintain and evolve;
  • Pros
    • Easier to develop, deploy and scale;
    • Better team organization;
    • Better fault isolation - Failure in one service does not affect the other services;
  • Cons
    • It introduces additional complexicity to develop;
    • With decentralized data storage, it becomes difficult to achieve data consistency with multiple services;
    • With many services running, it requires advanced observability tools to monitor the health and performance of the services;
    • Operational overhead - Need infrastructure to support service discovery, load balancing, API gateway, CI/CD etc;
  • When to use Microservices?
    • When the application is large and complex;
    • If your application needs to scale specific components independantly, based on demand;
    • When the application needs to be maintainable;
    • When the application needs to be testable;
  • When not to use Microservices?
    • When the application is small and simple;
    • If your team is small size - Managing microservices needs expertise in distributed systems and a dedicated devops team;
  • Many successful systems start as monolithic and then evolve into microservices at the right time;
