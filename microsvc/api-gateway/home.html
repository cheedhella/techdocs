API Gateway

1. What is API Gateway?
  • It sits in front of a set of microservices and acts as a entry point for every request from the clients(web, mobile app etc);
  • It is more than just a traffic router; It encapsulates several cross-cutting concerns(listed below) that would otherwise have to be implemented in each microservice;
2. Why API Gateway?
  • Centralized Routing
    • Clients interact with API gateway using a unified interface (/api/**), while the gateway routes requests to appropriate internal service endpoints (http://order-service/internal/v1/...), based on HTTP method, URL path OR Header;
  • Authentication and Authorization
    • Instead of implementing security checks in each service, gateway handles token validation(OAuth2, JWT etc) and enforces role-based access control policies before forwarding the request;
  • Rate Limiting and Throttling
    • Protects backend services by enforcing request quotas per user, IP, or API key — often using token bucket or sliding window algorithms;
  • Request Aggregation
    • For composite views like dashboards, the gateway can call multiple services in parallel and merge the responses, reducing the number of round trips from the client;
  • Request/Response Transformation
    • Modifies headers or API payloads to support backward compatibility or API versioning;
  • API Versioning
    • Routes traffic based on API versions to support backward compatibility and gradual migrations;
  • Protocol Bridging/Translation
    • Converts between protocols (e.g., HTTP to gRPC or WebSocket);
  • Load Balancing & Failover
    • Distributes requests across service instances and can automatically retry or redirect traffic in case of failure;
  • Circuit Breaking & Retry
    • Detects downstream service failures and applies fallback logic or retries based on configured policies;
  • Caching
    • Stores responses temporarily to serve repeated requests faster and reduce backend load;
  • Documentation
    • Gateway can enforce standards like OpenAPI/Swagger, ensuring documentation stays updated;
  • Source Control Integration
    • Sync API configurations with Git to track changes and enable CI/CD pipelines;
3. Popular API Gateways
  • Kong
  • Nginx
  • Spring Cloud Gateway
  • Traefik
  • Zuul (by Netflix)
  • Apigee (by Google Cloud)
4. Which one to choose?
  • Managed API Gateway(AWS/Azure): if you are cloud-native and want minimal operational overhead;
  • Kong/Nginx: If you are on k8s and want control but not full custom;
  • Service Mesh: If you need internal traffic control + mTLS; Service mesh is not an API gateway, it is for inter-service traffic;
  • Instead of one large gateway, create separate gateways per client: Mobile BFF Web BFF Admin BFF
5. Challenges
  • While API gateways solve many challenges, misconfiguration can backfire;
  • Additional overhead - It introduces additional hop in request path;
  • Single point of failure - If it goes down, all services become inaccessible; Deploy it in a high availability (HA) setup with load balancing and health checks;
  • Complex Configuration - Managing route rules, filters, plugins, and policies for dozens of services can quickly become difficult — especially as the number of microservices grows;
  • Security Risks - Improper configuration of auth, rate limits, or CORS policies in the gateway can open up security vulnerabilities across all downstream services;
  • Operational Overhead - Gateways require careful monitoring to ensure it won't be a bottleneck; Integrate with observability stacks (Prometheus, Grafana, ELK, etc.) and track metrics like latency, error rates, and throughput;
