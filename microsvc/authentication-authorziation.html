3. New Terms
  • Identity Provider OR Authentication Server
    • A service which validates who you are(authenticates) and gives you a token to access other services;
    • IDP handles only authenticaiton, but issued token will have roles or permissions or claims; Eg: { "user": "user123", "roles": ["admin", "editor"] }
    • It is the responsibility of service to enforce what user can do;
    • Modern IDPs: Keycloak, Auth0, Okta;
    • Federation or external sources
4. How it works?
  • When user clicks on Login, Credentials are sent to IDP; IDP validate the credentials;
  • If successful, IDP issues a JWT Access Token, ID Token and Refresh Token;
  • React app loads config (Auth URL + API URL). User clicks “Login”. React redirects to the IdP’s login endpoint (OIDC / OAuth2). After successful login, IdP redirects back to React with tokens. React stores the JWT and uses it for all API calls to the Gateway. Access token(for APIs) or ID token; User logs in via frontend → redirected to Identity Provider. IdP issues . Frontend sends requests to API Gateway with Authorization: Bearer . Gateway verifies JWT signature → forwards to microservice. Microservice checks claims or consults OPA for fine-grained access. OPA responds allow = true or false. Service processes or rejects request. React redirects to: https://auth.mycompany.com/realms/myrealm/protocol/openid-connect/auth ?client_id=my-react-app &redirect_uri=https://app.mycompany.com/callback &response_type=code &scope=openid IdP authenticates and redirects to /callback with an authorization code. React exchanges the code for tokens via IdP’s /token endpoint. React stores access_token (in memory) and uses it for API requests: fetch(`${apiUrl}/users`, { headers: { Authorization: `Bearer ${token}` } }); Frontend calls API Gateway The frontend app sends API requests like: Authorization: Bearer eyJhbGciOiJIUzI1... The API Gateway verifies the token (using the IdP’s public key). If valid, it forwards the request to the backend service. 4. Microservices trust the Gateway Microservices trust that any request with a valid token has been authenticated. They can perform authorization based on token claims (roles, groups, etc.).
5. What IDP stores user information and tokens?
  • Does IDP stores tokens?
  • Modern Identity Providers may or may not store issued tokens; It depends on the token type and IDP configuration;
  • Stateful (stored server-side); Stateless (self-contained, e.g., JWTs);
  • Stateless token - The token itself contains all necessary data; IDP also signs the token with its private key and any service can verify it using the public key; Downside is Hard to revoke early (before expiration), since the IdP doesn’t track them;
    • Usually mitigated by: Short token lifetimes (e.g., 5–15 minutes) Refresh tokens that can be revoked Token blacklists or introspection endpoints
  • Client further includes the access token in API requests;
  • API verifies token signature using IdP’s public key;
6. How Does the React App Know the IdP and API Gateway?
  • We need to configure it via environment variables or a config file during build time;
  • For eg, if IDP is running at: https://auth.mycompany.com and API gateway is running at: https://api.mycompany.com, define this in .env file:
  • REACT_APP_AUTH_URL=https://auth.mycompany.com/realms/myrealm REACT_APP_API_URL=https://api.mycompany.com/ REACT_APP_CLIENT_ID=my-react-app
  • Then, in React: const authUrl = process.env.REACT_APP_AUTH_URL; const apiUrl = process.env.REACT_APP_API_URL; const clientId = process.env.REACT_APP_CLIENT_ID;
7. How React App Stores the JWT Token?
  • 3 ways: Memory(React state/context), sessionStorage, localStorage, Secure http-only cookies;
    • React state
      • Pros:
        • Very secure (cannot be stolen by XSS since it’s never written to disk);
      • Cons:
        • Token lost on page reload — you’ll need a refresh token mechanism or silent re-login;
      • Applications:
        • high-security apps (banking, healthcare);
    • sessionStorage
      • Eg: sessionStorage.setItem('access_token', token);
      • Pros:
        • Available until browser/tab is closed;
      • Cons:
        • Not shared across tabs;
        • Vulnerable to XSS if malicious scripts run in the page
      • Applications:
        • moderately secure apps, single-tab usage;
    • localStorage
      • Eg: localStorage.setItem('access_token', token);
      • Pros:
        • Persists even after closing the browser;
      • Cons:
        • XSS vulnerable — scripts can read it;
        • Cannot be automatically cleared on logout (you must handle it);
      • Applications:
        • Not recommended for highly sensitive apps;
    • Secure HTTP-only Cookies
      • Eg: Set-Cookie: access_token=...; HttpOnly; Secure; SameSite=Strict;
      • Pros:
        • Very secure — browser handles it, and JS can’t access it;
        • Works well with session-based flows;
      • Cons:
        • Harder to use in SPA (React) + cross-domain setups;
        • CORS and CSRF protection must be configured correctly;
      • Applications:
        • Best for enterprise SPAs with strong backend integration (e.g., via API Gateway session handling);
User clicks “Log in” → redirected to the IdP (e.g., Auth0). IdP shows a login page → verifies credentials. If successful, IdP issues: Access Token (for APIs) ID Token (user identity info) Client app includes the Access Token in API requests. API verifies token signature using IdP’s public key. Authorization Models 1. Role-Based Access Control (RBAC) Assigns users to roles (e.g., admin, editor, viewer). Services check user’s role claim in the JWT. 2. Attribute-Based Access Control (ABAC) Rules based on attributes (user, resource, environment). Example: “Allow access if department == resource.department.” 3. Policy-Based Access Control (PBAC) Centralized policy engine (e.g., Open Policy Agent (OPA)). Services query the policy engine for access decisions. API Gateway: NGINX / Kong / Spring Cloud Gateway
