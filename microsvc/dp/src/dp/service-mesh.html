What is Service Mesh? What problems it solves in Microservices world?

  • As you know, monolithic applications are complex to build and slow to release;
  • While microservices architecture helps in resolving above issues, it brings in new problems:
    • Security - How do we secure the traffic between all the services deployed in k8s cluster?
      • In general, you will have firewall rules set up for your k8s cluster;
      • We can have proxy, which gets the request first, acts as an entry point to the cluster, so that resources can't be accessed directly;
      • So, we have security around the cluster;

      • But, once the request reaches inside the cluster, communication is insecure;
      • Microservices talk to each other using http or some other insecure protocol;

      • Every service can talk to every other service in the cluster directly, there are no restrictions on that;
      • From security perspective, if an attacker gets inside the cluster, he can do anything;

      • For some applications, it is fine; But, most of the applications, higher level of security is important!

    • Observability
      • Logs, metrics and traces are 3 pillars of observability - These are the external outputs of a system, which we may observe;
      • As distributed systems grow more complex, demand to observe those systems grows equally;
      • Traditional logging and monitoring systems often struggle with today's hybrid and multi-cloud, polyglot language-based, event-driven, container-based and serverless, infinitely scalable, ephemeral-compute platforms;
      • Instead of adding this logic to each and every service that you write, modern tools are designed to handle this level of complexity in mind;

      • Tools like Istio attempt to solve the observability challenge by offering native integrations with several best-of-breed, open-source telemetry tools;
      • Istio's integrations include Jaeger for distributed tracing, Kiali for distributed system visualization, and Prometheus and Grafana for metric collection, monitoring, and alerting;
      • Combined with cloud platform-native monitoring and logging services, such as Stackdriver for Google Kubernetes Engine (GKE) on Google Cloud Platform (GCP), and we have a complete observability platform for modern, distributed applications;

    • Advanced traffic control, such as, circuit breaking, latency-aware load balancing, fault injection, retries, etc;

    • Kubernetes is not designed or equipped to handle all those problems, but service meshes are!
    • In short, service mesh is a dedicated infrastructure layer that controls service-to-service communication;
    • The mesh provides critical capabilities including service discovery, load balancing, encryption, observability, traceability, authentication and authorization, and support for the circuit breaker pattern;
    • Service Mesh Implementations: Istio, AWS App Mesh etc;

Istio Architecture

  • It contains a data plane and a control plane;
  • Fundamentally, Istio works by deploying envoy proxy as a sidecar to every service/container; envoy proxy is a open source implementation;
  • Data plane consists of network of Envoy proxies that control the communication between services(mesh traffic), incoming traffic (called ingress), outgoing traffic (called egress) and also collect metrics;
  • Control plane layer manages the configuration of envoy proxies;
  • istiod binary is the core of the control plane and provides service discovery, configuration and certificate management;

  • Istio is quite flexible in terms of integrating with external libraries and platforms;
  • For instance, we can integrate Istio with an external logging platform, telemetry, or policy system;

  • You don't have to write yaml files for creating envoy proxy for each container;

Isito Features

  • Traffic Splitting
  • Configuration
  • Service Discovery
  • Certificate Management
  • Monitoring and Tracing
  • Ingress Gateway

Traffic Splitting

  • when you make changes to one service(for eg, payment service), you deploy the changes and test it in dev environment and then rolled out to production;
  • What if you have a bug, that none of the tests caught it;
  • In general, we don't want the buggy service in the producion;
  • You may want to send only 10% of the traffic to the new service for a period of time, to make sure it really works;
  • With service mesh, you can route 90% of traffic to older version and remaining 10% of traffic to new version;
  • It is also called Canary Deployment;

How to configure all these features for all services?

  • You dont have to adjust k8s(deployment/service) YAML files;
  • Isito configuration is different from application configuration;
  • Isito uses k8s CustomResourceDefinitions; No need to learn any other language;
  • CRD is basically a customer resource in k8s, that is used to configure 3rd party technologies like istio, prometheus etc;

  • We create CRDs;
  • Using CRD rules, we can configure different routing rules b/w our services, like which service can talk to which service? traffic split configuration? retry rules? other network configuration;
  • VirtualService - It defines How to route traffic to given destination?
  • DestinationRule - Using this, we can define policies on the traffic, like what kind of load balancing to use? etc

  • istiod converts these high level routing rules into envoy specific configurations and propagates the configuration into envoy proxy sidecars;
  • So, we don't configure proxies, we configure control plane; istiod pushes configuration to individual envoy proxies;

  • Proxies can communicate with each other, without connecting to istiod control plane, as they have all the configuration they need;

Certificate Management

  • It secures all the communiation b/w services using certificates;

Monitoring and Tracing

  • It gathers telemetry and tracing data from the envoy proxies, that can be later consumed by monitoring service such as Prometheus OR tracing server such zipkin;

Ingress Gateway

  • It is entry point to k8s cluster; It runs as a pod in your cluster and acts as a load balancer by accepting incoming traffic in your cluster and gateway will then direct traffic to one of your microservices inside the cluster, using VirtualService compoennt;
  • You can configure Ingress gateway using gateway CRD;

Traffic Flow with Isito

  • User intiates a request;
  • Request will first goes to Istio Gateway, as it is entry point to the k8s cluster;
  • Gateway will evaluate the VirtualService rules, to route the request to envoy proxy in one of the service;
  • Envoy proxy evaluates the request and forwards it to the container running in same pod, using localhost;
