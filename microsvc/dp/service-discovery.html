1. What is Service Discovery?
  • In a microservices environment, containers/services are spin up/down, scaled up/down dynamically based on demand;
  • This means that the IP addresses of the services are not static, and they can change frequently;
  • Service Discovery is a mechanism that allows services to find and communicate with each other without hardcoding IP addresses;
2. How does it work?
  • 1. Service Registry:
    • Every service instance registers itself with the service registry on startup and deregister on shutdown;
    • Usually, every service sends this information to service registry during registration: IP address, port, service name, health check endpoint, instanceID etc;
    • Registry periodically checks if services are still alive;
  • 2. Service Discovery:
    • When a service A wants to call service B, it queries the service registry to get the current location of B;
    • The service registry returns the list of available instances of B;
    • The client then calls one of the available instances of B;
3. Types of Service Discovery
  • Client-Side Discovery:
    • Client queries the service registry to find an available instance and then calls it directly;
    • Example: Netflix Ribbon;
  • Server-Side Discovery:
    • The client calls a load balancer/proxy, which then queries the registry and routes the request to an instance;
    • Example: AWS Elastic Load Balancer;

5. How does services know about the service registry?
  • 1. Configuration
    • Every service is explicitly configured where the service registry is located;
    • eureka:
    client:
        service-url:
            defaultZone: http://localhost:8761/eureka/
    • When the service starts, it reads config and registers itself with the service registry;
    • This configuration injected into the service via application.yml, environment variables, or configuration server;
  • 2. DNS
    • K8s runs a cluster-wide DNS server (CoreDNS) as a Deployment in kube-system namespace; It keeps track of service names and their IP addresses;
    • This Registry is exposed to services via DNS name;
    • Services use a fixed DNS name such as http://consul.default.svc.cluster.local
    • Service A calls http://payment-service -> CoreDNS resolves it to IP address;
6. What if the service registry is down?
  • Existing services may continue working (thanks to caching);
  • But new registrations and updates stop;
  • Over time, the system becomes less reliable;
  • Best Practices:
    • Run multiple instances(cluster) to maintain HA;
    • Use circuit breakers - to prevent cascading failures;
