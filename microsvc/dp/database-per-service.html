1. What is the Database per Service pattern?
  • In this pattern, each microservice has its own private database that is accessible only by that service;
  • No other service can access the database directly; instead, they must use the service's API;
  • This ensures that services are loosely coupled and can be developed, deployed, and scaled independently;
2. Why use Database per Service?
  • Loose Coupling: Changes to one service's database schema do not affect other services;
  • Independent Scaling: You can scale the database for a specific service based on its needs;
  • Polyglot Persistence: Each service can use the type of database that best fits its requirements (e.g., NoSQL for one, Relational for another);
  • Encapsulation: Data is hidden behind the service's API, preventing direct dependencies on the data structure;
3. Challenges
  • Data Consistency: Maintaining consistency across multiple databases requires patterns like Saga or Event Sourcing;
  • Complex Queries: Joining data from multiple services becomes difficult and often requires data aggregation or API composition;
  • Operational Overhead: Managing multiple database instances can be more complex than a single monolithic database;
