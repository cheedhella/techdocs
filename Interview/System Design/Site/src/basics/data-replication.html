What is Replication?

  • Replication means keeping a copy of the same data on multiple machines that are connected via a network;
  • Replication can be synchronous or asynchronous;

  • There are 3 approaches to replicate data:
    • Master Slave Replication
    • Multi-Master Slave Replication
    • Leaderless Replication
  • Master-Slave Replication
    • In this case, there will be only 1 master/leader and multiple replicas/slaves;
    • In case of writes, cache client can write to only master; In case of reads, cache client can read from any node(master/slave);

    • In case of synchronous replication:
      • Cache client considers the write as successful, only after data is written to all replicas successfully;
      • In case of any issue, cache client can rollback the transaction and retry;
      • There will not be any data loss!

      • What if the master goes down?
        • Replica with most updated data will become the master; TODO: leader-election is another topic;

    • In case of asynchronous replication:
      • Master node logs each and every write(insert/update/delete) that it performs;
      • Each replica asks the master for the logs, parses the SQL and executes those queries, as if it is received from cache client;

      • Any SQL statement that calls a non-deterministic function, such as NOW()/RAND()/current date-time is likely to generate a different value on each replica;
      • Solution: Let the the leader to replace any non-deterministic function calls with a fixed return value when the statement is logged;

      • What if the master goes down?
        • There is a chance there are some writes which are not yet propagated to replicas;
        • That will cause data loss! This makes the solution not durable; In case of Distributed Cache, this would cause cache miss;
        • There are no easy solutions to this problem; For this reason, some operations teams prefer to perform fail-overs manually;

        • TODO: leader-election is another topic;

      • What if a slave goes down?
        • Each slave keeps a replication log of the data changes that it has received from the master, on the local disk;
        • If the slave crashes or is restarted, it can recover from its local log as it knows the last transaction that was processed before the shutdown;
        • Once the slave is up, it connects to the master and syncs up where it was left out;

      • Problems with asynchrnous replication:
        • Problem #1:
          • There is some chance that the new master may not receive all the writes from the old master, assuming that is still down;
          • Hence, those write changes will be discarded, which could impact the applications;
          • In case of Distributed Cache, this would cause cache miss;
        • Problem #2:
          • If the user tries to read the data immediately after making a write, the new data may not yet have reached the replica;
          • However, to the user, it will look as though the data they submitted was lost;
    • Applications
      • For workloads that consist of mostly reads and only a small percentage of writes (a common pattern on the web), this is an attractive option to create many followers and distribute the read requests across those followers;
      • This removes a load from the leader and allows read requests to be served by nearby replicas
