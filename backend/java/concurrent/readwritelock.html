  • A lock ensures that only one thread (or a controlled number) can access a critical section at a time;

# Configuration Service 
Your app reads config values thousands of times per second
Config updates happen rarely (e.g., feature flag change)



    
Why ReadWriteLock fits perfectly?
✅ Many threads can read config simultaneously
❌ Only one thread can write config at a time


    

import java.util.*;
import java.util.concurrent.locks.*;

class ConfigService {
    private final Map config = new HashMap<>();
    private final ReadWriteLock lock = new ReentrantReadWriteLock();

    // Read config (very frequent)
    public String get(String key) {
        lock.readLock().lock();
        try {
            return config.get(key);
        } finally {
            lock.readLock().unlock();
        }
    }

    // Update config (rare)
    public void update(String key, String value) {
        lock.writeLock().lock();
        try {
            config.put(key, value);
            System.out.println("Updated config: " + key);
        } finally {
            lock.writeLock().unlock();
        }
    }
}

public class Main {
    public static void main(String[] args) {

        ConfigService configService = new ConfigService();

        // Initial config
        configService.update("featureFlag", "OFF");

        // Reader task
        Runnable reader = () -> {
            for (int i = 0; i < 5; i++) {
                String value = configService.get("featureFlag");
                System.out.println(Thread.currentThread().getName() +
                        " got value: " + value);
                try { Thread.sleep(200); } catch (InterruptedException ignored) {}
            }
        };

        // Writer task
        Runnable writer = () -> {
            try { Thread.sleep(500); } catch (InterruptedException ignored) {}

            configService.update("featureFlag", "ON");

            try { Thread.sleep(500); } catch (InterruptedException ignored) {}

            configService.update("featureFlag", "OFF");
        };

        // Start threads
        new Thread(reader, "Reader-1").start();
        new Thread(reader, "Reader-2").start();
        new Thread(reader, "Reader-3").start();

        new Thread(writer, "Writer").start();
    }
}

        ReentrantLock lock = new ReentrantLock();

        try {

        ReentrantLock lock = new ReentrantLock();
        if (lock.tryLock()) {
            try {
                // critical section
            } finally {
                lock.unlock();
            }
        } else {
            // couldn't acquire lock → do something else
        }
        

    
        # Non-blocking - TryLock with timeout(Waits for limited time → avoids deadlock situations)
        ReentrantLock lock = new ReentrantLock();

                // critical section
            } finally {
                lock.unlock();
            }
        } else {
            // couldn't acquire lock → do something else
        }

Why use Locks instead of synchronized blocks?
While synchronized is easier to use, Lock provides several advanced features:
  • Fairness: You can configure a lock to grant access to the longest-waiting thread (fairness policy), whereas synchronized makes no such guarantees (thread starvation is possible).
  • Non-blocking Attempts: You can try to acquire a lock using tryLock(). If it's already held by another thread, you can do something else instead of blocking indefinitely.
  • Interruptible Waiting: You can use lockInterruptibly(), which allows a waiting thread to be interrupted and stop waiting for the lock.
  • Multiple Conditions: A lock can be associated with multiple Condition objects (similar to wait() and notify()), allowing for finer-grained thread communication.
What is ReentrantLock?
ReentrantLock is the most widely used implementation of the Lock interface. "Reentrant" means that a thread that currently holds the lock can acquire it again multiple times without deadlocking itself. It must release the lock the exact same number of times it acquired it.
What is ReadWriteLock?
ReadWriteLock (with its implementation ReentrantReadWriteLock) maintains a pair of associated locks: one for read-only operations and one for writing.
  • Read Lock: Can be held simultaneously by multiple reader threads, as long as there are no writers.
  • Write Lock: Is exclusive. Only one thread can hold it, and no other thread can hold the read lock at the same time.
This is incredibly useful for data structures that are read frequently but modified rarely, significantly improving concurrency.
Can you show a ReentrantLock example?
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class Counter {
    private int count = 0;
    // Create a lock (can pass 'true' for a fair lock)
    private final Lock lock = new ReentrantLock();

    public void increment() {
        lock.lock(); // Acquire the lock
        try {
            count++; // Critical section
        } finally {
            // ALWAYS release the lock in a finally block!
            // Otherwise, if an exception occurs, the lock is never released.
            lock.unlock(); 
        }
    }

    public int getCount() {
        return count;
    }
}
When should you use Locks?
Stick to synchronized blocks by default as they are simpler and less prone to errors (like forgetting to call unlock()). Use the Lock API when you specifically need its advanced features: fair locks, interruptible lock acquisition, non-blocking tryLock, or when you need separate read vs. write locks (ReadWriteLock).
