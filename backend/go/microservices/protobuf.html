1. What is Data Format?
  • It is a way of representing data; There are many types of data formats;
  • Text format: CSV, XML, JSON;
  • Binary format: Avro, Protobuf;
2. What is Protocol Buffer?
  • It is a language-neutral, platform-neutral data format(developed by Google);
  • It enables our web applications to exchange data faster;
  • gRPC uses protobuf as it's default serialization format;
3. Key features of Protocol Buffer?
  • Provides Schema definition langauge
    • Protobuf uses schema to define the structure of the data to be serialized;
    • This schema is defined in a language-agnostic format and serves as a contract between systems;
  • Uses Binary Format
    • Protobuf serializes data into a binary format, which is more compact compared to human-readable formats like JSON or XML;
    • This results in smaller payload sizes, making it more efficient;
  • Multiple Language Support
    • Protobuf provides compilers for multiple languages;
    • It allows you to implement systems in different languages;
    • As long as they share a common schema, data can be serialized and deserialized;
  • Backward and Forward Compatibility
    • New fields can be added to messages without breaking compatibility with existing code;
    • Unknown fields are ignored, and missing fields are treated as having default values;
    • As long as they share a common schema, data can be serialized and deserialized;
  • High Performance
    • Binary format and code generation contribute to faster serialization and deserialization;
    • Also with server compression turned on, Protobuf payload size becomes even smaller;
  • Extensible
    • Protobuf supports extending existing message types, allowing for the addition of new fields without modifying the original message definition;
4. How it works?
  • You define schema(structure of data) in a .proto file;
  • From that, you can generate code for multiple languages (e.g., C++, Java, Python, Go, Rust, etc) using protoc compiler;
    • protoc - python_out=. User.proto
Why do we need field tags or field numbers?
  • When Protobuf serializes data, it does not store field names like id/username (that would waste space);
  • Instead, it uses the field number in the binary format to identify which field is which during serialization and deserialization;
  • Each field in a message must have a unique field number;
  • If you remove a field, mark its number as reserved so future versions don’t break backward compatibility;


Presence Tracking Example

message User {
  string id = 1;
  string username = 2;
  reserved 3; // removed field 3 and reserved it to avoid collisions
}
It is particularly designed to be efficient in terms of both size and speed, making it suitable for communication protocols and data storage. Protobuf also provides support for versioning, allowing for changes to the schema without breaking compatibility with existing clients or servers. Additionally, Protobuf messages are extensible, meaning that new fields can be added to a message without breaking backward compatibility.
2. Protobuf vs JSON
  • Small Initial stack and resizable
    • A goroutine starts with a very small stack (about 2 KB) and it grows or shrinks dynamically as needed by the workload; Where as regular OS threads starts with a large fixed stack (often 1 MB);
  • User space scheduling and M:N modeling
    • goroutines are scheduled in the user space(rather than kernel space) by go runtime;
      So, swiching b/w goroutines is faster - as there is no need to enter kernel mode, only minimal state(like program counter, stack pointer etc) needs to be saved/restored;
    • Goroutines are multiplexed onto OS threads - It means thousands of goroutines can run on just a handful of threads, thus taking less memory and CPU;
  • Efficient communication via channels
    • Instead of shared memory and locks, Goroutines use channels to communicate(exchange data) with each other;
3. Protobuf Scalar types
  • double: A double-precision floating-point number.
  • float: A single-precision floating-point number.
  • int32: A signed 32-bit integer.
  • int64: A signed 64-bit integer.
  • uint32: An unsigned 32-bit integer.
  • uint64: An unsigned 64-bit integer.
  • sint32: A signed 32-bit integer encoded as a zigzag-encoded 32-bit integer.
  • sint64: A signed 64-bit integer encoded as a zigzag-encoded 64-bit integer.
  • fixed32: An unsigned 32-bit integer, encoded as a fixed-width 32-bit value.
  • fixed64: An unsigned 64-bit integer, encoded as a fixed-width 64-bit value.
  • sfixed32: A signed 32-bit integer, encoded as a fixed-width 32-bit value.
  • sfixed64: A signed 64-bit integer, encoded as a fixed-width 64-bit value.
  • bool: A boolean value.
  • string: A string of UTF-8 characters.
  • bytes: A sequence of bytes.
Protobuf also supports more complex types like enums, nested messages, and repeated fields to represent more complex data structures.
proto2 vs proto3
  • Rules
    • proto2:
      • It supports required, optional, repeated(for multiple values like array/list);
    • proto3:
      • required is removed, as it is problematic for backward and forward compatibility;
      • All fields are optional by default;
      • It still supports optional keyword and repurposed it for presence tracking;
  • Default values
    • proto2:
      • You can explicitly specify default values; Eg: optional int32 age = 1 [default = 18];
    • proto3:
      • Defaults are implicit; No custom/explicit defaults are allowed;
      • int32 → 0, bool → false, string → "", message → not set, repeated → empty list
  • Enums
    • proto2:
      • Enums can start with any integer;
    • proto3:
      • Enums must have a value 0 defined as the first element;
  • Presence Tracking in protoc3: int32 age = 2 VS optional int32 age = 2;
    • int32 age = 2
      • If you don't set it, it defaults to 0 implicitly;
      • But, no presence tracking for scalar types - You cannot tell if the field was explicitly set to 0 or if it was never set at all;
    • optional int32 age = 2
      • If you don't set it, it defaults to 0 implicitly;
      • But, you can do presence tracking;


Presence Tracking Example

// int32 age = 2
msg = Person()
print(msg.age)        # 0 (default)
print(msg.HasField("age"))  # ❌ raises error (not supported)

// optional int32 age = 2
msg = Person()
print(msg.age)        # 0 (default)
print(msg.HasField("age"))  # False  (not set)

msg.age = 0
print(msg.age)        # 0
print(msg.HasField("age"))  # True  (explicitly set)

    for i := 0; i < 3; i++ {
        fmt.Println(msg, i)
        time.Sleep(500 * time.Millisecond)
    }
}

func main() {
    go printMessage("goroutine") // run concurrently with main goroutine
    printMessage("main")         // run in main goroutine - It is possible main routine can finish and die before child goroutine;
}
