1. Why Caching Is Challenging
  • GraphQL Characteristics
    • Single endpoint (usually POST);
    • Can't use HTTP caching like REST;
    • Flexible queries make caching complex;
  • Graph Data Challenges
    • Interconnected data changes frequently;
    • Hard to invalidate related data;
    • Need smart cache invalidation;
2. Client-Side Caching
  • Apollo Client Cache
    • Normalized cache by ID;
    • Automatic cache updates;
    • Optimistic UI updates;
  • Cache Policies
    • cache-first - use cache, fallback to network;
    • network-only - always fetch from network;
    • cache-and-network - return cache, then update;
3. Server-Side Caching
  • Response Caching
    • Cache entire query results;
    • Use query + variables as cache key;
    • Works well for public, read-heavy data;
  • DataLoader Caching
    • Request-scoped cache;
    • Prevents duplicate queries in single request;
    • Automatic with DataLoader;
  • Redis/Memcached
    • External cache for query results;
    • Shared across server instances;
    • Set TTL based on data volatility;
4. Cache Invalidation
  • Time-Based (TTL)
    • Cache expires after set time;
    • Simple but may serve stale data;
    • Good for data that changes predictably;
  • Event-Based
    • Invalidate cache on mutations;
    • Clear related data when entity changes;
    • More complex but more accurate;
  • Tag-Based
    • Tag cache entries by entity type;
    • Invalidate all entries with tag;
    • Example: clear all "User:123" tagged entries;
  • Hybrid Approach
    • Combine TTL with event-based;
    • TTL as fallback, events for immediate updates;
    • Balance freshness and performance;
