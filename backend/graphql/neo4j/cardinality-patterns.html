1. One-to-One Relationships
  • Pattern
    • Each entity relates to exactly one other entity;
    • GraphQL: type User { profile: Profile };
    • GraphQL: type Profile { user: User };
  • Neo4j Implementation
    • (u:User)-[:HAS_PROFILE]->(p:Profile);
    • Use uniqueness constraint to enforce one-to-one;
  • Examples
    • User → Profile;
    • Employee → Desk;
    • Country → Capital;
2. One-to-Many Relationships
  • Pattern
    • One entity relates to multiple entities;
    • GraphQL: type User { posts: [Post] };
    • GraphQL: type Post { author: User };
  • Neo4j Implementation
    • (u:User)-[:POSTED]->(p1:Post);
    • (u:User)-[:POSTED]->(p2:Post);
    • One user, multiple POSTED relationships;
  • Examples
    • User → Posts;
    • Company → Employees;
    • Category → Products;
3. Many-to-Many Relationships
  • Pattern
    • Multiple entities relate to multiple entities;
    • GraphQL: type User { friends: [User] };
    • GraphQL: type Movie { actors: [Actor] };
    • GraphQL: type Actor { movies: [Movie] };
  • Neo4j Implementation
    • (u1:User)-[:FRIENDS_WITH]->(u2:User);
    • (a:Actor)-[:ACTED_IN]->(m:Movie);
    • Multiple relationships from both sides;
  • With Metadata
    • (a:Actor)-[:ACTED_IN {role: "Hero"}]->(m:Movie);
    • Store additional data on relationship;
4. Choosing the Right Pattern
  • Consider Cardinality
    • How many related entities typically exist?;
    • Will this change over time?;
  • Query Patterns
    • Do you need to traverse from both directions?;
    • Need to filter or sort by relationship properties?;
  • Performance
    • One-to-many: Use pagination for large lists;
    • Many-to-many: Consider intermediate nodes for complex cases;
