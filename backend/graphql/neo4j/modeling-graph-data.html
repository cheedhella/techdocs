1. Core Principles
  • Model for Queries
    • Design based on how you'll query the data;
    • Optimize for common access patterns;
    • Different from relational normalization;
  • Relationships Are Cheap
    • Don't be afraid to create many relationships;
    • Traversing relationships is fast;
    • More relationships = more query flexibility;
  • Denormalization Is OK
    • Duplicate data when it improves query performance;
    • Graph databases handle redundancy differently;
2. When to Use Nodes vs Properties
  • Use Nodes When:
    • Entity has its own identity;
    • Need to connect to other entities;
    • Need to query or filter by it;
    • Example: User, Product, Company;
  • Use Properties When:
    • Simple attribute of an entity;
    • Not connected to other entities;
    • Example: name, age, email, price;
  • Example
    • Good: (u:User)-[:LIVES_IN]->(c:City) - City is a node;
    • Bad: (u:User {city: "New York"}) - if you need to query by city;
3. Relationship Modeling Patterns
  • Specific Relationship Types
    • Use meaningful names: :MANAGES, :REPORTS_TO, :PURCHASED;
    • Avoid generic: :RELATED_TO, :CONNECTED;
  • Intermediate Nodes
    • For many-to-many with metadata;
    • (u:User)-[:MADE]->(o:Order)-[:CONTAINS]->(p:Product);
    • Order stores purchase details;
  • Qualified Relationships
    • Add properties to relationships for context;
    • -[:KNOWS {since: 2020, strength: 0.8}]->
4. Common Anti-Patterns
  • Storing Lists of IDs
    • Bad: {friendIds: [1, 2, 3]};
    • Good: Use actual relationships;
  • Dense Nodes
    • Nodes with millions of relationships;
    • Can cause performance issues;
    • Solution: Use intermediate nodes or time-based bucketing;
  • Over-Normalization
    • Don't apply relational database rules blindly;
    • Some duplication is acceptable;
