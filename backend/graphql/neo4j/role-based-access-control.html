1. What Is RBAC?
  • Definition
    • Access control based on user roles;
    • Users assigned roles (admin, editor, viewer);
    • Roles have specific permissions;
  • Benefits
    • Centralized permission management;
    • Easy to add/remove permissions;
    • Scalable for large applications;
2. Implementing RBAC in GraphQL
  • Store Roles in JWT
    • Include roles array in JWT payload;
    • { sub: "user123", roles: ["admin", "editor"] };
    • Available as $jwt.roles in @auth rules;
  • Schema-Level Rules
    • type Post @auth(rules: [{operations: [CREATE], roles: ["editor", "admin"]}]) {
    • title: String!
    • };
    • Only editors and admins can create posts;
3. Common Role Patterns
  • Admin Role
    • Full access to all operations;
    • @auth(rules: [{roles: ["admin"]}]);
    • Can bypass other restrictions;
  • Hierarchical Roles
    • Admin > Editor > Viewer;
    • Higher roles inherit lower role permissions;
    • Implement in application logic;
  • Resource-Specific Roles
    • Project admin, team member;
    • Roles scoped to specific resources;
    • Store in graph relationships;
4. Advanced RBAC
  • Combining Rules
    • @auth(rules: [{roles: ["admin"]}, {allow: {owner: "$jwt.sub"}}]);
    • Admin OR owner can access;
    • Rules are OR'd by default;
  • Graph-Based Roles
    • Store roles as relationships in Neo4j;
    • (user:User)-[:HAS_ROLE]->(role:Role {name: "admin"});
    • Query roles dynamically;
    • More flexible than JWT roles;
  • Permission Checks
    • Use @cypher for complex permission logic;
    • Check graph relationships;
    • Example: user is member of project team;
