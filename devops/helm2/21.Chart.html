Charts.yaml 
    apiVersion
        - It should be v2 for Helm charts that require at least Helm 3;
    name 
    description 
    type  -> application | library;
        Library 
            - They contain utility functions; Application charts can depend on the library charts;
            - As they don't define any templates, they can't be deployed;
        Application 
            -
    version
        It represents the version of the helm chart; Major.Minor.Patch;
        It should be incremented each time you make changes to the chart and its templates, including the app version;
    appVersion 
        It represents the version of the application;
        For eg, a drupal chart with appVersion: "8.2.1", indicates that the version of Drupal included in the chart (by default) is 8.2.1;
        You can override it, during the packaging time: helm package . --app-version 9.1.2 
        You can override it, during the release(install/upgrade) time: helm upgrade <release_name> <chart> --set "image.tag=9.1.2"

Values.yml 
    It contains default configuration for the chart;
    You can override the values in the Values.yml, using: -f myValues.yml, --set key=value 

charts folder

    - Templates when combined with Values.yml, will generate valid k8s manifest files;
    - Helm runs each file in this directory through a GO template rendering engine;

Values.yaml 
    serviceAccount:
    # Specifies whether a service account should be created
    create: true
    # Annotations to add to the service account
    annotations: {}
    # The name of the service account to use.
    # If not set and create is true, a name is generated using the fullname template
    name: myfirstapp  <--- Please do note this value
  
    Note : The serviceAccount section in the values.yaml file of a Helm chart provides configuration options for creating and configuring a Kubernetes service account to be used by the application deployed via the chart.
    The create field specifies whether a service account should be created. 
    If set to true, a service account will be created for the application. 
    If set to false, the application will use the default service account.








Deployment.yml specifies the desired state of a containerized application in Kubernetes, including replication, rolling updates, scaling, health checks, and resource allocation
Services.yml defines a stable network endpoint for accessing a deployment.
Ingress.yml provides routing rules for incoming traffic.
hpa.yml sets up automatic scaling of deployments based on resource utilization
