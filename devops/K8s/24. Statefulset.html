What is StatefulSet?
	It is used to deploy stateful applications;

What are the characterstics of stateful applications?
	- Persistent and Unique Pod Name
		-- Every Pod created by a StatefulSet gets a unique pod name;
		-- That identity is persisted even after pod restarts, rescheduling and even cluster upgrades;
		-- For eg, If you create a StatefulSet with name mysql and 3 replicas, it creates 3 pods: mysql-0, mysql-1, mysql-2;
		-- Why is it important?
			-- It is needed for ordered start and scaling, persistent DNS, persistent storage mapping;
	- Persistent and Unique DNS Name
		-- Headless service(ClusterIP: None) is used for stable DNS;
	- Persistent and Unique storage 
		-- When a Pod is created, a persistent volume is created based on volumeClaimTemplate and associated with the Pod;
		-- When a Pod is deleted or rescheduled, associated volume is not deleted, this ensures data persistence;
	- Ordered deployment and scaling 
		-- Pods are created/updated in forward order (0 -> N), one after one;
		-- Pods are deleted in reverse order (N -> 0), one after one;
		-- Pods are scaled in order;

Usecases
	- Databases such as MySQL, PostgreSQL, Cassandra, ElasticSearch;
	- Message queues such as Kafka, RabbitMQ;
	- Distributed key-value stores such as Zookeeper, etcd;
	- Streaming platforms such as Spark, Flink;
	- Any service that requires:
		-- Persistent storage; // Stateful monitoring with prometheus;
		-- Stable network identity;
		-- Ordered startup/shutdown;

What is headless service?
	It is a special type of service that doesn't have assigned any IP;
	It is useful when you want to expose the underlying Pods directly, rather than load balancing or routing the traffic through a single IP address;

How it works?
	Instead of resolving to a single service IP, a headless service's DNS name (like my-service.default.svc.cluster.local) returns multiple A (or SRV) records, one for each Pod backing the service, each contains IP of the Pod;

Why the Pods are started one after another and on order(1 to n)?
	If you start all Pods at once, then each pod fails to joins the cluster as DNS refereces to offline pods, causing each pod creating a separate cluster;

What is the need to delete one Pod after another, on scale down?
	As Statefulset is for stateful applications, clustered apps can potentially lose data if multiple replicas are terminated simultaneously;
	StatefulSets ensures there is no data loss, by deleting the pods one after another;

How is unique ID is useful?
	- Unique Identify
		-- Every Pod created by a StatefulSet gets a unique ID, like my-pod-0, my-pod-1 etc; That identity is persisted even after pod restarts, rescheduling and even cluster upgrades;
		-- Applications like Kafka, Zookeeper require this;
		-- How unique ID helps Zookeeper?
			-- ZooKeeper is a quorum-based system where each node (called a server) must have a unique ID, written in a file called myid;
			-- Quorum specifies the minimum number of nodes that must agree to take a decision; For eg, in a 3-node cluster, if 2 nodes acknowledge, then the write operation is considered completed;
			-- How voting works?
				When Zookeeper starts:
					-- Each node broadcasts it's id and epoch;
					-- A voting round begins, where each node proposes itself or another node as leader;
					-- ZooKeeper selects the leader based on:
						-- Highest transaction ID (zxid) (i.e, who has the most up-to-date data);
						-- If tie: higher myid wins the vote
		-- How unique ID helps Kafka?
			-- Each kafka broker will have a unique broker.id;
			-- How controller voting works?
				-- Controller is a special broker that manages partition leadership and cluster metadata;
				-- The broker with the lowest broker.id typically becomes the controller;
	- Stable DNS Name
		
	- Ordered deployment and scaling 
		-- It deploys Pods sequentially, one after another, from lower index to higher; Specifically, it checks the pod's readiness probe;
		   This helps in:
		   	Cluster bootstrapping
			Peer discovery
			Leader election
			Ensuring quorum nodes are ready before followers start
		-- Pods are terminated in reverse order, one after another, from higher index to lower;
			This helps with:
				Letting followers shut down before leaders (e.g., Kafka)
				Avoiding loss of quorum
				Giving clients time to migrate connections
				Flushing logs, closing connections, etc.
		-- If pods start randomly or shut down simultaneously, it could cause: Split-brain scenarios, Failures in leader election, Temporary unavailability;
		-- Scaling 
			-- When you increase replicas from 3 to 5, Kubernetes will: Create my-app-3, Wait for it to be Ready, Then create my-app-4;
			-- When scaling down from 5 to 3 replicas: Kubernetes deletes my-app-4, Waits for it to shut down cleanly, Then deletes my-app-3;
	- Persistent Storage Binding 
		- StatefulSet creates volumes that are indexed;
		  For eg, it creates volumes: data-mysql-0, data-mysql-1 etc;
			volumeClaimTemplates:
				- metadata:
				  name: data
		  Each pod keeps its volume even if it restarts or moves. This ensures data isn't lost and is always matched to the right pod by name.


		  	
		When a pod is deleted, Kubernetes ensures that any associated persistent volumes are not deleted until the pod is completely terminated. 
		This ensures that data is not lost when pods are scaled down or replaced.

How Deployment Chooses Pods to Scale Down
When reducing replicas (e.g., from 5 to 3), Kubernetes uses the ReplicaSet controller behind the scenes, which handles the actual Pods. Here's the key logic:

Pod Deletion is Randomized (but fair):

Kubernetes doesn't have a strict order (like oldest/youngest).

It picks any of the Pods associated with the ReplicaSet—selection can seem random but is actually based on internal implementation, like the order in the API server.

Pod Priority & Graceful Termination:

If any PodDisruptionBudgets (PDBs) or terminationGracePeriodSeconds are set, those are respected.

Kubernetes also honors Pod priority, taints, and node pressure if those are configured.

Deletion Cost (Kubernetes v1.21+):

You can influence which Pod is deleted using the controller.kubernetes.io/pod-deletion-cost annotation.

Higher value = less likely to be deleted.

Lower value = more likely to be deleted.

This is useful in multi-zone or cost-sensitive deployments.



Structure of a StatefulSet Manifest
A StatefulSet manifest, defined in YAML, describes the desired state of your application. It's similar to a Deployment manifest but includes key additions for stateful applications. Your StatefulSet manifest must define:

serviceName: This field specifies the headless service that manages network identities for your pods.
replicas: Like Deployments, this indicates the desired number of pods.
selector: This ensures the StatefulSet manages the correct pods, matching labels defined in the pod template.
template: This section defines the pod template, similar to Deployments, specifying the container images, resource requests, and other pod configurations. It also includes the labels that link back to the StatefulSet's selector.
volumeClaimTemplates: This section, specific to StatefulSets, defines the PersistentVolumeClaims that provide persistent storage to each pod. Each pod gets its own PersistentVolume based on this template, ensuring data persists across restarts and rescheduling.

# StatefulSet to deploy a MySQL cluster;

# Create a headless service, which provides stable DNS for each Pod, allowing them to discover each other directly for replication;
apiVersion: v1
kind: Service
metadata:
  name: mysql-headless-svc 									# Name of the service and it's labels;
  labels:
    app: mysql
spec:
  ports:
  - port: 3306												# Expose port 3306, default MySQL port;
    name: mysql
  clusterIP: None											# Headless service - Critical for stateful apps like mysql clusters, where each node must be accessible directly;
  selector:													# It selects all Pods with label - app: mysql-pod
    app: mysql-pod
---
apiVersion: v1
kind: Secret
metadata:
  name: mysql-secret
type: Opaque 												# Opaque secrets are base64 encoded, but not encrypted at rest by default
data:
  # Base64 encoded values for passwords.
  # You should generate these outside of Kubernetes and paste them here,
  # or use `kubectl create secret generic ... --from-literal` as shown below.

  # Example of how to generate base64 encoded values:
  # echo -n 'YOUR_ROOT_PASSWORD' | base64
  # echo -n 'YOUR_USER_PASSWORD' | base64

  mysql-root-password: <BASE64_ENCODED_ROOT_PASSWORD> 		# Replace with your base64 encoded root password
  mysql-user-password: <BASE64_ENCODED_USER_PASSWORD> 		# Replace with your base64 encoded user password
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql-pod
spec:
  serviceName: mysql-headless-svc 							# It specifies the headless service to use for forming the cluster;
  replicas: 3												# 3 Pods/replicas - named mysql-0, mysql-1, and mysql-2;
  selector:													# It manages all the pods with label app: mysql-pod only;
    matchLabels:
      app: mysql-pod 										
  template:													# Template for each Pod;
    metadata:
      labels:												# Labels for each Pod;
        app: mysql
    spec:
      containers:											# Containers specification;
        - name: mysql
          image: mysql:5.7
          env:
		    - name: MYSQL_ROOT_PASSWORD 					# It gets the root password to use from the specified secret;
              valueFrom:
				secretKeyRef:
				  name: mysql-secret 						# Assumes a secret named 'mysql-secret' exists
				  key: mysql-root-password
            - name: MYSQL_DATABASE 							# Optional: Define a default database
              value: "mydatabase"
            - name: MYSQL_USER 								# Optional: Define a default user
              value: "myuser"
            - name: MYSQL_PASSWORD 							# Optional: Define password for the default user
              valueFrom:
                secretKeyRef:
                  name: mysql-secret
                  key: mysql-user-password
          ports:
            - containerPort: 3306
              name: mysql
          volumeMounts:										# Mount volume at /var/lib/mysql, where MySQL stores data;
            - name: mysql-data
              mountPath: /var/lib/mysql
		  # Health checks for robust operation
		  livenessProbe:
		    tcpSocket:
			  port: 3306
			initialDelaySeconds: 30
			periodSeconds: 10
			timeoutSeconds: 5
			successThreshold: 1
			failureThreshold: 3
		  readinessProbe:
			tcpSocket:
				port: 3306
			initialDelaySeconds: 10
			periodSeconds: 5
			timeoutSeconds: 3
			successThreshold: 1
			failureThreshold: 3
		  resources: 										# Define resource requests and limits
			requests:
				memory: "512Mi"
				cpu: "250m"
			limits:
				memory: "1Gi"
				cpu: "500m"
  volumeClaimTemplates: 									# Each Pod gets it's own PersistentVolumeClaim created from this template, which provisions a persistent storage for each Pod;
    - metadata:
        name: mysql-data
      spec:
        accessModes: [ "ReadWriteOnce" ] 					# Only one Pod can mount the volume at a time;
        resources:
          requests:
            storage: 1Gi 									# Requests 1GB of storage for each Pod;
