What is Container Orchestration?
	Say, you have below requirement:
		- I want 10 instances of Microservice A container, 20 instances of Microservice B container etc;
		- Auto scaling: scale containers based on load;
		- Service Discovery: Help microservices find each other;
		- Load Balancing: Distribute load among multiple instances of a microservice;
		- Self Healing: Do health checks and replace failing instances;
		- Zero Downtime Deployments: Release new versions without downtime;
	A container orchestration framework will help with all the above requirements;

Container Orchestration Frameworks
	- Elastic Container Service(AWS specific);
	- Fargate(Serverless version of ECS, AWS specific);
	- Kubernetes(Works with any cloud provider);

You need to run below k8s commands to meet above requirements:
	# It deploys the application in the Cluster that you are connected to!
	kubectl create deployment hello-world-rest-api --image=in28min/hello-world-rest-api:0.0.1.RELEASE 
	# Expose the deployment to outside world!	
	kubectl expose deployment hello-world-rest-api --type=LoadBalancer --port=8080

	// If you want 3 more instances right away, independant of load?
	kubectl scale deployment hello-world-rest-api --replicas=3

	// If you want bring up new pods, based on load(when cpu utilization goes beyond 70)?
	kubectl autoscale deployment hello-world-rest-api --min=1 --max=10 --cpu-percent=70

	// If you want to bring up another instance, when one of them goes down!
	// Try deleting one of the instance manually, k8s automatically brings up another instance!
	kubectl delete pod hello-world-rest-api-232322

	// you want to upgrade all containers to 0.0.2.RELEASE version of image;
	kubectl edit deployment hello-world-rest-api 	# change 'minReadySeconds: 45' to 'minReadySeconds: 15'
	kubectl set image deployment hello-world-rest-api hello-world-rest-api=in28min/hello-world-rest-api:0.0.2.RELEASE

What is Node?
	What is K8s - It is the best resource manager ever;
	What resources it manages? It manages your servers; Because, these servers are in the cloud, they are virtual servers;
	Different cloud providers gave different names to those servers: AWS calls it EC2, GCP calls it Compute Engine, Azure calls it Virtual Servers;
	K8s gave all of them a generic name called Node;

	K8s can manage thousands of Nodes; What do you when you have 1000s Nodes to manage? You introduce managers;
	In k8s, these managers are nothing but Master Nodes;
	Typically, you will have 1 master node; But, if you need high availability, go for multiple master nodes;

What is Cluster?
	It is nothing but a set of Nodes;
	Nodes that actually does the work are called Worker Nodes;
	Master nodes ensure that nodes are available and do some useful work;

> kubectl get events 		# You will see lot of events: it created a pod, replicaset, deployment, service etc;   

# When you create a deployment, it internally creates a Pod, Replicaset, Deployment etc;
# Why? Because K8s follows single resposibility principle; Each of them have an important role to play!

What is a Pod?
	Pod is the smallest deployable unit;
	You might think container is the smallest deployable unit? Not the case in K8s!
	In K8s, you can't have a Container without Pod! Container lives in a Pod;

	So, what does a Pod can have?
		- Check the output of: kubectl get pod -o wide;
		- Each pod will have a unique IP address;
		- 1/1 -> Number of containers in that Pod and how many of them are ready;

	A pod can have multiple containers;
	All containers in a Pod share the resources;
	Within the Pod, containers can talk to each other using localhost;

	A pod can have a namespace, labels, annotations;

	A pod can have a Status; 

What is a Replicaset?
	It ensures that specific number of Pods are running at all times;
	It always keeps monitoring the pods and if there are lesser number of pods than what is needed, then it creates new pods;

	How can I tell the replica set to maintain a higher number of pods? 
	The way we can do that in Kubernetes is by saying: kubectl scale deployment --replicas=3

	So, what we now have is more than two instances of the application running and they are also having load distribution between them.
	Let's not worry about the load distribution part for now.

	In practice, you would see that a replica set is always tied with a specific release version.


What is a Deployment?
	Typically, we want to update applications and when we update, we want zero downtime;

	kubectl set image deployment <deploymentName> <containerName>=<imageName>

	The strategy which the deployment is using, by default, is something called rolling updates.



What is a Service?
	Service gets created, when you expose a deployment;
	It allows your application to receive traffic through a permanent lifetime IP address;
	It provides an always-available external interface to the applications which are running inside the pods;

	If you access the URL, while the pods are being deleted and new ones are being launched up, you would see that this service is always up and running.
	How is this magic happening?
	This magic is happening because of something called a Service. In the Kubernetes world, a pod is a throw away unit.
	Your pods might go down, new pods might come up whenever I do a new release, there might be several new pods which are 
	created, and the old pods completely go away.
	Irrespective of all the changes happening with the pods, we don't want the consumer side of things to get affected.
	We don't want the user of the application to use a different URL, that's the role of a service.

	LoadBalancer - it balances the load b/w all active pods;
	ClusterIP
		You can see that the Kubernetes service is actually running as a ClusterIP service.
		A ClusterIP service can only be accessed from inside the cluster.
		You will not be able to access this service from outside the cluster.
		You can see that there is no External-IP for this specific service.
		So, if you have any services which are directly consumed inside your cluster, you can have them use a ClusterIP.
