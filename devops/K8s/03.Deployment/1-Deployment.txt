What is Deployment? // Deployment = ReplicaSet + Rollout and Rollback;
	- Let's say you have a Pod running V1 of an application; 
	  Your team has developed V2 and you would like upgrade the Pod with V2?
	  How would you upgrade the pods with latest version? 
	  How about rolling back, if you find any issues with V2? 
	  Can Replicaset handle Rollout and Rollback? Not really!
	  Deployment does it!

	- It extends Replicaset and provides below features:
		-- Rollout new software versions;
		-- You can also pause/resume/stop the rollouts that are in-progress;
		-- Rollback to older version(k8s maintains a history of Rollouts);

	Every Deployment manages one or more identical Pods. Stateless apps;


------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
K8s supports 2 deployment strategies: Recreate Strategy, Rolling Update Strategy; It defaults to Rolling Update strategy;

Recreate Strategy
	- It will first deletes all the pods and then creates new pods with new version of the image;
	- This strategy is often used in development environments, where downtime is acceptable;

Why Zero Down Time?
	- The Deployment must produce no downtime; 
	  It does not matter whether it is performed on a testing or a production cluster;
	  Interrupting consumers is disruptive and leads to a loss of money and confidence in a product;
	- Gone are the days when users did not care if an application sometimes did not work;
	  There are so many competitors out there that a single bad experience might lead users to another solution;
	  With today’s scale, a 0.1% rate of failed requests is considered disastrous;
	- While we might never be able to reach 100% availability, we should certainly not cause downtime ourselves and must minimize other factors that could cause downtime;
	- Deployment is a tool that helps us avoid such failures, by allowing us to update our applications without downtime;
	
Rolling Update Strategy
What is Rollingupdate?
	When you upgrade, do you think it is a good idea to upgrade all PODs at once?
	Definitely not! What if there are issues with V2? Your application will run into problems, as all pods are upgraded to V2;
	One of the upgrade strategies is Rollingupdate;

	Rollingupdate - It upgrades the Pods in batches; If you find any issues with V2, you can pause the upgrade, inspect and stop if needed;
	This will prevent downtime for the application, as there are pods with older version, which can serve the requests;

	- It creates a new replicaset with updated version of the image;
	- It first creates one new pod with new version of the image and then deletes one old pod, and repeats the process for all pods;
	- Once all pods are upgraded, it won't delete the replicaset, as old replicaset will be used during rollback;
	- There is only one replicaset in active state, with DESIRED > 0;

	- In other words, pods are upgraded in batches; Thus, Users of the application could face no downtime, ensuring high availability;

	- It takes 2 important optional parameters:
		-- maxSurge 
			--- It specifies the number of pods to upgrade at a time; Defaults to 25%;
			--- Assume we have 4 pods and if it is 25%, then it upgrades one pod at a time;
		-- maxUnavailable
			--- It ensures that there are minimum number of pods are always up and running;
			--- Assume we have 4 pods and if it is 25%, then it ensures 75% of the pods(3 pods) are up and running;

	- Note that, If you set maxSurge/maxUnavailable to low values, your upgrade usually takes longer time;

Docker Swarm VS k8s Deployment 
	Both serve the same purpose and can be used to deploy new applications or update those that are already running inside a cluster;
	In both cases, we can easily deploy new releases without any downtime (when application architecture permits that).
	
	Differences:
		- A k8s Deployment will not perform any corrective action in case of a failure;
		  It will stop the update, leaving a combination of new and old Pods running in parallel;
		- On the other hand, Docker Swarm can be configured to roll back automatically;

		- We can use the kubectl rollout status command to determine whether the update was a success or failure.
		  In case the update is a failure, we can also undo the rollout.
