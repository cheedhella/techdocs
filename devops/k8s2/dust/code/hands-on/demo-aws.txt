It doesn't matter if reports from vehicles have stopped coming in, as long as the service event is eventually restored;
But, within a few minutes, we should see reports coming in again;

How do we know which pod is running on which Node? 
	kubectl get pods -o wide

You can kill a node: Goto instance -> find which node is having webapp pod and terminate it;
Underlying replicaset quickly brings up that pod in another node; In that short gap, if you try to access, you will see a spinner/loading;

If you refresh again the instances page, you would see a new instance is up, in place of the dead node;
But, that is not because of rs/k8s, but because of auto scaling group;
Click on Auto Scaling Group -> select the group -> check activity history, to find what happened;

But, because another node is available doesn't mean that k8s is going to shift some of existing pods to that Node;

Solution to above requirement is: increase the number of replicas to 2;
Given that, we have each node in a separate availability zone, we have a high resilent system;

You can't have replicas for queue pod, b/c it stores data and it is stateful; 
If you replicate it, you're going to end up with a kind of a split brain situation, where half the data is in one part, half the data is in the other part;
Really what you're aiming for with any pod is to make it stateless, so it's not holding data;

Requirement: make queue and mongoDB pods stateless;

Luckly, ActiveMQ supports replication; You could work quite hard to configure that so that you can run multiple instances of that pod;
An easier way could be look to your cloud provider and see if they have a hosted service that does the same job that your pod was doing;
Amazon do indeed have a managed mass message broker service for Apache ActiveMQ.
You would configure an Amazon MQ instance in your Amazon account, and that would give you a URL for a queue, and then you would just have 
to re-engineer your code so it works with this hosted queue and you can get rid of queue pod entirely;

It's the same story with MongoDB;
Amazon have a very simple NoSQL data store called SimpleDB, which I think would meet the requirements quite well.
Failing that, there's Amazon DynamoDB, a more complicated database.
Or they have a hosted version of MySQL;

There are many tools to setup a cluster in the cloud; But, there are 2 by far most popular tools: Kops and EKS;
KOPS: It helps you to create, destroy, upgrade and maintain production-grade, highly available k8s cluster from command line; 
You could use it with many cloud providers such as AWS, GCE etc;

KOPS vs EKS
	- One major difference is: 
	  In case of KOPS, master node EC2 instance appear in your account, just like other nodes;
	  So, an administrator can kill and restart the master node;
	  Even without master node, the worker nodes will continue to work just fine;
	  
	  In case of EKS, you have no visibilit of it; It runs in the background; It is protected by Amazon;
	  Some administrators don't like it; But, administrator has less to worry about it, as it is managed by Amazon;

	  It's possible that more than half of the projects in the world on Kubernetes now are using EKS;

	  In case of KOPS, you could have more than 1 master;
	  EKS - Amazon hosted version of k8s;
