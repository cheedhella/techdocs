Taints and Tolerations

1. Concept
  • Taints are applied to nodes — they repel Pods from being scheduled;
  • Tolerations are applied to Pods — they allow Pods to be scheduled on tainted nodes;
  • Think of it as: taints are "keep away" signs, tolerations are "I can handle it" passes;
  • Tolerations do NOT guarantee scheduling — they just allow it;
2. Taint Effects
EffectDescription
NoScheduleNew Pods won't be scheduled on this node (existing Pods stay)
PreferNoScheduleScheduler tries to avoid this node but doesn't guarantee it
NoExecuteNew Pods won't be scheduled AND existing Pods without toleration are evicted
3. Managing Taints
# Add a taint
kubectl taint nodes worker-1 key=value:NoSchedule

# Examples
kubectl taint nodes worker-1 gpu=true:NoSchedule
kubectl taint nodes worker-1 dedicated=ml-team:NoExecute

# Remove a taint (add minus at the end)
kubectl taint nodes worker-1 gpu=true:NoSchedule-

# View taints
kubectl describe node worker-1 | grep Taint
4. Pod Tolerations
spec:
  tolerations:
    # Exact match
    - key: "gpu"
      operator: "Equal"
      value: "true"
      effect: "NoSchedule"

    # Match any value for the key
    - key: "dedicated"
      operator: "Exists"
      effect: "NoExecute"
      tolerationSeconds: 3600   # Tolerate for 1 hour, then evict

    # Tolerate ALL taints (use with caution)
    - operator: "Exists"
5. Common Use Cases
  • Dedicated nodes: Taint GPU nodes so only ML workloads run on them;
  • Master nodes: Control plane nodes are tainted with NoSchedule by default;
  • Node maintenance: Taint a node with NoExecute to drain workloads;
