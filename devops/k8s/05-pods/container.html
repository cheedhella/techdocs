1. What is a Container?
  • Container is instance of Image;
  • Containers are stateless, immutable and disposable/ephemeral;
    • Stateless: Container doesn't have any state of it's own; If you need a state, use volumes or databases;
    • Immutable: You can't make any changes to a running container; If you need a change, create new image and redeploy it;
    • Why Stateless and Immutable? It allows k8s to:
      • Restart a container without losing any data;
      • Scale up/down as needed;
      • Replace a failed container with a new one;
      • Reschedule a container to a different node;
2. Relationship between Pod and Container
  • A Pod is the smallest deployable unit in Kubernetes — not a container;
  • A Pod wraps one or more containers;
  • What they share?
    • All containers in a Pod share the same network namespace(IP Address, Port Space);
      • Every Pod gets it's own IP address, which is unique within the cluster;
      • Container doesn't have it's own IP address; All containers in a Pod share the IP address of their Pod;
      • Containers within the same Pod communicate via localhost;
      • You can't run multiple containers on the same port in the same Pod;
    • Storage volumes
  • What they don't share?
    • Container Image
    • File system - Each container has it's own file system;
    • Environment variables
    • CPU/Memory limits
3. Container YAML Configuration
- name: web                                 # Name of the container, must be unique with in a Pod. You can't update it, once container is created.
  image: nginx:latest                       # Name and tag of Docker Image.
  imagePullPolicy: IfNotPresent
  workingDir: /app                          # Working directory for the container; Commands are executed from this directory; All relative paths are resolved relative to this directory; It overrides WORKDIR instruction in Dockerfile;
  command: [ "echo" ]
  args: [ "Hello k8s" ]

  ports:
    - containerPort: 80
      name: http
      protocol: TCP

  env:
    - name: ENV
      value: production

  resources:
    requests:
      cpu: 100m
      memory: 128Mi
    limits:
      cpu: 500m
      memory: 512Mi

  volumeMounts:
    - name: config
      mountPath: /etc/config

  livenessProbe:                          # Detect broken container; If broken, kubelet will restart the container; It doesn't wait for the readiness probes to succeed; If you want to wait, use initialDelaySeconds;
    httpGet:                            
      path: /health
    port: 80
    initialDelaySeconds: 10
    periodSeconds: 5

  startupProbe:                           # Wait for the container to start up; If not started, kubelet will restart the container;
    httpGet:
      path: /health
      port: 8080
    failureThreshold: 30
    periodSeconds: 10

  readinessProbe:                         # Determine if ready for traffic; If not ready, kubelet will not send any traffic to the container;
    httpGet:
      path: /ready
      port: 8080
    periodSeconds: 5
3. Lifecycle and Hooks
PhaseDescription
WaitingContainer is not yet running; Reason could be one of the errors: ContainerCreating, ErrImagePull, ImagePullBackOff, CrashLoopBackOff;
RunningContainer is running;
TerminatedContainer has finished execution (either successfully or with an error);
  • Common Reasons for Waiting State
    • ContainerCreating - Container is not yet running, being created; This is normal and temporary;
    • ErrImagePull - It indicates an error pulling the image from the registry, on first attempt; It could be because of:
      • Invalid image name or tag;
      • Image not found in the registry;
      • Authentication issue;
    • ImagePullBackOff - K8s is backing off (waiting) before retrying image pull, to avoid hammering the registry with requests; This state indicates that further pull attempts also failed;
    • CrashLoopBackOff - Container has started and crashed; K8s backed off before restarting and restart also crashed; Repeated crashes indicate a problem with the application code;
  • Lifecycle Hooks
    • postStart - Runs immediately after the container is started;
    • postStart:
    exec:
      command: ["/bin/sh", "-c", "echo started > /tmp/started"]
    • preStop - Executed immediately before a container is terminated;
    • preStop:
    httpGet:
      path: /health
      port: 8080
image
  • Specifies the Docker image name and tag to use for the container;
  • Format: registry/repository:tag (e.g., nginx:latest, gcr.io/my-project/my-app:v1.2);
  • If no tag is specified, :latest is assumed;
  • If no registry is specified, Docker Hub is assumed;
3. imagePullPolicy
  • It tells kubelet when to pull the image from the registry, while creating a container;
  • It can be Always, Never, IfNotPresent; Defaults to Always if tag is :latest; Otherwise, IfNotPresent;
  • Always - It will not blindly download the image always; But, It always contacts registry for the digest and matches it with the local cache; It there is a mismatch, it downloads the image(only the layers that are not matching) from registry; It does this, even when the container is restarted;
  • IfNotPresent - It contacts registry only if that image is not present in local cache;
  • Never - It never pulls the image from docker registry;
4. command and args
  • command: It overrides the default startup command(ENTRYPOINT) defined in docker image; This is executed every time the container is started;
  • args: It overrides the default arguments(CMD) defined in docker image, which are passed to the command;
  • If you define args without a command, default command is used with new args;
  • If you define command without args, default args are used with new command;
  • If you define command and args, command is executed with new args;
  • By default, command is not executed within a shell; It is executed directly as a process by the container runtime; So, things like pipes(|), redirection(>), environment variables expansion($HOME), chaining(&&) will not work;
  • If you want to execute a command in the shell, do this: command: ["/bin/sh", "-c"] args: ["echo hello && sleep 10"]
workingDir
  • Sets the working directory for the container's main process;
  • Commands are executed from this directory; All relative paths are resolved relative to this directory;
  • It overrides the WORKDIR instruction in the Dockerfile;
  • If not specified, the container runtime default is used (usually / or the WORKDIR from the image);
5. ports
  • It can be a single port or a list of ports;
  • Each port can have a name, protocol and port number;
  • containerPort:
    • server.port=8080 in application.yml -> Actual port on which the application is listening;
    • It doesn't override the port on which the application is listening;
    • It is used to pass the port to the container runtime;

    • Why is this needed? Container can run absolutely fine without this; But, it is used by other resources like Service, Ingress, etc to route traffic to the container;
    • Can containers running in different pods(may be same or different nodes) use same port?
      • Yes, they can; But, they need to be in different pods; If they are in the same pod, they will conflict;
    • What is the purpose of supporting multiple ports in container spec?
      • Many modern apps expose a metrics port separate from the main API;
      • Eg: Prometheus 8080 for REST API and 9090 for metrics;
      • Application can support multiple protocols like HTTP(60), HTTPS(443), TCP(9090), gRPC(50051), etc;
  • name: Optional name for the port; Used by other resources like Service, Ingress, etc;
  • protocol: Protocol for the port; Can be TCP, UDP or SCTP; Defaults to TCP;
  • hostPort
    • It maps a port on the node (host machine) to a port inside the container;
    • It is optional and if not specified, a random port is assigned;
    • Only one Pod per node can use a given hostPort;
    • It is rarely used; Alternatively, use: ClusterIP, NodePort, LoadBalancer, Ingress;
    • When is it used?
      • Monitoring agents like Prometheus, Grafana, etc;
      • Log collectors
      • These often run as DaemonSets so each node has one Pod;
  • hostIP
    • If hostIP is not specified, container will listen on all node interfaces; Eg: node-ip1:8080, node-ip2:8080, localhost:8080
    • If hostIP is specified, container is accessible only on that IP address;
    • - containerPort: 80 hostPort: 8080 http://node-ip:8080 -> http://container-ip:80 kubectl port-forward pod/my-pod 8080:80
    : It specifies the IP address of the host; It is optional and if not specified, the container will be assigned an IP address from the node's IP address space;
6. env
  • It defines environment variables that are avaialble inside the container; They are available to all processes in the container;
  • Instead of hardcoded values, k8s can pull these values from a ConfigMap or Secret or Pod metadata;
  • ConfigMap 
    # ConfigMap 
apiVersion: v1
kind: ConfigMap
metadata:
    name: app-config
data:
    APP_MODE: production

# Pod 
env:
    - name: APP_MODE
        valueFrom:
        configMapKeyRef:
            name: app-config
            key: APP_MODE
  • Secret 
    # Secret 
apiVersion: v1
kind: Secret
metadata:
    name: app-secret
data:
    DB_PASSWORD: cGFzc3dvcmQ=

# Pod 
env:
    - name: DB_PASSWORD
        valueFrom:
        secretKeyRef:
            name: app-secret
            key: DB_PASSWORD
  • Pod Metadata 
    # Pod 
env:
    - name: POD_NAME
        valueFrom:
        fieldRef:
            fieldPath: metadata.name

# Inside the container 
POD_NAME=myapp-7d8c9f   # Useful for logging, tracing etc;
  • Resource Fields - Application can then read its CPU limit; 
    # Pod 
env:
    - name: CPU_LIMIT
        valueFrom:
        resourceFieldRef:
            containerName: app
            resource: limits.cpu

# Inside the container 
CPU_LIMIT=500m   # Useful for logging, tracing etc;
  • If the value changes in a ConfigMap or Secret, the container must be restarted to see the change;
7. envFrom
  • Instead of mapping individual keys from a ConfigMap or Secret, envFrom loads all key-value pairs at once;
  • envFrom:
  - configMapRef:
      name: app-config
  - secretRef:
      name: app-secret
  • All keys from the referenced ConfigMap/Secret become environment variables inside the container;
  • You can add an optional prefix to avoid naming collisions;
8. resources
  • Example 
    • resources:
                        limits:
                          memory: "256Mi"
                          cpu: "500m"  # 500 millicores = 0.5 CPU
                          ephemeral-storage: "1Gi" 
                        requests:
                          memory: "128Mi"
                          cpu: "250m"
  • It defines the maximum amount of CPU and memory that a container is a allowed to use;
  • It ensure that a container doesn't effect other containers running on the same node;
  • CPU Limit
    • It defines the maximum CPU that a container is allowed to use;
    • It is specified in millicores; 1000 millicores = 1 CPU;
    • If a container exceeds its CPU limit, CPU throttling occurs;
  • Memory Limit
    • It defines the maximum memory that a container is allowed to use;
    • It is specified in bytes; Ki -> kibibytes; Mi -> mebibytes; Gi -> gibibytes;
    • If a container exceeds its memory limit, it is killed;
  • Ephemeral Storage Limit
    • It defines the maximum disk storage that a container is allowed to use; It is used for temporary storage; It is deleted when the container is deleted;
    • It includes /tmp, emptyDir volume etc;
    • If a container exceeds its ephemeral storage limit, it is killed;
  • Requests
    • It defines the minimum CPU and memory needed by the container;
    • When scheduling a Pod on a node, Kubernetes looks at requests, not limits; If the node doesn't have enough resources, scheduler will look for another node;
    • Limits are enforced after the container starts;
10. Probes
  • It is used to check the health of a container;
  • It can be a single probe or a list of probes;
  • Each probe can have a name and type;
  • There are 3 types of probes: Startup, Liveness, Readiness;
  • K8s uses probes to automatically restart the container if it is not healthy or ready to serve traffic;
  • Startup probe is executed only on startup, liveness and readiness probes are run periodically(as defined by periodSeconds) after startup probe succeeds;
  • Liveness probe 
    •                             - Liveness probe don't wait for the readiness probes to succeed; If you want to wait, use initialDelaySeconds;
- It is used check the health of a Pod - whether the Pod is up and running and responding(may be deadlocked and not responding);
- If the probe is successful, no action is taken and no logs are recorded;
- If a liveness probe fails failureThreshold number of times, kubelet will restart the application;

initialDelaySeconds -> how long to wait after the container starts and before sending the probe; Defaults to 0;
timeoutSeconds      -> how long to wait for the response, during probing; If the time is exceeded, probe is considered failed; Defaults to 1;
periodSeconds       -> It specifies the period/gap between each check; Defaults to 10;
successThreshold    -> Specifies the minimum consecutive successes for the probe to be considered successful after it has failed; Defaults to 1;
failureThreshold    -> Specifies the minimum consecutive failures for the probe to be considered failed after it has succeeded; Defaults to 3;

Type of probes 
- Command probe 
    -- It executes the specified command in the container and considers the container ready, if the command returns zero exit code;
- HTTP probe 
    -- It sends HTTP request to specified endpoint in the container and checks if it receives a successful response;
- TCP probe 
    -- It checks if a specific port is open and listening on the container;
  • Readiness probe
    • It indicates whether the container is ready to receive requests or not;
    • It is useful to perform time-consuming initial tasks, such as loading/warming caches etc;
    • If it fails, K8s will not send traffic to the container;
    • If a readiness probe fails failureThreshold number of times, kubelet will restart the application;
  • Startup probe
    • It is used to check if the container has started up;
    • If you specify a startup probe, k8s will not send any traffic to that pod, until that container's startup succeeds;
    • It is useful in some situations, where you have to deal with legacy applications that take lot of time to start up, thus avoiding them getting killed by kubelet, before they are up and running;
    • If you specify a startup probe, liveness and readiness probes will not run, until startup succeeds, making sure these probes don't interfere with the application startup;
    • If startup probe fails, kubelet logs an event, kills the container and follows the Pod's restartPolicy;
    • Make sure failureThreshold * periodSeconds is enough to cover the worst case startup time;
  • Example 
    • livenessProbe:
                        httpGet:
                        path: /healthz
                        port: 8080
  • Best Practices
    • Misconfigured probes can impact application performance, if they run too frequently;
    • If a container performs a simple operation and terminates quickly, it may not need health probe;
    • Set a realist wait time - if the readiness probe takes more than configured wait time, kubelet may assume the application is not responing and restart it, while it is still running;
    • Set a failure threshold for your liveness probes to avoid unnecessary restarts of your application;
    • Use the kubectl command-line tool to test your probes and make sure that they are correctly configured;
Container Lifecycle Hooks
  • Kubernetes provides two lifecycle hooks for containers: postStart and preStop;
  • postStart
    • Executed immediately after a container is created;
    • There is no guarantee that it will execute before the container's ENTRYPOINT;
    • If the handler fails, the container is killed and restarted according to restartPolicy;
  • preStop
    • Called immediately before a container is terminated;
    • It is blocking — the container is not killed until the hook completes (or the grace period expires);
    • Useful for graceful shutdown: draining connections, deregistering from service discovery, flushing logs;
  • Hook handlers can be: exec (run a command), httpGet (send an HTTP request);
  • Example 
    lifecycle:
  postStart:
    exec:
      command: ["/bin/sh", "-c", "echo started > /tmp/started"]
  preStop:
    httpGet:
      path: /shutdown
      port: 8080
9. volumeMounts
  • It specifies where to mount the specified volume inside the container;
  • It can be a single volume or a list of volumes;
  • name: Name of the volume to mount;
  • mountPath: Path inside the container to mount the volume;
  • readOnly: If true, the volume is mounted as read-only; Defaults to false;
  • subPath: If specified, only a sub-path of the volume is mounted; Defaults to empty;
  • subPathExpr: If specified, a sub-path expression of the volume is mounted; Defaults to empty;
  • Example 
    • volumeMounts:
                        - name: config
                          mountPath: /etc/config
  • Why volumeMounts is needed?
    • To use external storage systems;
    • To share data between containers in the same Pod;
  • Relationship with Pod volumes: Volumes are defined at the Pod level (spec.volumes), and then each container mounts the volumes it needs via volumeMounts; A volume must be declared in spec.volumes before it can be referenced in a container's volumeMounts;
Security Context (Container Level)
  • Defines privilege and access control settings for a container;
  • runAsUser: Specifies the UID to run the container process as;
  • runAsGroup: Specifies the GID to run the container process as;
  • privileged: If true, the container runs in privileged mode (access to all host devices); Defaults to false;
  • allowPrivilegeEscalation: Controls whether a process can gain more privileges than its parent; Defaults to true;
  • capabilities: Add or drop Linux capabilities (e.g., NET_ADMIN, SYS_TIME);
  • Example 
    securityContext:
  runAsUser: 1000
  runAsGroup: 3000
  privileged: false
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
    add:
      - NET_BIND_SERVICE
Image Pull Configuration
  • imagePullSecrets is defined at the Pod level but directly affects container image pulling;
  • It references Kubernetes Secrets of type docker-registry that contain credentials for private registries;
  • Example 
    # Create the secret
kubectl create secret docker-registry my-registry-cred \
  --docker-server=registry.example.com \
  --docker-username=user \
  --docker-password=pass

# Reference in Pod spec
spec:
  imagePullSecrets:
    - name: my-registry-cred
  containers:
    - name: app
      image: registry.example.com/my-app:v1
  • Without this, pulling from a private registry will result in ErrImagePull or ImagePullBackOff;
Container Termination Settings
  • terminationMessagePath: Path where the container writes its termination message; Defaults to /dev/termination-log; Kubernetes reads this file and surfaces it in the container's status;
  • terminationMessagePolicy: Can be File (default) or FallbackToLogsOnError (uses the last chunk of container log output if the termination message file is empty);
  • terminationGracePeriodSeconds: Defined at the Pod level; Time (in seconds) given to a container to shut down gracefully after receiving SIGTERM; Defaults to 30 seconds; After this period, the container receives SIGKILL;
Standard Streams
  • stdin: If true, allocates a stdin buffer for the container; Defaults to false;
  • stdinOnce: If true, stdin is closed after the first attach session; Defaults to false;
  • tty: If true, allocates a TTY (terminal) for the container; Requires stdin to be true; Useful for interactive containers;
  • These are primarily used for interactive/debugging scenarios, not typical production workloads;
Advanced Container Options
  • volumeDevices: Allows mapping raw block devices (instead of filesystems) into a container; Used with PersistentVolumeClaims that have volumeMode: Block;
  • resizePolicy: Controls how the container behaves when its resource requests/limits are changed in-place (without restarting); Part of the In-Place Pod Vertical Scaling feature;
  • restartPolicy interaction: The Pod-level restartPolicy (Always, OnFailure, Never) determines what happens when a container exits; Kubernetes restarts individual containers within a Pod, not the entire Pod;
  • Container restart behavior: When a container crashes, kubelet restarts it with exponential back-off delay (10s, 20s, 40s, ...) capped at 5 minutes;
Full Container YAML Example
  • Minimal container spec 
    containers:
  - name: app
    image: nginx:1.25
  • Production-level container spec 
    containers:
  - name: web
    image: myregistry.io/myapp:v2.1.0
    imagePullPolicy: Always
    ports:
      - containerPort: 8080
        name: http
        protocol: TCP
    env:
      - name: APP_ENV
        value: production
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-secret
            key: password
    resources:
      requests:
        cpu: 250m
        memory: 256Mi
      limits:
        cpu: "1"
        memory: 512Mi
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 15
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
    startupProbe:
      httpGet:
        path: /healthz
        port: 8080
      failureThreshold: 30
      periodSeconds: 10
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 5"]
    volumeMounts:
      - name: config-vol
        mountPath: /etc/config
        readOnly: true
    securityContext:
      runAsUser: 1000
      runAsGroup: 3000
      allowPrivilegeEscalation: false
      capabilities:
        drop:
          - ALL
