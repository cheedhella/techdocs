Cluster Upgrade Strategy

1. Version Skew Policy
  • Kubernetes supports upgrading one minor version at a time (e.g., 1.27 → 1.28, not 1.27 → 1.29);
  • Control plane must be upgraded before worker nodes;
  • kubelet can be up to 2 minor versions behind the API Server;
  • kubectl can be ±1 minor version from the API Server;
2. Upgrade Order
  1. Upgrade the control plane (API Server, Controller Manager, Scheduler);
  2. Upgrade etcd (if managed separately);
  3. Upgrade worker nodes (one at a time or in batches);
  4. Upgrade kubectl on admin machines;
3. Upgrading with kubeadm
# On control plane node:
# 1. Upgrade kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm=1.28.0-00

# 2. Plan the upgrade
sudo kubeadm upgrade plan

# 3. Apply the upgrade
sudo kubeadm upgrade apply v1.28.0

# 4. Upgrade kubelet and kubectl
sudo apt-get install -y kubelet=1.28.0-00 kubectl=1.28.0-00
sudo systemctl daemon-reload
sudo systemctl restart kubelet

# On each worker node:
# 1. Drain the node
kubectl drain worker-1 --ignore-daemonsets --delete-emptydir-data

# 2. Upgrade kubeadm, then kubelet
sudo apt-get install -y kubeadm=1.28.0-00
sudo kubeadm upgrade node
sudo apt-get install -y kubelet=1.28.0-00
sudo systemctl daemon-reload
sudo systemctl restart kubelet

# 3. Uncordon the node
kubectl uncordon worker-1
4. Managed Kubernetes Upgrades
  • EKS/AKS/GKE: Control plane upgrades are handled by the cloud provider;
  • Worker node upgrades are done by updating node groups/pools;
  • Always test upgrades in a staging environment first;
