Multi-Container Pods (Sidecar, Init, Ambassador, Adapter)

1. Why Multi-Container Pods?
  • Containers in a Pod share network and storage — they can work together as a cohesive unit;
  • The main application container is enhanced by helper containers;
  • Each container has a single responsibility;
2. Sidecar Pattern
  • A helper container that extends or enhances the main container;
  • Examples: log shipping (Fluentd sidecar), service mesh proxy (Envoy/Istio), file syncing;
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-example
spec:
  containers:
    - name: app
      image: myapp:v1
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
    - name: log-shipper
      image: fluentd:latest
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
  volumes:
    - name: logs
      emptyDir: {}
3. Ambassador Pattern
  • A proxy container that handles external communication on behalf of the main container;
  • Main container talks to localhost; the ambassador routes to the correct external service;
  • Example: A Redis ambassador that handles connection pooling and failover;
4. Adapter Pattern
  • A container that transforms output from the main container into a standardized format;
  • Example: Converting proprietary log format to a standard format for monitoring tools;
5. Key Points
  • All containers in a Pod start and stop together;
  • Containers share the same IP address — communicate via localhost;
  • Containers can share volumes for data exchange;
  • If the main container dies, the Pod is restarted (all containers);
