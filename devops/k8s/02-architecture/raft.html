Raft Consensus Algorithm

1. What is Raft Consensus Algorithm?
  • etcd uses Raft consensus algorithm for leader election, replication, fault tolerance and high availability;
  • No split-brain situation
    • Split-brain is a dangerous situation in distributed systems where 2 or more nodes think they are the leader at the same time;
    • By following Majority rule(A leader must have > 50% of votes), it ensures there is only leader at any given time;
  • Single source of truth(Strong consistency)
    • It ensure that there is only one leader at any given time, which takes care of making changes to state and replicating changes to followers;
    • Every write must be accepted by a majority (quorum), thus ensuring all nodes have same and correct data, even when a node is down; No stale reads!
  • Fault tolerance & High Availability
    • Fault Tolerance: If a leader crashes, new leader gets elected automatically;
    • High Availability: A cluster with 3 masters, can tolerate failure of 1 node; A cluster with 5 masters, can tolerate failure of 2 nodes;
2. How it works?
  • Role - Each node in the cluster acts as one of below 3 Roles:
    • Leader
      • Only one leader at a time;
      • API server writes always goes to the leader;
      • It handles all writes and replicates data to followers;
      • It keeps sending heartbeat to all followers; Heartbeat is a message sent by leader to say: "I’m still alive, stay followers, don’t start an election; Followers reset their election timer, when they receive it";
    • Follower
      • Receives data from leader, stores it locally(replicates) and sends ACK to leader; Leader waits for majority ACKs before committing; Without followers, no write can succeed;
      • Leader sends periodic heartbeats to all followers; Follower resets the election timer, thus preventing unnecessary election;
      • If follower doesn't receive the heartbeat, then it assumes the leader is dead, converts itself into candidate and starts election;
      • When a candidate asks for votes, Follower decides yes/no, based on: Log freshness and term number;
      • Followers may serve read-only queries(reduces load on leader); In strict consistency mode, reads still go via leader;
    • Candidate - Think of candidate as: “I think leader is gone, let me try”!
      • If follower doesn't receive the heartbeat, then it assumes the leader is dead, converts itself into candidate and starts election;
      • When a candidate asks for votes, Follower decides yes/no, based on: Log freshness and term number;
      • Wins majority → becomes Leader;
      • Loses → goes back to Follower
  • Leader election
    • Initially, all nodes are followers;
    • If no leader heartbeat is received → timeout triggers election;
    • A node becomes a candidate and requests votes;
    • Majority wins → becomes leader;
    • This ensures only one leader at a time;
  • How etcd uses Raft - when you ran any kubectl command:
    • API server receives request
    • Writes new desired state to etcd
    • etcd leader logs change
    • Followers replicate via Raft
    • Once committed → controllers act (create pods)
