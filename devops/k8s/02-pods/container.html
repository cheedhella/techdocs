Container

1. What is Container?
  • Container is instance of Image;
  • Containers are stateless, immutable and disposable/ephemeral;
    • Stateless: Container doesn't have any state of it's own; If you need a state, use volumes or databases;
    • Immutable: You can't make any changes to a running container; If you need a change, create new image and redeploy it;
    • Disposable/Ephemeral: Container is not meant to be long-lived; It is meant to be replaced with a new one if it fails or is replaced;
    • Why Stateless and Immutable? It allows k8s to:
      • Restart a container without losing any data;
      • Scale up/down as needed;
      • Replace a failed container with a new one;
      • Reschedule a container to a different node;
2. Container YAML Configuration
  • containers:

                  image: nginx:latest               # Name and tag of Docker Image.
                  imagePullPolicy: IfNotPresent        
                  command: ["echo"]                
                  args: ["Hello k8s"]              
                  workingDir: /app                  # Working directory for the container; Commands are executed from this directory; All relative paths are resolved relative to this directory; It overrides WORKDIR instruction in Dockerfile;
                  
                  ports:
                    - containerPort: 80             # Port on which the application in the container is listening; 
                      name: http                    # Optional name for the port; Used by other resources like Service, Ingress, etc;
                      protocol: TCP                 # Protocol for the port; Can be TCP, UDP or SCTP; Defaults to TCP;      
              
                  env:                              
                    - name: ENV
                      value: production
              
                  resources:
                    requests:
                      cpu: "100m"
                      memory: "128Mi"

                      cpu: "500m"

                  volumeMounts:
                    - name: config

                    httpGet:

3. imagePullPolicy
  • imagePullPolicy: It specifies the image pull policy for the container;
  • It can be Always, Never, IfNotPresent;
  • Defaults to Always if tag is :latest; Otherwise, IfNotPresent;
    • Always - It will not blindly download the image always; But, It always contacts registry for the digest and matches it with the local cache; It there is a mismatch, it downloads the image(only the layers that are not matching) from registry; It does this, even when the container is restarted;
    • IfNotPresent - It contacts registry only if that image is not present in local cache;
    • Never - It never pulls the image from docker registry;
4. command and args
  • command: It overrides the default startup command(ENTRYPOINT) defined in docker image; This is executed every time the container is started;
  • args: It overrides the default arguments(CMD) defined in docker image, which are passed to the command;
  • If you define args without a command, default command is used with new args;
  • If you define command without args, default args are used with new command;
  • If you define command and args, command is executed with new args;
  • By default, command is not executed within a shell; It is executed directly as a process by the container runtime; So, things like pipes(|), redirection(>), environment variables expansion($HOME), chaining(&&) will not work;
  • If you want to execute a command in a shell, do this: command: ["/bin/sh", "-c"] args: ["echo hello && sleep 10"]
5. ports
  • It can be a single port or a list of ports;
  • Each port can have a name, protocol and port number;
  • containerPort:
    • server.port=8080 in application.yml -> Actual port on which the application is listening;
    • It doesn't override the port on which the application is listening;
    • It is used to pass the port to the container runtime;
    • Why is this needed? Container can run absolutely fine without this; But, it is used by other resources like Service, Ingress, etc to route traffic to the container;
    • Can containers running in different pods(may be same or different nodes) use same port?
      • Yes, they can; But, they need to be in different pods; If they are in the same pod, they will conflict;
    • what is the purpose of supporting multiple ports in container spec?
      • Many modern apps expose a metrics port separate from the main API;
      • Eg: Prometheus 8080 for REST API and 9090 for metrics;
      • Application can support multiple protocols like HTTP(60), HTTPS(443), TCP(9090), gRPC(50051), etc;
  • name: Optional name for the port; Used by other resources like Service, Ingress, etc;
  • protocol: Protocol for the port; Can be TCP, UDP or SCTP; Defaults to TCP;
  • hostPort
    • It maps a port on the node (host machine) to a port inside the container;
    • It is optional and if not specified, a random port is assigned;
    • Only one Pod per node can use a given hostPort;
  • hostIP
    • If hostIP is not specified, container will listen on all node interfaces; Eg: node-ip1:8080, node-ip2:8080, localhost:8080
    • If hostIP is specified, container is accessible only on that IP address;
    • - containerPort: 80 hostPort: 8080 http://node-ip:8080 -> http://container-ip:80 kubectl port-forward pod/my-pod 8080:80
    : It specifies the IP address of the host; It is optional and if not specified, the container will be assigned an IP address from the node's IP address space;
  • hostPort
    • It is rarely used; Alternatively, use: ClusterIP, NodePort, LoadBalancer, Ingress;
    • When is it used?
      • Monitoring agents like Prometheus, Grafana, etc;
      • Log collectors
      • These often run as DaemonSets so each node has one Pod;
6. env
  • It defines environment variables that are avaialble inside the container; They are available to all processes in the container;
  • Instead of hardcoded values, k8s can pull these values from a ConfigMap or Secret or Pod metadata;
  • ConfigMap 
    • # ConfigMap 
                        apiVersion: v1
                        kind: ConfigMap
                        metadata:
                          name: app-config
                        data:
                          APP_MODE: production
                        
                        # Pod 
                        env:
                            - name: APP_MODE
                                valueFrom:
                                configMapKeyRef:
                                    name: app-config
                                    key: APP_MODE
  • Secret 
    • # Secret 
                        apiVersion: v1
                        kind: Secret
                        metadata:
                          name: app-secret
                        data:
                          DB_PASSWORD: cGFzc3dvcmQ=
                        
                        # Pod 
                        env:
                            - name: DB_PASSWORD
                                valueFrom:
                                secretKeyRef:
                                    name: app-secret
                                    key: DB_PASSWORD
  • Pod Metadata 
    • # Pod 
                        env:
                            - name: POD_NAME
                                valueFrom:
                                fieldRef:
                                    fieldPath: metadata.name
                        
                        # Inside the container 
                        POD_NAME=myapp-7d8c9f   # Useful for logging, tracing etc;
  • Resource Fields - Application can then read its CPU limit; 
    • # Pod 
                        env:
                            - name: CPU_LIMIT
                                valueFrom:
                                resourceFieldRef:
                                    containerName: app
                                    resource: limits.cpu
  • If the value changes in a ConfigMap or Secret, the container must be restarted to see the change;

8. resources
  • Example 
    • resources:
                        limits:
                          memory: "256Mi"
                          cpu: "500m"  # 500 millicores = 0.5 CPU
                          ephemeral-storage: "1Gi" 
                        requests:
                          memory: "128Mi"
                          cpu: "250m"
  • It defines the maximum amount of CPU and memory that a container is a allowed to use;
  • It ensure that a container doesn't effect other containers running on the same node;
  • CPU Limit
    • It defines the maximum CPU that a container is allowed to use;
    • It is specified in millicores; 1000 millicores = 1 CPU;
    • If a container exceeds its CPU limit, CPU throttling occurs;
  • Memory Limit
    • It defines the maximum memory that a container is allowed to use;
    • It is specified in bytes; Ki -> kibibytes; Mi -> mebibytes; Gi -> gibibytes;
    • If a container exceeds its memory limit, it is killed;
  • Ephemeral Storage Limit
    • It defines the maximum disk storage that a container is allowed to use; It is used for temporary storage; It is deleted when the container is deleted;
    • It includes /tmp, emptyDir volume etc;
    • If a container exceeds its ephemeral storage limit, it is killed;
  • Requests
    • It defines the minimum CPU and memory needed by the container;
    • When scheduling a Pod on a node, Kubernetes looks at requests, not limits; If the node doesn't have enough resources, scheduler will look for another node;
    • Limits are enforced after the container starts;
9. volumeMounts
  • It specifies where to mount the specified volume inside the container;
  • It can be a single volume or a list of volumes;
  • name: Name of the volume to mount;
  • mountPath: Path inside the container to mount the volume;
  • readOnly: If true, the volume is mounted as read-only; Defaults to false;
  • subPath: If specified, only a sub-path of the volume is mounted; Defaults to empty;
  • subPathExpr: If specified, a sub-path expression of the volume is mounted; Defaults to empty;
  • Example 
    • volumeMounts:
                        - name: config
                          mountPath: /etc/config
  • Why volumeMounts is needed?
    • To use external storage systems;
    • To share data between containers in the same Pod;
10. Probes
  • It is used to check the health of a container;
  • It can be a single probe or a list of probes;
  • Each probe can have a name and type;
  • There are 3 types of probes: Startup, Liveness, Readiness;
  • K8s uses probes to automatically restart the container if it is not healthy or ready to serve traffic;
  • Startup probe is executed only on startup, liveness and readiness probes are run periodically(as defined by periodSeconds) after startup probe succeeds;
  • Liveness probe 
    •                             - Liveness probe don't wait for the readiness probes to succeed; If you want to wait, use initialDelaySeconds;
- It is used check the health of a Pod - whether the Pod is up and running and responding(may be deadlocked and not responding);
- If the probe is successful, no action is taken and no logs are recorded;
- If a liveness probe fails failureThreshold number of times, kubelet will restart the application;

initialDelaySeconds -> how long to wait after the container starts and before sending the probe; Defaults to 0;
timeoutSeconds      -> how long to wait for the response, during probing; If the time is exceeded, probe is considered failed; Defaults to 1;
periodSeconds       -> It specifies the period/gap between each check; Defaults to 10;
successThreshold    -> Specifies the minimum consecutive successes for the probe to be considered successful after it has failed; Defaults to 1;
failureThreshold    -> Specifies the minimum consecutive failures for the probe to be considered failed after it has succeeded; Defaults to 3;

Type of probes 
- Command probe 
    -- It executes the specified command in the container and considers the container ready, if the command returns zero exit code;
- HTTP probe 
    -- It sends HTTP request to specified endpoint in the container and checks if it receives a successful response;
- TCP probe 
    -- It checks if a specific port is open and listening on the container;
  • Readiness probe
    • It indicates whether the container is ready to receive requests or not;
    • It is useful to perform time-consuming initial tasks, such as loading/warming caches etc;
    • If it fails, K8s will not send traffic to the container;
    • If a readiness probe fails failureThreshold number of times, kubelet will restart the application;
  • Startup probe
    • It is used to check if the container has started up;
    • If you specify a startup probe, k8s will not send any traffic to that pod, until that container's startup succeeds;
    • It is useful in some situations, where you have to deal with legacy applications that take lot of time to start up, thus avoiding them getting killed by kubelet, before they are up and running;
    • If you specify a startup probe, liveness and readiness probes will not run, until startup succeeds, making sure these probes don't interfere with the application startup;
    • If startup probe fails, kubelet logs an event, kills the container and follows the Pod's restartPolicy;
    • Make sure failureThreshold * periodSeconds is enough to cover the worst case startup time;
  • Example 
    • livenessProbe:
                        httpGet:
                        path: /healthz
                        port: 8080
  • Best Practices
    • Misconfigured probes can impact application performance, if they run too frequently;
    • If a container performs a simple operation and terminates quickly, it may not need health probe;
    • Set a realist wait time - if the readiness probe takes more than configured wait time, kubelet may assume the application is not responing and restart it, while it is still running;
    • Set a failure threshold for your liveness probes to avoid unnecessary restarts of your application;
    • Use the kubectl command-line tool to test your probes and make sure that they are correctly configured;

2. Container States
  • Waiting: Container is not yet running (pulling image, applying secrets, etc.);
  • Running: Container is executing;
  • Terminated: Container has finished execution (either successfully or with an error);
# Check container state
kubectl get pod my-pod -o jsonpath='{.status.containerStatuses[0].state}'
3. Pod Conditions
  • PodScheduled: Pod has been scheduled to a node;
  • Initialized: All init containers have completed;
  • ContainersReady: All containers in the Pod are ready;
  • Ready: Pod is ready to serve traffic (passes readiness probe);
