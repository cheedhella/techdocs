What is Service Account?
    - Whenever you interact with a k8s cluster using kubectl, you need to authenticate yourself with your user account; User accounts are meant to be used by humans;
    - But, if a process running in a pod needs to interact with API server, it needs to use service account; Service accounts are meant to be used by non-humans;
    - For eg, a CI/CD pipeline(a job that runs inside a pod) that deploys applications in k8s cluster uses service account to authenticate itself with API server;
    - In simple words, it authenticates and authroizes the application/service running in a Pod to interact with k8s API server;

    - Service Account is namespace aware resource;

    - A pod can have one and only one service account assigned to it;
      You can also assign service account to a deployment;
      Consider a deployment running multiple Pods that interact with the Kubernetes API;
      Instead of granting permissions to each Pod, you can create a service account with the necessary permissions and attach it to the Deployment;
      Then all the Pods under this Deployment will inherit this service account, effectively having the permissions to interact with the Kubernetes API;

Default Service Account 
    - K8s creates a service account in every namespace, called default service account;
    - Prior to k8s 1.24:
        - On every default service account creation, a secret with a token(with infinite validity) is created and attached to the service account;
        - That secret is mounted in every pod that is launched in that namespace; Mount path: /var/run/secrets/kubernetes.io/serviceaccount
        - It contains the credentials needed to authenticate with the k8s API server;
    - Post k8s 1.24:
        - It is discouraged to use secrets with infinite validity;
        - No secrets are created automatically;
        - Default service account doesn't have any roles OR special permissions attached to it, it is not much of a use until we bind it with a RBAC role;
        - What can your pod do with that default service account? Well, pretty much nothing.

Service Account Token 
    - k8s supports 2 types of tokens: Long-Lived Token, Time Bound Token;
        - Long-Lived Token
            -- This token has no expiry and it is discouraged to use it;
        - Time Bound Token
            -- It expires after the specified time;
    - Generally, it is not required to create a token manually;

    - Why aren’t Service Account Tokens Short-Lived by Default?
        -- The problem is that implementing short-lived tokens comes with some overhead;
        -- First, implementing short-lived tokens typically requires a more complex setup;
        -- You need an automated process to handle token renewal before it expires;
        -- This may involve additional scripts or Kubernetes operators that watch for token expiration and request new tokens as necessary;
        -- Tools like service mesh implementations (e.g., Istio), secret managers (e.g., CyberArk Conjur), or cloud provider services can manage the lifecycle of short-lived certificates and tokens, helping to reduce the overhead;
        -- Additionally, recent versions of Kubernetes offer features like the TokenRequest API, which can automatically rotate tokens and project them into the running pods;

Role and ClusterRole 
    Role
        - It defines a set of permissions (verbs like get, list, create, delete) on resources (like Pods, Services, ConfigMaps) within a specific namespace;
    ClusterRole 
        - It defines a set of permissions on non-namespaced resources(nodes, persistent volumes etc) and endpoints(like /healthz); It is cluster-wide resource;

RoleBindings and ClusterRoleBindings
    RoleBinding
        - It is used to assign a Role (or ClusterRole) to a user, group or service account; It is namespace specific;
    ClusterRoleBinding
        - It is used to assign a ClusterRole to user, group or service account; It is cluster-wide version of RoleBinding;

    If you need a ServiceAccount in namespace A to have access to some resource in same namespace: // Create a Role, RoleBinding, ServiceAccount in the same namespace;
        Create a Role with the needed permissions.
        Create a RoleBinding in namespace a.
        Point that RoleBinding to the ServiceAccount in namespace A.

    If you need a ServiceAccount in namespace A to have access to some resource in namespace B:
        Create a ClusterRole with the needed permissions.
        Create a RoleBinding in namespace B.
        Point that RoleBinding to the ServiceAccount in namespace A.

    - When a service account is created, it doesn’t have any permissions by default. 
    - You must explicitly bind the service account to a Role or ClusterRole using a RoleBinding or ClusterRoleBinding.
    - Role and RoleBindings are namespace aware; ClusterRole and ClusterRoleBindings not namespace specific, they are cluster wide objects;

Old Behavior (Pre-1.24):
    Kubernetes automatically created a secret (type: kubernetes.io/service-account-token) when a ServiceAccount was created.
    The token was stored as a Secret in the namespace and mounted into pods.

New Behavior (1.24+):
    Kubernetes now uses Bound ServiceAccount Tokens.
    Tokens are:
        Short-lived (default 1 hour)
        Not stored as Secrets
    Auto-mounted at /var/run/secrets/kubernetes.io/serviceaccount/token in pods
    More secure and rotated automatically

Request a ServiceAccount Token Manually
    kubectl create token <serviceaccount-name> --duration=1h -n <namespace>

List token
    kubectl exec -it <pod> -- cat /var/run/secrets/kubernetes.io/serviceaccount/token

Token Expiration and Rotation
    You can configure the expiration time when creating tokens manually.
    Bound tokens expire automatically and are rotated by the kubelet.
    Tokens are tied to the audience (e.g., API server).

What RBAC?
    - Role Based Access Control;
    - It controls who(users or service accounts) can perform what actions(get, list, create, update, delete etc), on which resources(pods, services, nodes etc);
    - RBAC uses the rbac.authorization.k8s.io API group to drive authorization decisions;
    - By using RBAC with service accounts, you can limit the potential damage done, if a service account’s credentials are ever exposed;
