Job

1. What is a Job?
  • It creates one or more Pods, that run a specific task, until specified number of Pods succeed;
  • If specified number of Pods are completed successfully, then the job is marked complete;
  • If a Pod fails, then the Job creates a new Pod(based on restart policy);
  • Job is marked as Failed, after either specified number of retrials OR specified timeout;
2. Purpose of a Job?
  • It is useful for one time tasks, such as:
    • Database migration - schema upgrade or data migration;
    • Database backup;
    • Delete logs older than certain number of days;
    • Run set of automated tests;
    • Batch Processing - Job could creat a set of pods, that divide the task into smaller chunks and process them in parallel;
3. What causes a Job to run infinitely forever?
  • If no timeout is configured and application never exits(keeps failing internally or ran into a infinite loop), k8s thinks job is still running and it never finishes;
  • If no timeout is configured and with restartPolicy: OnFailure, if the container keeps failing, container may restart endlessly inside the same Pod;
  • A job stops only when: successful completions reached OR backoffLimit exceeded OR activeDeadlineSeconds exceeded;
2. Job YAML
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 4
  activeDeadlineSeconds: 300
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myapp:migrate
          command: ["python", "migrate.py"]
3. Key Fields
  • restartPolicy: Never | OnFailure;
    • For jobs, you need to explicitly set restartPolicy in pod template;
    • OnFailure: If container fails, k8s restarts the container, inside the same pod;
    • Never: If container fails, pod is considered failed and k8s keeps retrying by creating a new Pod, until pod is successful or backoffLimit is reached;
    • Always: Not allowed for jobs;
  • backoffLimit - Defaults to 6;
    • It specifies how many times k8s create a new pod to retry a failed job;
    • When task/container fails(If it is java application, JVM returns exit code 1), Pod is marked as Failed;
    • K8s creates another retry Pod, until backoffLimit is reached;
  • parallelism - Defaults to 1;
    • It specifies number of pods that can run simultaneously;
  • completions - Defaults to parallelism;
    • It specifies how many successful pod executions are needed, to consider the job successful;
    • What happens if parallelism is set but completions is NOT set? It defaults to parallelism;
    • What happens when both parallelism and completions are NOT set? Both defaults to 1;
  • activeDeadlineSeconds - Defaults to infinite;
    • It specifies the maximum time(like ttl) a job is allowed to run;
    • If a Job runs longer than this, k8s terminates all the pods and marks the job as failed;
    • If this is not specified, job has no time limit and it runs until:
      • Job is completed succesfully;
      • Job fails after backoffLimit retries;
      • User manully deletes the job;
  • ttlSecondsAfterFinished
    • Job object along with it's pods are deleted, ttlSecondsAfterFinished seconds after job is completed(succeeded/failed);
    • If not set, created Job and its Pods remain in the cluster forever unless you delete them manually;
  • completionMode - Indexed | NonIndexed; Defaults to NonIndexed;
    • Indexed job gives each pod a different index(0..N); It is useful to split the work b/w Pods;
    • NonIndexed job is useful when tasks are stateless and all pods does same thing;
  • suspend - Defaults to false;
  • It is used pause/resume a job;
  • It is useful if your cluster is under going maintanance OR experiencing resource shortages etc;
  • Pause: kubectl patch job <job-name> -p '{"spec":{"suspend":true}}'
  • Resume: kubectl patch job <job-name> -p '{"spec":{"suspend":false}}'
  • What happens if job is running and if you restart node? Job controller detects the failed or missing pod and creates a new pod on another node; So, application code needs to idempotent OR maintain checkpoints;
