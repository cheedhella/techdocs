What is CronJob?
CronJobs run Jobs on a scheduled basis.
Manages the creation of Jobs on a scheduled basis.
Uses cron syntax to define the schedule.
CronJobs are perfect for scheduling these tasks to run on a recurring basi
CronJobs are useful for tasks that need to be performed periodically, such as backups, report generation, or system maintenance.
The CronJob controller, which is part of the kube-controller-manager, implements the primary logic. By default, it checks every 10 seconds to see if a CronJob should be run
When the controller identifies a CronJob that needs to be executed (i.e., the current time matches the time specified in cron syntax), it creates a new object called a Job. Each Job tracks a specific invocation and contains information inherited from the CronJob about what to do
Once Kubernetes detects a new Job object, it immediately attempts to execute it. It schedules the creation of a new Pod based on the configuration passed down from the CronJob via the Job in jobTemplate. When the Pod is running, it performs the cron task



Scheduled Execution: CronJobs run at specified times, defined using Cron syntax.
Time-based Triggers: You can schedule tasks to run daily, weekly, monthly, etc.

The schedule field uses the standard cron format: * * * * *
  minute (0 - 59), hour (0 - 23), day of the month (1 - 31), month (1 - 12), day of the week (0 - 6) (Sunday to Saturday)

schedule: "* * * * *"                   # Every minute
schedule: "*/15 * * * *"                # Every 15 minutes
schedule: "0 * * * *"                   # Every hour at minute 0
schedule: "30 2 * * *"                  # Daily at 2:30 AM
schedule: "0 9 * * 1"                   # Every Monday at 9:00 AM

# Shorthand expressions
schedule: "@hourly"    # Every hour
schedule: "@daily"     # Every day at midnight
schedule: "@weekly"    # Every Sunday at midnight
schedule: "@monthly"   # First day of each month at midnight
schedule: "@yearly"    # January 1st at midnight

Running a CronJob to Back Up a Database
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup-cronjob
spec:
  schedule: "0 0 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: db-backup
            image: busybox
            command: ["sh", "-c", "echo Backing up database...; sleep 10; echo Database backed up!"]
          restartPolicy: OnFailure
  backoffLimit: 3

    It is used to create one or more instances of a Pod, each Pod contains one or more containers, each container performs a specific task and then terminate; // one-time tasks 
    If parallelism is 2 and completions is 5, then the job runs 2 pods concurrently, until 5 pods are completed successfully, subjecting to backoffLimit;
    Pod is considered failed, if any of it's containers fail(exits with non-zero return code); Pod failures accumulates toward the backoff limit;

CronJob Configuration
    1. successfulJobsHistoryLimit: <n>                   # You can specify successfulJobsHistoryLimit and failedJobsHistoryLimit to retain a certain number of successful and failed Job histories.


parallelism: <n>                             # Number of pods that can run parallely; Defaults to 1;
    2. completions: <n>                             # Number of successful pods needed to mark the Job as completed; Defaults to 1;
    3. backoffLimit: <n>                            # If a Pod fails, it is retried; After backoffLimit retries, Job is marked as failed; Defaults to 6;
    4. restartPolicy: Never | OnFailure;            # Job doesn't have any default; It must be set to Never or OnFailure;
                                                    # Never - when a container fails, Pod is marked failed and spwans a new Pod, subjecting to backoffLimit;
                                                    # OnFailure - when a container fails, kubelet retries it endlessly in the same pod, until the job controller intervenes;
    5. activeDeadlineSeconds: 300                   # If a job runs longer than this duration, it is terminated and marked as failed; By default, no deadline, job runs indenfinitely until is completed(successful or failed);
    6. ttlSecondsAfterFinished: 60                  # It specifies how long to retain the job object, after it is completed(successful or failed); By default, no ttl, Jobs stay forever unless manually deleted; Set it to 0, to delete it immediately;
