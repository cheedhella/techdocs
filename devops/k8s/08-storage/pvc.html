Persistent Volume Claim

1. What is a Persistent Volume Claim?
  • It is a request for storage by an application — like a Pod requesting CPU/memory;
  • K8s finds or creates a PV that matches the PVC's requirements (size, access mode, StorageClass) and binds it to PVC;
  • Pod referencing PVC uses it;
2. PVC Lifecycle
  • Pending: PVC is created, but no PV is bound to it;
  • Bound: PVC is bound to a PV;
  • Lost: PV is lost, but PVC is still bound to it;
3. PVC YAML Configuration
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
  namespace: production
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard

  • Access Modes
    • It specifies how the volume can be used by the Pods;
    • ReadWriteOnce: The volume can be mounted as read-write by a single node;
    • ReadOnlyMany: The volume can be mounted as read-only by many nodes;
    • ReadWriteMany: The volume can be mounted as read-write by many nodes;

      Why Pods needs specify this informaton?
      • Different storage systems support different capabilities;
      • So, K8s uses this information to match the PVC with the appropriate PV;
  • resources.requests.storage - It specifies the size of the volume needed by the application;
  • volumeMode - Filesystem or Block;
    • Filesystem - Volume is formatted with a file system and can be mounted in specified directory inside the container; 
                        # Pod YAML
                  spec:
                    containers:
                      - name: my-container
                        volumeMounts:
                          - name: my-volume
                            mountPath: /data
                  volumes:
                    - name: my-volume
                      persistentVolumeClaim:
                        claimName: my-pvc
    • It is the default mode; It is used for: webapps, logs, databases etc;
    • Block - Volume doesn't have any filesystem, storage is given as raw disk to the container; Application itself decides how to use it;
    • So, instead of /data/file1, /data/file2, container sees something like /dev/xvdb, /dev/xvdc etc;
    • Application can format the block device with custom file system and mount it as a directory; Eg: mkfs.ext4 /dev/xvda and mount /dev/xvda /data 
      # Block PVC 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: block-storage
spec:
  accessModes:
  - ReadWriteOnce
  volumeMode: Block
  resources:
    requests:
      storage: 20Gi

# Block Pod YAML
apiVersion: v1
kind: Pod
metadata:
  name: block-app
spec:
  containers:
  - name: app
    image: busybox
    command: ["sleep", "3600"]
    volumeDevices:
    - name: data
      devicePath: /dev/xvda
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: block-storage

Inside the container, you will see: /dev/xvda;
    • When using block volumes, containers must use volumeDevices instead of volumeMounts;
  • storageClassName - It specifies the name of the StorageClass to use;
