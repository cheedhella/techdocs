How it works?
    A Service selects Pods using labels;
    Traffic sent to the Service is automatically routed to one of the matching Pods
    kube-proxy (or similar) handles routing;

    Client calls: my-service.default.svc.cluster.local
    DNS resolves to Service IP
    Service routes request to one of the Pods
    Pod processes the request

    Provided by CNI plugins
        Networking is implemented by plugins like:
            Calico
            Flannel
            Cilium

        These ensure:
            IP allocation
            Routing between nodes
        
        It acts as a load balancer
        how kube-proxy actually routes traffic (iptables/IPVS)
        or how headless services expose Pod IPs directly
Services provide:
    Stable IP + DNS
    Load balancing
    Service discovery - when a pod wants to talk to another servcie, it can use service name(which gets resolved to IP address by DNS);

    Each Pod in the K8s Cluster has a unique IP address; 
    
    For external access, Ingress often comes into play.


    

    Service exposes an always available URL(called cluster IP) to applications running in one or more pods, even when one of the pod is down OR it is being upgraded;
    It load balances the requests among all running pods;

    The set of Pods that Service is proxying are determined by the label selectors defined in the Service definition;

Service provides access to the Pods from inside the cluster(through kube proxy) and from outside the cluster(through kube dns);

how this is implemented internally (kube-proxy, iptables, IPVS)
👉 or how this differs from Ingress / Gateway (very important in interviews)


If you recreate the service, service IP can change; but, DNS remains the same;

K8s supports 4 type of Services: ClusterIP, NodePort, LoadBalancer, External IP;

ClusterIP
    - You could have multiple front-end pods, multiple backend pods and multiple redis pods;
    - ClusterIP allows one pod type to communicate to another Pod type, within the cluster; // inter-pod communication

apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP

NodePort
    - It exposes the applications running in a Pod to the external world;
    - It internally creates a ClusterIP service; It routes all it's requests to that ClusterIP Service;
    - Cons
      -- You could expose only one service per port; You could use only ports from 30000 to 32767;
      -- If your node IP address changes, you need to deal with that;
         So, this is not a recommended approach to expose a service to external world;
         This is useful in cases when your service need not to be always available, or you are very cost sensitive;

LoadBalancer
    - It is a standard way of exposing the applications running in a Pod to the external world;
    - It internally uses a cloud provider's load balancer; // If you use AWS, it internally creates AWS ELB (Elastic LoadBalancer);
    - Load Balancer will be assigned an external IP address; You will be charged for this;
    - All traffic(HTTP, TCP, UDP, Websockets etc) on any port that you specify will be forwarded to the service;

External IP
    - You can use External IP, if you want to get the full control of IP that you use;
      You can use IP that belongs to your ASN instead of a cloud provider’s ASN;

There are four types of services that Kubernetes supports: ClusterIP, NodePort, LoadBalancer, and Ingress

How Service works?
A user sends a request to one of the nodes of the cluster. That request is received by a Service and load balanced to one of the associated Pods. 
It’s a bit more complicated than that, with iptables, kube DNS, kube proxy, and a few other things involved in the process.

What is Headless Service?
A headless service is a Kubernetes service that doesn't assign a cluster IP. Instead, it provides a stable DNS entry for each pod in the StatefulSet. This allows direct access to individual pods, crucial for applications requiring specific pod-to-pod communication, such as distributed databases or peer-to-peer networks. For example, in a Cassandra cluster deployed as a StatefulSet, each Cassandra node needs a unique identity and the ability to communicate directly with other nodes. A headless service provides this by creating DNS records for each pod.
