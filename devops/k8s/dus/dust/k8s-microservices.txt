K8s and Microservices
	- 


Microservice vs monolitic application
	- In case of monolitic application, entire system is deployed as a single unit or single war file;
	  If this is a shopping site, you will find code for shopping cart mgmt, catalog mgmt, sales, inventory mgmt, authentication etc;
	- Usually, of course there will be a global database backing this application;
	  All of these business areas would typically be able to read and write to that database schema;
	  That's not always the case;
	  A schema could be broken up into separate schemas, but it is common to have one of these global databases;
	  Often, this database might even be shared with other monolith applications;
	- What's the problem here?
	  It gets harder and harder to make changes to one business area, without you accidentally breaking another business area;

	You can really think of microservices as just being an extreme form of modularity, of building the system as a set of self-contained components;

	The key thing is that these microservices can function on their own.
	They can be deployed on their own.
	They can be developed on their own.
	But these microservices can of course communicate with each other, through well-defined interfaces.
so in practise, the microservices would often be deployed to their own containers.

	The code in one microservice is going to have no direct visibility of code in another one.
	Now of course, there's got to be communication between them,
		Traditionally REST calls are used,
		but you could also have messages passing between them.

	and to have a microservice only dealing with one single requirement is something of an ideal.

	Two-pizza rule
		- many companies are adopting two-pizza rule;
		- can we feed the entire development team for this microservice using just two pizzas?
		- The microservices are going to be very constrained in their size;
		- If you start finding that you have four, five, six developers who need to work on a microservice, then it's definitely too big;
		- I'm going to keep saying my rule of thumb is that a microservice should be dealing with only one specific area of business functionality.
		- what point do we break a microservice down into multiple microservices? single responsibility principle;
		- it really is possible to have a microservice that is just a few lines of code.

		- Each microservice should be highly cohesive and loosely coupled; what does this mean?
		- highly cohesive ->  each microservice should be handling one business requirement.
			Cohesive means that a microservice should have a single set of responsibilities.
		- loosely coupled -> 
			wherever possible, we need to minimise the interfaces between our microservices.
			It would be no good if the dependencies between the microservices looks something like this. Now maintaining loose coupling is hard, I don't deny that.
		- We have to be very careful in designing the interfaces, and not letting them get out of control.
		  And that's typically the job of a system architect,
		- We're also going to see on this course that we can use messaging.
		  That can help us to loosen the coupling in the system;


Let's talk about databases in microservices;
	- For microservice architectures, integration databases are a definite NO. So, why is that the case?
	  Because they immediately violate the two principles that we've discussed;
	  They are, by design, not cohesive because they contain many different business areas;
	  They're certainly not loosely coupled because any part of the system can read or write to this database;

	- The key thing is that each microservice will maintain its own data store.
	  That microservice will be really the only part of the system that can read or write that data.



It's worth mentioning then that when building a microservice architecture, I don't believe you can possibly do a big design upfronts;
Microservice architectures are very, as we say, emergence.
They tend to develop over time as your understanding of the system improves.
So you will find yourself designing, building, and deploying a microservice;

But it's only a few weeks later or whatever down the line that you, you have a eureka moment, and you realise that no that's too big, it's doing too much, it should be broken down. And that's fine, that's good. You refactor later.
So agility is really important in microservices because it is impossible for any human being to get the right answer in advance of building the system.

	Why networking is needed?
		Imagine you have 2 containers running: one runs mysql db, another runs your application;

Kubernetes Concepts
To help you get started with Minikube, it helps to understand some basic k8s concepts. Below are the most basic aspects you should know:

Deployment—configured and operational resources. Deployments are the overall processes that enable you to orchestrate your resources.
ReplicaSet—sets of pods that provide the resources for your services.
Pod—a unit that contains one or more containers along with attached storage resources, and configuration definitions. Pods are grouped together in ReplicaSets and all pods in a set run the same container images.
Node cluster—control plane and worker nodes that each contain one or more pods. The workers run your workloads and the control plane orchestrates the workers together. This is what is created by Minikube.
Node processes—the various components that you use to connect and manage Kubernetes. Control plane processes include API servers, ectd, Scheduler, kube-controller-manager, and cloud-controller-manager. Worker processes include kubelet, kube-proxy, and your container runtime.
Container—the image you create to hold your applications.


Basic concepts: Pods, Replicasets, deployments, services;


In an orchestration system, we'll be defining a series of fairly simple text files called manifests.
Now these manifests are going to allow us to capture our system's entire architecture.
It'll allow us to describe what containers we want to be running.
It will allow us to describe what infrastructure we want to be running, so just hard discs or nodes.
And really importantly, it will allow us to make the system robust.


We're going to be able to ensure that, for example, there is always one or more instances of a particular container running at any one time.

And even if there's some kind of catastrophe, which means containers have crashed, then the orchestration system will be responsible for restoring the system back to it's healthy state with no intervention required from an administrator.

Now if you're on this course, you're probably going to be working in the cloud.
And the cloud, of course, brings lots of complications of it's own.
We're going to need things like load balances, external hard drives, security configurations and so on.
And again, this is something that can be handled by our orchestration system.

Towards the end of this course, you'll be taking these manifest files that you've developed locally and you'll transfer them to the cloud.

and you can deploy them to different cloud platforms, Amazon, Azure, Google, and so on.
And without changing those manifests, Kubernetes is capable configuring the infrastructure in your environment.
So Kubernetes is almost the way of abstracting away the low level details of your underlying cloud platform.

And if that doesn't make any sense yet, don't worry, when we get to the chapter
when we move to AWS, you'll see that we hardly do anything with AWS.
We don't even need to start up any images.
We just run our scripts and all the load balances, the hard discs, and the instances are all automatically created.
