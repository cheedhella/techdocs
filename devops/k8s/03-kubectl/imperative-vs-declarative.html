Imperative vs Declarative Approach

1. Imperative Commands
  • Tell Kubernetes what to do step by step;
  • Quick for ad-hoc tasks and experimentation;
  • Not reproducible — no record of what was done;
# Create resources directly
kubectl run nginx --image=nginx
kubectl create deployment myapp --image=myapp:v1
kubectl expose deployment myapp --port=80 --type=NodePort
kubectl scale deployment myapp --replicas=3
kubectl set image deployment/myapp myapp=myapp:v2
2. Imperative Object Configuration
  • Use YAML files but with imperative commands (create, replace, delete);
kubectl create -f deployment.yaml
kubectl replace -f deployment.yaml
kubectl delete -f deployment.yaml
3. Declarative Configuration (Recommended)
  • Tell Kubernetes the desired state and let it figure out how to get there;
  • Uses kubectl apply — creates if not exists, updates if it does;
  • Idempotent: Running it multiple times produces the same result;
  • GitOps-friendly: Store manifests in Git, apply them in CI/CD;
# Apply a single file
kubectl apply -f deployment.yaml

# Apply all files in a directory
kubectl apply -f ./manifests/

# Apply recursively
kubectl apply -R -f ./manifests/
4. When to Use Which?
ApproachUse Case
Imperative commandsQuick experiments, CKA exam, one-off tasks
Imperative configSimple workflows, learning
Declarative (apply)Production, CI/CD, GitOps — always prefer this
