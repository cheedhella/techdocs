Docker — Architecture

1. Overview
  • Docker uses a client-server architecture;
  • The Docker Client issues commands; the Docker Daemon (server) does the heavy lifting;
  • Client and daemon can run on the same machine, or the client can connect to a remote daemon over a network;
  • Communication between the client and daemon happens via a REST API over a Unix socket or TCP;

2. Docker Client
  • The Docker Client (docker CLI) is the primary way users interact with Docker;
  • When you run a command like docker run or docker build, the client translates it into a REST API call and sends it to the Docker Daemon;
  • A single Docker CLI can communicate with multiple Docker Daemons — local or remote — using Docker Contexts;
docker context ls                                          # list all configured daemons
docker context use my-remote-server                        # switch to a remote daemon
docker context create remote --docker host=ssh://user@host # create a new SSH context
3. Docker Daemon (dockerd)
  • The Docker Daemon (dockerd) is a long-running background process on the Docker Host;
  • It listens for API requests from the client and manages all Docker objects: images, containers, networks, and volumes;
  • It delegates low-level container execution to containerd;
  • Responsibilities include:
    • Building images from Dockerfiles;
    • Pulling images from and pushing images to a registry;
    • Creating, starting, stopping, and removing containers;
    • Managing networks and volumes;
docker version   # verify both client and daemon are running and their versions
docker info      # detailed daemon configuration: storage driver, runtime, registry, etc.
4. containerd & runc
  • containerd is an industry-standard container runtime that dockerd delegates to for managing the container lifecycle (create, start, stop, delete);
  • It is a CNCF project and is also used directly by Kubernetes (via CRI);
  • runc is the low-level OCI-compliant runtime that containerd uses to actually spawn container processes on the host OS;
  • Every running container has its own runc instance managing it;
  • This layered design means Docker can be replaced at any layer — e.g., Kubernetes can use containerd directly without dockerd;

5. Docker Registry
  • A Docker Registry is a centralized store for Docker images — similar to Maven Central for Java JARs;
  • Docker Hub (docker.io) is the default public registry, hosting millions of official and community images;
  • Organizations can run private registries (e.g. Harbor, AWS ECR, GCR, Azure ACR) to store proprietary images securely;
  • docker pull downloads an image from a registry to the local image cache;
  • docker push uploads a locally built image to a registry;
docker pull nginx:latest                              # pull from Docker Hub (default)
docker pull myregistry.local:5000/myapp:1.0           # pull from a private registry
docker login myregistry.local:5000                    # authenticate to a private registry
docker push myuser/myapp:v1.0                         # push image to Docker Hub
6. Linux Namespaces — How Isolation Works
  • When Docker creates a container, it sets up a set of Linux namespaces to isolate it from the host and other containers;
NamespaceWhat it Isolates
PIDProcess IDs — container processes cannot see host or other container processes
NETNetwork interfaces, IP addresses, routing tables — each container gets its own network stack
MNTFilesystem mount points — container has its own root filesystem
IPCInter-process communication — shared memory and semaphores are isolated
UTSHostname and domain name — each container can have a unique hostname
USERUser and group IDs — a root user inside a container need not be root on the host
7. cgroups — How Resource Limits Work
  • Control Groups (cgroups) is a Linux kernel feature that limits, accounts for, and isolates resource usage of process groups;
  • Docker uses cgroups to enforce per-container resource constraints;

8. Image Layers & Copy-on-Write
  • Docker images are composed of read-only layers stacked on top of each other;
  • Each RUN, COPY, or ADD instruction in a Dockerfile creates a new layer;
  • Layers are identified by a SHA256 digest and are shared across images — stored only once on disk;
  • When a container starts, Docker adds a thin read-write layer on top (the container layer). All changes (new files, modifications, deletions) go into this layer;
  • This is the Copy-on-Write (CoW) strategy — a file from a lower read-only layer is only copied up to the writable layer when it is modified;
  • When the container is removed, its writable layer is discarded — use volumes to persist data;
