Docker — Introduction

1. What is Docker?
  • Docker is an open-source platform that enables developers to automate the building, shipping, and running of applications inside lightweight, portable containers;
  • It packages an application together with all its dependencies — runtime, libraries, environment variables, and config — into a single unit called an image;
  • That image can be run as a container on any machine that has Docker installed, regardless of the underlying OS or environment;
  • The full Docker ecosystem consists of: Docker Engine (Client + Daemon), Docker Images, Docker Hub (registry), and Docker Compose;
2. Why Docker? — The Problem it Solves

The era of physical servers:

  • In the early days, only one application could be deployed per physical server;
  • Operations teams had to guess resource requirements, often resulting in either under-powered or over-powered (5–10% utilization) servers — wasting capital;

Virtual Machines — better, but not perfect:

  • VMware introduced VMs, allowing multiple applications on a single server via a hypervisor;
  • However, each VM requires its own full Guest OS — consuming CPU, RAM, storage, licenses, and maintenance overhead;

Containers — the modern solution:

  • Containers share the host OS kernel — no Guest OS per application;
  • All containers on a host share the same Docker Engine, freeing up CPU, RAM, and storage;
  • Result: lower infrastructure cost, faster startup, and simpler maintenance;

3. Key Concepts
  • Image: A read-only, layered package containing the application and all its dependencies. Built from a Dockerfile. Can be stored in and pulled from a registry;
  • Container: A running instance of an image. Isolated from other containers and the host via Linux namespaces and cgroups. You can run many containers from the same image;
  • Dockerfile: A plain-text script of instructions (FROM, RUN, COPY, CMD, etc.) used to build an image;
  • Registry: A centralized repository for storing and sharing images. Docker Hub is the default public registry; private registries are also supported;
  • Docker Engine: The core runtime — composed of the Docker Client (CLI) and the Docker Daemon (dockerd);
  • Namespace: A Linux kernel feature that provides process isolation — each container gets its own PID, network, IPC, mount, UTS, and user namespaces;
  • cgroups (Control Groups): A Linux kernel feature used to limit and account for resource usage (CPU, memory, disk I/O, network bandwidth) per container;
  • Layer: Images are built in layers. Each RUN, COPY, or ADD instruction adds a new layer. Layers are cached and shared across images, saving disk space and speeding up builds;
4. Docker Image in Detail
  • An image is a read-only template containing the app, its runtime, libraries, env vars, and config;
  • Images are identified by a tag (e.g. nginx:1.25) and an immutable digest (SHA256 hash of its content);
  • Tags are mutable — the same tag can be reassigned to a newer image. Digests are immutable — use them for reproducible deployments;
  • Dangling image: An untagged image (shows as <none>:<none>) created when a newer build overwrites an existing tag. They waste disk space and can be removed with docker image prune;
  • Unused image: An image that has a tag but has never been used to create a container;
  • Image layers are stored only once on disk even if referenced by multiple images — this is the copy-on-write (CoW) model;

Image identifier format:

<registry>/<namespace>/<repository>:<tag>

# Examples:
docker.io/library/nginx:latest          # Official Docker Hub image
docker.io/myuser/myapp:v1.0            # User image on Docker Hub
myregistry.local:5000/team/myapp:1.2   # Private registry image

6. Common Use Cases
  • Microservices: Package each service independently, deploy and scale them separately;
  • CI/CD pipelines: Build, test, and deploy in consistent, reproducible environments — no more "works on my machine";
  • Local development: Spin up databases, message brokers, or third-party services locally without installing them natively;
  • Cloud-native applications: Containers are the unit of deployment on Kubernetes and all major cloud platforms (AWS ECS/EKS, GKE, AKS);
  • Environment consistency: Dev, staging, and production all run the exact same image — eliminating environment drift;
