OCI Registry

1. What is OCI Registry?
  • OCI Registry is nothing but a container registry(HTTP server like Docker Hub, GitHub Container Registry etc) which is capable of storing and distributing OCI artifacts over OCI protocol in a secured way;
  • OCI support was introduced as experimental in Helm 3.0 and became stable/GA in Helm 3.8+; It is enabled by default in Helm 3.8+;
  • OCI URL examples:
    • oci://registry.example.com/myorg/mychart
    • oci://registry.example.com/myorg/mychart:1.0.0
    • oci://registry.example.com/myorg/mychart@sha256:xxxxx
    • oci://registry.example.com/myorg/mychart:1.0.0@sha256:xxxxx
    • oci://registry.example.com/myorg/mychart:1.0.0@sha256:xxxxx
2. Why Use a Helm Registry?
  • Version control for deployments
    • You can version control your charts using tags and digests;
    • You can rollback to a specific version if needed;
    • You can track changes to the chart;
    • You can see who made the changes;
    • You can see when the changes were made;
  • Share charts across teams
  • Private secure distribution
  • CI/CD integration

4. What is OCI Artifact?
  • For helm OCI chart, it is stored as:
    • Config object (Helm metadata)
    • One layer (the .tgz chart)
    • Manifest tying them together
    • Registry does not “know” it’s Helm. It just sees OCI artifact with Helm media types;
5. Non-OCI Artifact vs OCI Artifact
  • Non-OCI Artifact:
    • Store the file somewhere and refer it by it's name; Eg: https://charts.bitnami.com/bitnami/nginx-15.2.3.tgz
    • System cares about the file name, version, location; It doesn't care about the content of the file, whether it is changed or not, whether it is deduplicated or not;
  • OCI Artifact:
    • Filename is irrelevant; Digest is the unique identifier of the content;
    • You can store the file in a registry and refer it by it's digest; Eg: oci://registry.example.com/myorg/mychart@sha256:xxxxx
    • If the content is changed, the digest will change; It is impossible to change the content of the file, without changing the digest;
5. What is OCI Protocol?
  • It is a set of standards defined by the Open Container Initiative (OCI) for creating, storing(push) and distributing(pull) artifacts;
  • Helm leverages this protocol to store charts as OCI artifacts;
  • Communication is done over HTTP(S), and artifacts are layered tarballs, just like Docker images;
  • OCI registries provide authentication, access control, caching, and content-addressable storage;
6. How does OCI Protocol work?
  • When you push an artifact:
    • Registry ping
      • Client checks if the registry is reachable; GET https://registry.example.com/v2/, if it responds with 200 OK, then the registry is reachable;
    • Authentication
      • If it requires authentication, login to the registry using the following command:
      • GitHub container registry:echo "$GITHUB_TOKEN" | helm registry login ghcr.io -u $GITHUB_USER --password-stdin
      • Docker Hub: docker login -u $DOCKER_USER -p $DOCKER_PASSWORD
      • JFrog Artifactory: helm registry login $REGISTRY_URL -u $USERNAME -p $PASSWORD

      • Client requests a token from the registry; POST https://registry.example.com/v2/token, if it responds with 200 OK, then the client is authenticated and retries the request with the token in the Authorization header;
    • Repository check
      • Client checks if the repository exists; GET https://registry.example.com/v2/myorg/mychart, if it responds with 200 OK, then the repository exists;
    • Check if the blob already exists(Deduplication)
      • Client checks if the blob exists; HEAD https://registry.example.com/v2/myorg/mychart/blobs/sha256:xxxx, if it responds with 200 OK, then the blob exists;
      • If 2 artifacts share the same blob, then the blob is stored only once and the same blob is used by both artifacts;
    • Upload the blob
      • Client calls: POST https://registry.example.com/v2/myorg/mychart/blob/uploads/ and registry returns an upload URL;
      • Client uploads the blob to the registry; PUT https://registry.example.com/v2/myorg/mychart/blobs/uploads/?digest=sha256:abc123
      • Registry verifies if digest matches content and stores blob in content-addressable storage;
    • Upload the config
      • OCI artifacts have a small config JSON: For container image → image config, For Helm chart → Helm metadata;
      • Config is uploaded same way as blobs;
      • Client uploads the config to the registry; PUT https://registry.example.com/v2/myorg/mychart/config.json, if it responds with 200 OK, then the config is uploaded;
    • Upload the manifest
      • Manifest is a JSON file that links the everything(config and blobs) together;
      • Example: 
         {
                                    "schemaVersion": 2,
                                    "config": {
                                      "digest": "sha256:config123"
                                    },
                                    "layers": [
                                      {
                                        "digest": "sha256:layer456"
                                      }
                                    ]
                                  }
      • Manifest is uploaded same way as blobs;
      • Client uploads the manifest to the registry; PUT https://registry.example.com/v2/myorg/mychart/manifests/1.0.0, Content-Type: application/vnd.oci.image.manifest.v1+json
      • Registry verifies if digest matches content and stores manifest in content-addressable storage;
      • Only now the artifact becomes available;
    • Tag association
      • What is a tag? A tag is a label that points to a specific manifest;
      • Example: 1.0.0, latest, stable, etc;
      • Internally, tag is mapped to a specific manifest digest: sha256:manifestDigest;
      • Internally, tags are stored as symbolic links to the manifest;
      • Client associates the tag with the manifest; PUT https://registry.example.com/v2/myorg/mychart/manifests/sha256:xxxx, if it responds with 200 OK, then the tag is associated with the manifest;
      • Client uploads the manifest to the registry; PUT https://registry.example.com/v2/myorg/mychart/manifests/sha256:xxxx, if it responds with 200 OK, then the manifest is uploaded;
      • Tags are mutable; Digests are immutable;
    • Tag association
      • Client associates the tag with the manifest; PUT https://registry.example.com/v2/myorg/mychart/manifests/sha256:xxxx, if it responds with 200 OK, then the tag is associated with the manifest;
  • When you pull an artifact:
    • Client requests manifest;
    • Registry returns layer digests;
    • Client downloads blobs;
    • Everything is verified by SHA256 hash.
7. Authentication — helm registry login / logout
  • OCI registries typically use:
    • Basic auth
    • Bearer token auth
    • Cloud IAM integration
    • OAuth
  • Helm and Docker both use the same auth model; Both save the credentials in the same location: ~/.docker/config.json;
  • By default, credentails are base64 encoded in the config file;
  • You can configure a credential helper to store the credentials in a more secure way;
  • Example: 
    
                    {
                        "auths": {
                            "registry.example.com": {
                                "auth": "base64encoded(username:password)"
                            }
                        }
                    }
  • How to login to a registry: 
    
                    helm registry login registry.example.com # Prompts for username and password
                    helm registry login registry.example.com --username myuser --password mypass
  • How to logout from a registry: 
    
                    helm registry logout registry.example.com
  • docker login vs helm registry login
    • You don't actually need both.
    • If you already ran: 
      
                            docker login registry.example.com
    • You can push/pull Helm OCI charts without running helm registry login.
    • Because Helm reads Docker's credential store.
    • In CI/CD:
      • Most teams just use:
        • 
                            docker login ...
      • And Helm works automatically.
    • Or:
      • helm registry login ...
      • If Docker is not installed.
    • Both commands:
      • Authenticate your client to an OCI registry.
8. Pushing a Chart — helm push
  • Step 1: Package the chart 
    helm package ./mychart # Creates mychart-0.1.0.tgz
  • Step 2: Push to an OCI registry 
    helm push mychart-0.1.0.tgz oci://registry.example.com/myorg/myrepo
    ; This chart is stored at oci://registry.example.com/charts/mychart with tag 0.1.0;
  • The chart name comes from Chart.yaml, the tag comes from the chart version;
  • You do NOT specify the chart name or version in the URL — only the "namespace/path";
9. Pulling a Chart — helm pull
  • Step 1: Pull a specific version 
    helm pull oci://registry.example.com/myorg/mychart --version 0.1.0
    ; This chart is downloaded to the current directory as mychart-0.1.0.tgz;
  • Step 2: Pull and untar 
    helm pull oci://registry.example.com/myorg/mychart --version 0.1.0 --untar
    ; This chart is downloaded to the current directory and untarred;
10. Installing from an OCI Registry
  • Step 1: Install directly from OCI registry 
    helm install myrelease oci://registry.example.com/myorg/mychart --version 0.1.0
    ; This chart is installed from the OCI registry;
  • Step 2: Install from Docker Hub 
    helm install myrelease oci://registry-1.docker.io/bitnamicharts/nginx
    ; This chart is installed from the Docker Hub;
  • Step 3: Install with custom values 
    helm install myrelease oci://registry.example.com/myorg/mychart --version 0.1.0 -f values.yaml
    ; This chart is installed from the OCI registry with custom values;
11. Inspecting a Chart in OCI Registry — helm show
  • Step 1: Show chart metadata 
    helm show chart oci://registry.example.com/myorg/mychart --version 0.1.0
    ; This shows the chart metadata;
  • Step 2: Show default values 
    helm show values oci://registry.example.com/myorg/mychart --version 0.1.0
    ; This shows the default values;
  • Step 3: Show README 
    helm show readme oci://registry.example.com/myorg/mychart --version 0.1.0
    ; This shows the README;
  • Step 4: Show everything 
    helm show all oci://registry.example.com/myorg/mychart --version 0.1.0
    ; This shows everything;
8. Listing Tags in a Registry
  • helm search does NOT work with OCI registries;
  • To list available versions/tags, you need to use the registry's API or UI;
9. Helm Template / Upgrade with OCI
  • Step 1: Template rendering 
    helm template myrelease oci://registry.example.com/myorg/mychart --version 0.1.0
    ; This renders the template;
  • Step 2: Upgrade a release 
    helm upgrade myrelease oci://registry.example.com/myorg/mychart --version 0.2.0
    ; This upgrades the release;
