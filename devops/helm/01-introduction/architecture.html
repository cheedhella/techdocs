Helm Architecture

1. Helm v3 Architecture Overview
  • Helm is a client-only tool — nothing runs inside your cluster; Tiller (Helm v2) was removed;
  • The Helm CLI sits on your machine, reads a Chart (a package of template YAML files + default values), fills in the blanks using Go templating, and sends the finished Kubernetes manifests to the API server;
  • Kubernetes does the actual work of creating Pods, Services, etc. — Helm is just the delivery mechanism;
  • After every operation, Helm saves a snapshot of what it deployed as a Kubernetes Secret inside the cluster — this "receipt" enables upgrades, rollbacks, and history tracking;
  • Uses the same credentials as kubectl — reads ~/.kube/config and uses your RBAC permissions;
  • Each release revision is stored as sh.helm.release.v1.<name>.v<n>;
  • On upgrades, Helm performs a three-way merge (old manifest vs new manifest vs live cluster state) so manual changes aren't blindly overwritten;
2. How Does Helm CLI Know Which Cluster to Talk To?
  • Helm reads the kubeconfig file (default: ~/.kube/config) — the same file kubectl uses; if your kubeconfig lives elsewhere, point to it with --kubeconfig /path/to/config or export KUBECONFIG=/path/to/config;
  • It connects to whichever cluster is set as the current context — if kubectl can reach your cluster, so can Helm;
  • You can override this per-command without changing the global context:

Common ways to control which cluster Helm targets:

  • --kube-context <name> — target a specific context for a single command;
  • --kubeconfig <path> — use a different kubeconfig file;
  • --namespace <ns> / -n <ns> — override the target namespace;
  • KUBECONFIG env var — point to one or more kubeconfig files;
  • HELM_KUBECONTEXT env var — set a default context for all Helm commands;

Useful kubectl commands to verify what Helm will use:

  • kubectl config current-context — show the active context (this is what Helm uses);
  • kubectl config get-contexts — list all available contexts;
  • kubectl config use-context <name> — switch the active context;

4. Core Components Explained

Helm CLI

  • Command-line client installed on your local machine or CI/CD system;
  • Communicates with Kubernetes API using kubeconfig;
  • Responsible for: chart management, release operations, repository interactions;
  • Written in Go, available for Linux, macOS, and Windows;

Templating Engine

  • Built into the Helm CLI (not a separate process);
  • Uses Go's text/template package with Sprig function library;
  • Combines chart templates + values to produce final Kubernetes YAML;
  • Helm does NOT deploy anything itself — it sends rendered YAML to the Kubernetes API server;

Charts

  • Packaged Kubernetes application definitions;
  • Contains templates, default values, metadata, and dependencies;
  • Versioned using Semantic Versioning (SemVer);
  • Can be stored locally or in repositories;

Releases

  • An instance of a chart deployed to a Kubernetes cluster;
  • Each installation creates a new release with a unique name;
  • Release history is tracked — allows upgrades and rollbacks;
  • Stored as Kubernetes Secrets in the namespace where the release is installed;

Repositories

  • HTTP servers that host chart packages and index files;
  • Can be public (Artifact Hub, Bitnami) or private (ChartMuseum, Harbor);
  • Support for OCI registries (Docker Hub, ECR, GCR, etc.);

What happens step by step:

  1. Helm CLI reads the chart directory — Chart.yaml, templates/, values.yaml;
  2. Merges values: defaults from values.yaml → overridden by -f custom.yaml → overridden by --set key=value;
  3. Renders all templates through the Go templating engine to produce final Kubernetes YAML;
  4. Validates the rendered manifests;
  5. Sends the manifests to the Kubernetes API server via REST calls;
  6. Kubernetes creates the resources (Deployments, Services, ConfigMaps, etc.);
  7. Helm stores release metadata (revision 1) as a Secret named sh.helm.release.v1.myapp.v1;

       │                  │                      │                      │

       │                  │                      │─────────────────────▶│
       │                  │                      │                      │
       │                  │   Store release v2   │                      │
       │                  │   (keep v1 for       │                      │
       │                  │    rollback)         │                      │
       │                  │─────────────────────▶│                      │
       │                  │                      │                      │
       │  Upgrade done    │                      │                      │
       │◀─────────────────│                      │                      │
       │                  │                      │                      │

What happens step by step:

  1. Helm fetches the current release Secret from the cluster (e.g. revision 1);
  2. Renders new templates with the updated values;
  3. Performs a three-way merge comparing:
    • Old manifest — what Helm deployed last time (from the release Secret);
    • New manifest — what the new templates render to;
    • Live state — the actual current state of resources in the cluster;
  4. Only the differences are applied — unchanged resources are left alone;
  5. Stores a new release revision (v2) as a Secret, keeps v1 for potential rollback;

The three-way merge is critical — it means manual changes made directly with kubectl edit are respected and not blindly overwritten.

       │                  │                      │                      │

What happens step by step:

  1. Helm retrieves the target release revision (v1) from the cluster Secrets;
  2. Performs a three-way merge between the current release, the target revision, and the live cluster state;
  3. Applies the old manifest to bring resources back to the previous state;
  4. Creates a new revision (v3) — rollback does not delete history, it adds a forward revision that points back to the old config;

This means helm history myapp would show: v1 (install) → v2 (upgrade) → v3 (rollback to v1).

What happens step by step:

  1. Helm fetches the latest release Secret to get the full manifest;
  2. Sends delete requests for every resource listed in the manifest;
  3. Kubernetes removes the Deployments, Services, ConfigMaps, Ingresses, etc.;
  4. Helm deletes all release Secrets (every revision) — the release is completely gone;

To keep the release history after uninstall (for auditing), use:

helm uninstall myapp --keep-history

# The release Secrets remain, status changes to "uninstalled"
# You can still view history:
helm history myapp
9. Helm v2 vs Helm v3 Architecture
Aspect Helm v2 (Deprecated) Helm v3 (Current)
Architecture Client-Server (Helm CLI + Tiller) Client-only (Helm CLI)
Server component Tiller pod in cluster None
Security Tiller had cluster-admin by default Uses user's Kubernetes RBAC
Release storage ConfigMaps/Secrets in kube-system Secrets in release namespace
Namespace Tiller namespace separate from release Release in same namespace as resources
CRD handling CRDs upgraded with chart CRDs installed once, never upgraded
Release names Globally unique Unique per namespace
Upgrade strategy Two-way merge (old vs new) Three-way merge (old vs new vs live)
10. Release Storage in Helm v3

Every time Helm installs or upgrades a release, it saves a complete snapshot as a Kubernetes Secret in the same namespace as the release. Think of it as a receipt — Helm can look at any past receipt to know exactly what was deployed, with which values, and roll back to it.

  • Secret name format: sh.helm.release.v1.<release-name>.v<revision>;
  • Each revision gets its own Secret — so revision history grows over time;

What is stored inside each Secret:

  • Manifest — the full rendered Kubernetes YAML that was applied (Deployments, Services, etc.); used during upgrades for the three-way merge and during uninstall to know what to delete;
  • Values — the merged values (defaults + overrides) that were used for this revision; lets you inspect exactly what config was active at any point: helm get values myapp --revision 2;
  • Chart metadata — name, version, appVersion from Chart.yaml; so helm list can show which chart version each release is running;
  • Hooks — pre-install, post-install, pre-upgrade, etc. hook definitions;
  • Notes — the rendered NOTES.txt output shown after install/upgrade;
  • Release status — deployed, superseded, uninstalled, failed, etc.;

Why this matters:

  • Upgrades — Helm compares the old manifest (from the Secret) against the new render to compute the diff;
  • Rollbacks — Helm retrieves a previous revision's Secret and re-applies that manifest;
  • Uninstalls — Helm reads the manifest to know exactly which resources to delete;
  • Auditing — helm history myapp reads all revision Secrets to show who deployed what and when;
# List all release Secrets in the current namespace
kubectl get secrets -l owner=helm

# Example output:
# NAME                              TYPE                 DATA   AGE
# sh.helm.release.v1.myapp.v1      helm.sh/release.v1   1      3d
# sh.helm.release.v1.myapp.v2      helm.sh/release.v1   1      2d
# sh.helm.release.v1.myapp.v3      helm.sh/release.v1   1      1d

# Inspect what was deployed in a specific revision
helm get manifest myapp --revision 1
helm get values myapp --revision 1
helm get notes myapp --revision 1

12. Helm and Kubernetes Interaction
  • Helm uses the same kubeconfig as kubectl (~/.kube/config);
  • Respects current context and namespace;
  • Uses Kubernetes API for all operations (create, update, delete);
  • Does NOT require any special permissions beyond what the user already has;
  • Helm security = Kubernetes security (your RBAC permissions apply);
# Helm uses your current kubectl context
kubectl config current-context

# Helm respects namespace flag
helm install myapp ./chart --namespace production

# Or uses current namespace
kubectl config set-context --current --namespace=production
helm install myapp ./chart
13. Repository Types

HTTP Chart Repositories (Traditional):

  • Simple HTTP server hosting chart packages (.tgz files);
  • Requires an index.yaml file listing all charts;
  • Examples: Bitnami, Artifact Hub;

OCI Registries (Modern):

  • Store charts as OCI artifacts in container registries;
  • Same infrastructure as Docker images;
  • Examples: Docker Hub, ECR, GCR, Harbor, ACR;
  • Becoming the preferred method in Helm v3;
