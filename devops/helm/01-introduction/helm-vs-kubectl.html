Helm vs kubectl

1. What is kubectl?
  • kubectl is the official Kubernetes command-line tool;
  • It directly interacts with the Kubernetes API to manage resources;
  • Works with raw YAML manifests — no templating or packaging;
  • Essential for any Kubernetes work, including when using Helm;
2. Key Differences
Feature kubectl Helm
Purpose Low-level Kubernetes API client High-level package manager
Deployment unit Individual YAML files Charts (packaged collections)
Templating ❌ No built-in templating ✅ Go templating with variables
Release tracking ❌ No release concept ✅ Tracks every deployment as a release
Rollback ⚠️ Manual (kubectl rollout undo) ✅ Automatic (helm rollback)
Dependency management ❌ None ✅ Built-in dependency resolution
Configuration management ⚠️ Manual or with kustomize ✅ values.yaml with overrides
Versioning ❌ No built-in versioning ✅ SemVer for charts and releases
Sharing ⚠️ Copy YAML files ✅ Chart repositories
Learning curve ✅ Simpler for beginners ⚠️ Requires understanding of templating
3. Deployment Comparison

Using kubectl:

# Apply each file individually
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl apply -f configmap.yaml
kubectl apply -f ingress.yaml

# Update image version (manual edit or sed)
kubectl set image deployment/myapp myapp=myapp:v2.0

# Rollback (only works for Deployments)
kubectl rollout undo deployment/myapp

# Delete everything (must remember all resources)
kubectl delete -f deployment.yaml
kubectl delete -f service.yaml
kubectl delete -f configmap.yaml
kubectl delete -f ingress.yaml

Using Helm:

# Install everything at once
helm install myapp ./chart

# Upgrade with new image version
helm upgrade myapp ./chart --set image.tag=v2.0

# Rollback entire release
helm rollback myapp 1

# Delete everything
helm uninstall myapp
4. Configuration Management Comparison

kubectl approach:

# Separate files for each environment
deployment-dev.yaml    # replicas: 1, image: myapp:dev
deployment-staging.yaml # replicas: 2, image: myapp:staging
deployment-prod.yaml   # replicas: 5, image: myapp:v1.0

# Deploy to each environment
kubectl apply -f deployment-dev.yaml
kubectl apply -f deployment-staging.yaml
kubectl apply -f deployment-prod.yaml

Helm approach:

# Single template: templates/deployment.yaml
replicas: {{ .Values.replicaCount }}
image: {{ .Values.image.repository }}:{{ .Values.image.tag }}

# Different values files
values-dev.yaml:    replicaCount: 1, tag: dev
values-staging.yaml: replicaCount: 2, tag: staging
values-prod.yaml:   replicaCount: 5, tag: v1.0

# Deploy to each environment
helm install myapp ./chart -f values-dev.yaml
helm install myapp ./chart -f values-staging.yaml
helm install myapp ./chart -f values-prod.yaml
5. When to Use Each

Use kubectl when:

  • Learning Kubernetes basics;
  • Quick one-off deployments or testing;
  • Debugging specific resources;
  • Very simple applications (1-2 resources);
  • You need direct, low-level control;

Use Helm when:

  • Managing complex applications with many resources;
  • Deploying across multiple environments;
  • Need versioning and rollback capabilities;
  • Want to share/reuse configurations;
  • Managing dependencies between applications;
  • CI/CD automation;
6. Can They Work Together?

Yes! They complement each other:

  • Helm uses kubectl under the hood to apply resources;
  • You can use kubectl to inspect resources deployed by Helm;
  • Use Helm for deployment, kubectl for debugging;
# Deploy with Helm
helm install myapp ./chart

# Debug with kubectl
kubectl get pods -l app=myapp
kubectl logs myapp-pod-xyz
kubectl describe pod myapp-pod-xyz
kubectl exec -it myapp-pod-xyz -- /bin/sh
7. Alternative: Kustomize
  • Kustomize is another tool for managing Kubernetes configurations;
  • Built into kubectl (kubectl apply -k);
  • Uses overlays instead of templates;
  • Simpler than Helm but less powerful;
  • Good middle ground between raw kubectl and Helm;
