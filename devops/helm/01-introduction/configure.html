Configuring Helm CLI with a k8s cluster

1. How Helm knows about k8s cluster?
  • Helm doesn't manager clusters by itselfl; It rather uses kubectl context(same cluster as kubectl is talking to);
  • If kubectl can reach your cluster, Helm can too — no extra setup is needed.
2. What is Context?
  • It defines the cluster, user/credentials and default namespace to use;
  • Think of it as a profile for kubectl to talk to a specific cluster;
  • > kubectl config get-contexts  # List all contexts
CURRENT   NAME              CLUSTER           AUTHINFO        NAMESPACE
*         dev-cluster       dev-cluster       dev-user        default
          prod-cluster      prod-cluster      prod-user       production

| Column      | Meaning                      |
| ----------- | ---------------------------- |
| `CURRENT`   | `*` shows the active context |
| `NAME`      | Context name                 |
| `CLUSTER`   | Kubernetes cluster name      |
| `AUTHINFO`  | User credentials used        |
| `NAMESPACE` | Default namespace            |
3. What is kube config file?
  • It is a YAML file that stores information about clusters, users, and contexts;
  • Kubectl loads config in this order:
    • --kubeconfig flag (highest priority)
    • KUBECONFIG environment variable
    • Default ~/.kube/config
  • KUBECONFIG is an environment variable that points to the kubeconfig file;
  • It can be set to a single file or a comma-separated list of files; Eg: export KUBECONFIG=~/.kube/dev-config:~/.kube/prod-config
  • If KUBECONFIG is not set, Kubernetes uses the default ~/.kube/config
  • It is used by kubectl and Helm to determine which cluster to talk to;
  • It is also used to store authentication credentials for different clusters;
  • It is also used to store default namespace to use for a context;
  • It is also used to store the current active context;
  • Structure of kube config file: 
    
apiVersion: v1
kind: Config
clusters:
- name: dev-cluster
  cluster:
    server: https://1.2.3.4
    certificate-authority-data: LS0tLS1CRUdJTi...

users:
- name: dev-user
  user:
    client-certificate-data: LS0tLS1CRUdJTi...
    client-key-data: LS0tLS1CRUdJTi...

contexts:
- name: dev-context
  context:
    cluster: dev-cluster
    user: dev-user
    namespace: default

current-context: dev-context
4. Commands to manage k8s cluster(contexts)
CommandDescription
kubectl config viewDisplays the current kubeconfig file;
kubectl config view --rawDisplays the current kubeconfig file in raw format;
kubectl config get-contextsLists all contexts as per your kubeconfig file;
kubectl config current-contextDisplays the current active context;
kubectl config use-context <context-name>Switches the active context to the specified context; All kubectl/helm commands will use this context;
kubectl config set-context <context-name> --cluster=dev-cluster -user=dev-user --namespace=devIt creates or modifies a context definition in the kubeconfig file; It doesn't switch the context;
kubectl config rename-context <old-name> <new-name>Renames the specified context;
kubectl config delete-context <context-name>Deletes the specified context;
kubectl cluster-infoIt displays information about k8s control plane and core services running on it;
5. Targeting a Specific Context Without Switching
  • --kube-context <context-name>
    • You can run any helm command against any specific context without changing the active context;
    • Eg: helm list --kube-context <context-name>
  • --kube-config <path-to-kubeconfig-file>
    • If the target context exists in another kubeconfig file, You can use this option;
    • Eg: helm list --kube-config <context-name>
6. Temporarily override the namespace in current context
  • --namespace <namespace-name>
    • You can override the namespace in current context for a single helm command;
    • Eg: helm install myapp ./chart --namespace production
7. Talk to API Server directly without context
  • helm list --kube-apiserver https://k8s-api.example.com:6443 --kube-token "$KUBE_BEARER_TOKEN" --kube-ca-file ca.crt
  • This approachis commonly used in:
    • CI/CD pipelines
    • Automation scripts
    • Service account–based deployments
