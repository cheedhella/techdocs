Helm Architecture

1. Helm v3 Architecture Overview
  • Helm v3 uses a client-only architecture — no server-side component (Tiller was removed);
  • The Helm CLI interacts directly with the Kubernetes API server;
  • Release information is stored as Kubernetes Secrets in the cluster;
  • Uses Kubernetes RBAC for access control;
2. Core Components

🔧 Helm CLI

  • Command-line client installed on your local machine or CI/CD system;
  • Communicates with Kubernetes API using kubeconfig;
  • Responsible for: chart management, release operations, repository interactions;
  • Written in Go, available for Linux, macOS, and Windows;

📦 Charts

  • Packaged Kubernetes application definitions;
  • Contains templates, default values, metadata, and dependencies;
  • Versioned using Semantic Versioning (SemVer);
  • Can be stored locally or in repositories;

🚀 Releases

  • An instance of a chart deployed to a Kubernetes cluster;
  • Each installation creates a new release with a unique name;
  • Release history is tracked — allows upgrades and rollbacks;
  • Stored as Kubernetes Secrets in the namespace where the release is installed;

📚 Repositories

  • HTTP servers that host chart packages and index files;
  • Can be public (Artifact Hub, Bitnami) or private (ChartMuseum, Harbor);
  • Support for OCI registries (Docker Hub, ECR, GCR, etc.);
3. How Helm Works: The Flow

Installation Flow:

1. User runs: helm install myapp ./chart
2. Helm CLI reads chart files and values
3. Helm renders templates using Go templating engine
4. Generated Kubernetes manifests are validated
5. Helm sends manifests to Kubernetes API server
6. Kubernetes creates the resources
7. Helm stores release info as a Secret in the cluster
8. Release is now tracked and can be managed

Upgrade Flow:

1. User runs: helm upgrade myapp ./chart --set image.tag=v2.0
2. Helm retrieves current release from cluster
3. Helm renders new templates with updated values
4. Helm performs a three-way merge:
   - Previous release manifest
   - New rendered manifest
   - Current live state in cluster
5. Helm applies only the changes to Kubernetes
6. New release version is stored
7. Previous release is kept for rollback

Rollback Flow:

1. User runs: helm rollback myapp 1
2. Helm retrieves the specified release version
3. Helm applies the old manifest to the cluster
4. Creates a new release version pointing to old config
5. Application returns to previous state
4. Helm v2 vs Helm v3 Architecture
Aspect Helm v2 (Deprecated) Helm v3 (Current)
Architecture Client-Server (Helm CLI + Tiller) Client-only (Helm CLI)
Server component ✅ Tiller pod in cluster ❌ None
Security ⚠️ Tiller had cluster-admin by default ✅ Uses user's Kubernetes RBAC
Release storage ConfigMaps/Secrets in kube-system Secrets in release namespace
Namespace ⚠️ Tiller namespace separate from release ✅ Release in same namespace as resources
CRD handling ⚠️ CRDs upgraded with chart ✅ CRDs installed once, never upgraded
Release names ⚠️ Globally unique ✅ Unique per namespace
5. Release Storage in Helm v3
  • Release metadata is stored as Kubernetes Secrets;
  • Secret name format: sh.helm.release.v1.<release-name>.v<revision>;
  • Each release revision gets its own Secret;
  • Contains: manifest, values, chart metadata, hooks, notes;
# View release secrets
kubectl get secrets -l owner=helm

# Example output:
sh.helm.release.v1.myapp.v1
sh.helm.release.v1.myapp.v2
sh.helm.release.v1.myapp.v3
6. Chart Structure
mychart/
├── Chart.yaml          # Chart metadata (name, version, description)
├── values.yaml         # Default configuration values
├── charts/             # Dependent charts (subcharts)
├── templates/          # Kubernetes manifest templates
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── _helpers.tpl   # Template helpers
│   └── NOTES.txt      # Post-install notes
├── .helmignore        # Files to ignore when packaging
└── README.md          # Documentation
7. Helm and Kubernetes Interaction
  • Helm uses the same kubeconfig as kubectl (~/.kube/config);
  • Respects current context and namespace;
  • Uses Kubernetes API for all operations (create, update, delete);
  • Does NOT require any special permissions beyond what the user already has;
# Helm uses your current kubectl context
kubectl config current-context

# Helm respects namespace flag
helm install myapp ./chart --namespace production

# Or uses current namespace
kubectl config set-context --current --namespace=production
helm install myapp ./chart
8. Repository Types

HTTP Chart Repositories (Traditional):

  • Simple HTTP server hosting chart packages (.tgz files);
  • Requires an index.yaml file listing all charts;
  • Examples: Bitnami, Artifact Hub;

OCI Registries (Modern):

  • Store charts as OCI artifacts in container registries;
  • Same infrastructure as Docker images;
  • Examples: Docker Hub, ECR, GCR, Harbor, ACR;
  • Becoming the preferred method in Helm v3;
