Hooks

1. What is a Hook?
  • Hooks are used to run a script/command/job at specific points in the release lifecycle(before/after installation/upgrade/deletion/rollback);
2. Purpose of Hooks
  • Sometimes, deployment requires some additional steps to be taken, such as:
    • Running database migration, before upgrading an application;
    • Running a job to backup a database before installing a new chart and a second job to restore the data in the database;
    • Running a job before deleting a release to gracefully take out a service before completely removing it;
  • It is just like any other template file, under templates folder;
  • Hooks run in a separate pod inside of your Kubernetes cluster. The value specified in the helm.sh/hook annotation determines when the hook should be rendered.
3. What makes a Hook different from a regular template?
  • A template becomes a hook, when you add 'helm.sh/hook' annotation to it, which tells Helm to run that resource at a particular point in the release lifecycle (instead of as a normal resource);
  • Eg:
    apiVersion: batch/v1
kind: Job
metadata:
  annotations:
    "helm.sh/hook": pre-install
    "helm.sh/hook-weight": "0"
4. Hook Annotations
  • helm.sh/hook
    • It specifies the type of hook to run(pre-install, post-install etc);
    • In other words, it specifies the point in the release lifecycle at which the resource should be run;
  • helm.sh/hook-weight
    • It controls the order in which the hooks are executed;
    • Default weight is 0; lower weights run first; Negative weights are allowed;
  • helm.sh/resource-policy
    • It is for normal resources, not for hook resources;
    • By default, helm deletes all normal resources, when the release is removed;
    • It can be one of the following values:
      • keep: It prevents helm from deleting a resouce(normal or hook resource);
    • Eg: 
      apiVersion: v1
    kind: PersistentVolumeClaim
    metadata:
      name: my-data
      annotations:
        "helm.sh/resource-policy": keep
    
    When the release is removed, the PVC will not be deleted. If needed, you can manually delete the PVC;
    • It is useful for:
      • Persistent volumes
      • Databases
      • Shared secrets
      • Manually managed resources
  • helm.sh/hook-delete-policy
    • It is for hook resources, not for normal resources;
    • It specifies the policy to use when deleting the hook;
    • It can be one of the following values:
      • before-hook-creation: Delete the previous hook resource before creating a new one (recommended);
      • hook-succeeded -> Delete the hook resource after it succeeds;
      • hook-failed -> Delete the hook resource if it fails;
    • You can specify multiple policies, separated by commas;
    • If no delete policy is set, hook resources are never automatically deleted — they accumulate;
    • Without hook-delete-policy, repeated installs/upgrades can create many leftover hook jobs;
5. Hook Types
  • pre-install: Executes after templates are rendered, but before any resources are created in Kubernetes
  • post-install: Executes after all resources are loaded into Kubernetes
  • pre-delete: Executes on a deletion request before any resources are deleted from Kubernetes
  • post-delete: Executes on a deletion request after all of the release’s resources have been deleted
  • pre-upgrade: Executes on an upgrade request after templates are rendered, but before any resources are updated
  • post-upgrade: Executes on an upgrade after all resources have been upgraded
  • pre-rollback: Executes on a rollback request after templates are rendered, but before any resources are rolled back
  • post-rollback: Executes on a rollback request after all resources have been modified
  • test: Executes when the Helm test subcommand is invoked ( view test docs)
  • before-hook-creation: Executes before a hook is created
  • hook-succeeded: Executes after a hook succeeds
  • hook-failed: Executes after a hook fails
6. Release Lifecycle with Hooks
  • Install Lifecycle:
    • pre-install hooks run
    • resources are created in k8s cluster
    • post-install hooks run
  • Upgrade Lifecycle:
    • pre-upgrade hooks run
    • resources are updated in k8s cluster
    • post-upgrade hooks run
  • Deletion Lifecycle:
    • pre-delete hooks run
    • resources are deleted from k8s cluster
    • post-delete hooks run
  • Rollback Lifecycle:
    • pre-rollback hooks run
    • resources are rolled back in k8s cluster
    • post-rollback hooks run
  • Test Lifecycle:
    • test hooks run
