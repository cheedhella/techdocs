2. What Makes a Template a Hook?
  • A single annotation on any Kubernetes resource turns it into a hook: 
    metadata:
  annotations:
    "helm.sh/hook": pre-install
  • The resource is not managed as part of the release — it is created/deleted independently by Helm at the designated lifecycle point;
  • Hook resources run as Jobs (or Pods) — Helm waits for them to complete before proceeding;
3. Hook Annotations
  • helm.sh/hook — which lifecycle event triggers this resource:
    ValueWhen It Runs
    pre-installAfter templates are rendered, before any resources are created
    post-installAfter all resources are loaded into Kubernetes
    pre-upgradeAfter templates are rendered, before any resources are updated
    post-upgradeAfter all resources have been upgraded
    pre-deleteBefore any resources are deleted from Kubernetes
    post-deleteAfter all release resources have been deleted
    pre-rollbackAfter templates are rendered, before any resources are rolled back
    post-rollbackAfter all resources have been rolled back
    testWhen you run helm test <release>
  • helm.sh/hook-weight — execution order when multiple hooks share the same event (lower runs first; default "0");
  • helm.sh/hook-delete-policy — when to clean up the hook resource:
    PolicyBehaviour
    before-hook-creationDelete the previous hook resource before creating a new one (recommended)
    hook-succeededDelete the hook resource after it succeeds
    hook-failedDelete the hook resource if it fails
4. Anatomy of a Hook Template
  • Every hook in this demo follows the same pattern — a Job that runs busybox and prints a message: 
    # templates/pre-install-hook.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-pre-install
  annotations:
    "helm.sh/hook": pre-install              # ← lifecycle event
    "helm.sh/hook-weight": "0"               # ← execution order
    "helm.sh/hook-delete-policy": before-hook-creation  # ← cleanup policy
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: pre-install
          image: busybox
          command: ["sh", "-c", "echo '>>> PRE-INSTALL hook executed at:' $(date)"]
  • All other hooks are identical except for the helm.sh/hook value and the echo message;
5. Install — pre-install and post-install
  • Install the chart: 
    helm install demo ./hook-types-demo
  • Lifecycle order:
    1. Helm renders all templates;
    2. pre-install hook Job is created → Helm waits for it to complete;
    3. All release resources are created (Deployment, Service);
    4. post-install hook Job is created → Helm waits for it to complete;
    5. helm install returns;
  • Verify the hooks ran: 
    # List hook Jobs
kubectl get jobs
NAME                  COMPLETIONS   DURATION   AGE
demo-pre-install      1/1           3s         45s
demo-post-install     1/1           3s         38s

# Check the pre-install log
kubectl logs job/demo-pre-install
>>> PRE-INSTALL hook executed at: Wed Mar 5 10:00:01 UTC 2026

# Check the post-install log
kubectl logs job/demo-post-install
>>> POST-INSTALL hook executed at: Wed Mar 5 10:00:08 UTC 2026
  • Notice the timestamps: pre-install ran before the resources were created, post-install ran after;
  • Verify the app resources: 
    kubectl get deploy,svc

deployment.apps/demo-app   1/1     1            1

9. Uninstall — pre-delete and post-delete
  • Uninstall the release: 
    helm uninstall demo
  • Lifecycle order:

    2. All release resources are deleted (Deployment, Service);
    3. post-delete hook Job is created → Helm waits;
    4. helm uninstall returns;

10. Complete Lifecycle Summary
Command Hooks Executed (in order) What Happens Between Hooks
helm install pre-install → post-install All chart resources are created
helm upgrade pre-upgrade → post-upgrade Chart resources are updated
helm rollback pre-rollback → post-rollback Chart resources are reverted to the target revision
helm test test Nothing — test just validates the running release
helm uninstall pre-delete → post-delete All chart resources are deleted
11. Hook Weights — Controlling Execution Order
  • When multiple hooks share the same event, helm.sh/hook-weight determines the order (ascending, lowest first): 
    # Runs first (weight -5)
metadata:
  annotations:
    "helm.sh/hook": pre-install
    "helm.sh/hook-weight": "-5"

# Runs second (weight 0)
metadata:
  annotations:
    "helm.sh/hook": pre-install
    "helm.sh/hook-weight": "0"

# Runs third (weight 10)
metadata:
  annotations:
    "helm.sh/hook": pre-install
    "helm.sh/hook-weight": "10"
  • Use case: run DB migration (weight: -5) before cache warming (weight: 5), both as pre-upgrade hooks;
12. Hook Delete Policies
  • Controls when Helm cleans up the hook resource:
    PolicyWhen DeletedBest For
    before-hook-creation Old hook is deleted just before the new one is created Most hooks — ensures a clean slate on each run
    hook-succeeded Deleted immediately after the hook succeeds When you don't want completed Jobs lingering
    hook-failed Deleted if the hook fails (keeps it on success for debugging) Rarely used alone
  • You can combine policies: 
    annotations:
  "helm.sh/hook-delete-policy": "before-hook-creation,hook-succeeded"
  • If no delete policy is set, hook resources are never automatically deleted — they accumulate;
13. Multiple Hooks on a Single Resource
  • A single resource can respond to multiple lifecycle events by listing them comma-separated: 
    annotations:
  "helm.sh/hook": "pre-install,pre-upgrade"
  • This Job runs before both install and upgrade — useful for DB migrations that should run on every deploy;
14. Practical Use Cases
  • pre-install / pre-upgrade: Database migration, schema validation, dependency checks;
  • post-install: Seed initial data, send deployment notification, register with service mesh;
  • post-upgrade: Warm caches, notify monitoring, run smoke tests;
  • pre-delete: Backup database, deregister from load balancer, drain connections;
  • post-delete: Clean up external resources (DNS records, cloud storage), send notification;
  • pre-rollback: Backup current state before reverting;
  • post-rollback: Invalidate caches, notify team;
  • test: Verify HTTP endpoints, check database connectivity, validate configuration;
