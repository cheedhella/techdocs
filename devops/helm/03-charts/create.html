Creating a Chart

1. helm create
  • Instead of creating all files manually, It creates/scaffolds a new chart with the standard directory structure and commonly used templatefiles;
  • The default scaffold deploys an Nginx application with Deployment, Service, ServiceAccount, Ingress, and HPA;
  • Syntax: 
    helm create <chart-name>
  • Eg: 
    helm create hello-world
Creating hello-world

> ls -a hello-world/

> ls hello-world/templates/

3. Understanding Each File and Its Fields
  • Chart.yaml — chart metadata (required) 
    • apiVersion: v2
name: mychart
description: A Helm chart for my application
type: application
version: 0.1.0
appVersion: "1.0.0"
keywords:
  - web
  - api
home: https://example.com
sources:
  - https://github.com/example/mychart
maintainers:
  - name: John Doe
    email: john@example.com
dependencies:
  - name: redis
    version: "18.x.x"
    repository: "https://charts.bitnami.com/bitnami"
    condition: redis.enabled
    • apiVersion — must be v2 for Helm 3 charts (v1 was for Helm 2)
    • name — name of the chart; must match the directory name
    • description — one-line description of the chart
    • type:
      • application (default) — can be deployed to a cluster; contains templates that produce k8s resources
      • library — provides reusable template helpers only; cannot be installed on its own; application charts can depend on library charts
    • version — version of the chart itself (SemVer: Major.Minor.Patch); must be incremented each time you change anything in the chart
    • appVersion — version of the application the chart deploys; purely informational — Helm doesn't use it for anything
      • Override at package time: helm package . --app-version 9.1.2
      • Override at install/upgrade time: helm upgrade <release> <chart> --set "image.tag=9.1.2"
    • keywords — list of keywords for searching in repositories
    • home — URL of the project home page
    • sources — list of URLs to source code
    • maintainers — list of maintainers with name, email, and optional url
    • dependencies — list of charts this chart depends on; downloaded to charts/ via helm dependency update
      • name — name of the dependency chart
      • version — version constraint (SemVer range)
      • repository — URL of the chart repository
      • condition — a values.yaml path that enables/disables this dependency (e.g., redis.enabled)
      • tags — list of tags to group-enable/disable dependencies
      • alias — an alternate name for the dependency
  • Chart.lock — auto-generated by helm dependency update; locks exact resolved dependency versions for reproducible builds
    • Do not edit manually; regenerated every time you run helm dependency update
    • helm dependency build uses Chart.lock to download the exact same versions
  • values.yaml — default configuration values for the chart's templates
    • Templates reference values using {{ .Values.<key> }}
    • You never need to edit template files — just override values
    • replicaCount: 1

image:
  repository: nginx
  pullPolicy: IfNotPresent
  tag: ""              # empty = defaults to appVersion

service:
  type: ClusterIP
  port: 80

ingress:
  enabled: false

resources:
  limits:
    cpu: 200m
    memory: 256Mi
  requests:
    cpu: 100m
    memory: 128Mi

autoscaling:
  enabled: false
  minReplicas: 1
  maxReplicas: 100
  targetCPUUtilizationPercentage: 80
    • How to override:
      • helm install myrelease mychart -f custom-values.yaml
      • helm install myrelease mychart --set replicaCount=3 --set service.type=NodePort
      • Multiple value files (later files take precedence): helm install myrelease mychart -f base.yaml -f production.yaml
  • values.schema.json — optional JSON Schema that validates values.yaml
    • If present, Helm validates user-provided values against this schema during install, upgrade, lint, and template
    • Useful for enforcing required fields, types, and allowed values
  • .helmignore — files to exclude when packaging with helm package
    • Works like .gitignore; one pattern per line
    • .git
.gitignore
*.swp
*.bak
.idea/
.vscode/
  • README.md — human-readable documentation for the chart
    • Typically describes what the chart does, prerequisites, configuration options, and usage examples
  • LICENSE — license file for the chart
  • charts/ — dependency charts
    • Contains dependency charts as .tgz packages or unpacked chart directories
    • Populated by helm dependency update which reads the dependencies section in Chart.yaml and downloads them here
    • You can also manually place chart directories here
  • crds/ — Custom Resource Definitions
    • CRDs placed here are installed before any templates are rendered
    • CRDs are never upgraded or deleted by Helm — this is by design to prevent accidental data loss
    • Only plain YAML files (no templating allowed in this directory)
  • templates/ — Kubernetes resource templates
    • Helm runs each file through the Go template rendering engine, combining them with values.yaml to produce valid k8s manifests
    • Files starting with _ (e.g., _helpers.tpl) do NOT produce k8s manifest output — they contain reusable named templates
  • templates/_helpers.tpl — reusable named template definitions
    • Contains {{- define "name" }} blocks that other templates include via {{ include "name" . }}
    • Commonly defines: chart name, fully qualified name, common labels, selector labels
    • Does not produce any k8s manifest output
  • templates/deployment.yaml — Deployment resource
    • Defines the application: container image, replicas, ports, health checks, resource limits, environment variables
    • References values like {{ .Values.image.repository }}, {{ .Values.replicaCount }}
  • templates/service.yaml — Service resource
    • Exposes the Deployment as a stable network endpoint inside the cluster
    • Type is typically ClusterIP, NodePort, or LoadBalancer
  • templates/serviceaccount.yaml — ServiceAccount resource
    • Creates a Kubernetes service account for the application pods
    • Usually conditionally created: {{- if .Values.serviceAccount.create }}
  • templates/ingress.yaml — Ingress resource
    • Provides HTTP routing rules for external traffic to reach the Service
    • Usually conditionally created: {{- if .Values.ingress.enabled }}
  • templates/hpa.yaml — HorizontalPodAutoscaler resource
    • Configures automatic scaling based on CPU/memory utilization
    • Usually conditionally created: {{- if .Values.autoscaling.enabled }}
  • templates/configmap.yaml — ConfigMap resource
    • Stores non-sensitive configuration data (config files, environment variables)
  • templates/secret.yaml — Secret resource
    • Stores sensitive data (passwords, API keys, TLS certificates)
  • templates/NOTES.txt — post-install/upgrade instructions
    • Rendered like other templates (supports Go templating) but output is printed to the user after helm install or helm upgrade
    • Not sent to Kubernetes — purely informational
    • Typically shows how to access the deployed application (port-forward commands, URLs)
  • templates/tests/ — test pod definitions
    • Pods annotated with "helm.sh/hook": test that verify the installation works
    • Run via helm test <release>
    • Common test: a curl pod that hits the Service endpoint and checks for a successful response
4. Customize the Chart
  • Edit Chart.yaml — set your chart name, version, and appVersion(optional);
  • Edit values.yaml — point to your Docker image and configure resources: 
    replicaCount: 2

image:
  repository: myuser/myapp
  pullPolicy: IfNotPresent
  tag: "2.0.0"

service:
  type: ClusterIP
  port: 8080

resources:
  limits:
    cpu: 200m
    memory: 256Mi
  requests:
    cpu: 100m
    memory: 128Mi
  • Edit templates/ as needed — adjust health checks, add ConfigMaps, Secrets, etc.;
5. Lint the Chart
  • helm lint
6. Render Templates Locally
  • Renders the Go templates into final k8s YAML without installing — lets you inspect the output: 
    helm template myrelease ./myapp
  • Render with custom values: 
    helm template myrelease ./myapp -f production-values.yaml
helm template myrelease ./myapp --set replicaCount=3
  • To also validate against the k8s API server (requires a running cluster): 
    helm install myrelease ./myapp --dry-run --debug
7. Package the Chart
  • Bundles the chart directory into a versioned .tgz archive: 
    helm package ./myapp
# Successfully packaged chart and saved it to: ./myapp-0.1.0.tgz
  • Output file name format: <name>-<version>.tgz (both come from Chart.yaml);
  • Files matching patterns in .helmignore are excluded;
  • Override versions at package time: 
    helm package ./myapp --version 1.0.0
helm package ./myapp --app-version 3.0.0
helm package ./myapp -d /path/to/output/
8. Login to the OCI Registry
  • Authenticate before pushing: 
    # Docker Hub
helm registry login registry-1.docker.io
# Username: myuser
# Password: ****
  • Other registries: 
    # GitHub Container Registry
echo $GITHUB_TOKEN | helm registry login ghcr.io --username myuser --password-stdin

# AWS ECR
aws ecr get-login-password --region us-east-1 | helm registry login \
  --username AWS --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com

# Azure ACR
helm registry login myregistry.azurecr.io --username myuser --password mypass

# Google Artifact Registry
gcloud auth print-access-token | helm registry login \
  -u oauth2accesstoken --password-stdin us-central1-docker.pkg.dev
9. Push the Chart
  • Push the .tgz to the registry — specify only the namespace, NOT the chart name or version: 
    helm push myapp-0.1.0.tgz oci://registry-1.docker.io/myuser
  • The chart is stored at: oci://registry-1.docker.io/myuser/myapp with tag 0.1.0;
  • The chart name comes from Chart.yaml name field;
  • The tag comes from Chart.yaml version field;
  • Other registries — same pattern: 
    helm push myapp-0.1.0.tgz oci://ghcr.io/myuser
helm push myapp-0.1.0.tgz oci://123456789.dkr.ecr.us-east-1.amazonaws.com
helm push myapp-0.1.0.tgz oci://myregistry.azurecr.io/charts
helm push myapp-0.1.0.tgz oci://us-central1-docker.pkg.dev/myproject/myrepo
10. Verify the Push
  • Show chart metadata directly from the registry: 
    helm show chart oci://registry-1.docker.io/myuser/myapp --version 0.1.0
  • Pull the chart back locally: 
    helm pull oci://registry-1.docker.io/myuser/myapp --version 0.1.0
  • Install from the registry: 
    helm install myrelease oci://registry-1.docker.io/myuser/myapp --version 0.1.0
11. Push a New Version
  • Bump the version in Chart.yaml: 
    version: 0.2.0
appVersion: "2.1.0"
  • Package and push: 
    helm package ./myapp
helm push myapp-0.2.0.tgz oci://registry-1.docker.io/myuser
  • Both 0.1.0 and 0.2.0 now exist as separate tags in the registry;
  • Users install a specific version with --version;
12. Logout
  • helm registry logout registry-1.docker.io
