Upgrading and Rolling Back Releases

1. Upgrading a Release
# Basic upgrade
helm upgrade myapp ./chart

# Upgrade with new values
helm upgrade myapp ./chart -f values-prod.yaml

# Upgrade with --set
helm upgrade myapp ./chart --set image.tag=v2.0

# Upgrade and wait for completion
helm upgrade myapp ./chart --wait --timeout 5m

# Atomic upgrade (rollback on failure)
helm upgrade myapp ./chart --atomic
2. Install or Upgrade
# Install if not exists, upgrade if exists
helm upgrade --install myapp ./chart

# Short form
helm upgrade -i myapp ./chart

# With namespace creation
helm upgrade --install myapp ./chart --create-namespace -n production
3. Upgrade Options
Option Description
--install Install if release doesn't exist
--atomic Rollback on failure
--wait Wait for resources to be ready
--timeout Time to wait (default: 5m)
--force Force resource updates (recreate pods)
--cleanup-on-fail Delete new resources on failure
--reset-values Reset values to chart defaults
--reuse-values Reuse values from previous release
--history-max Limit number of revisions saved
4. Understanding --reuse-values vs --reset-values
# Default: merge new values with existing
helm upgrade myapp ./chart --set image.tag=v2.0

# Reset to chart defaults, then apply new values
helm upgrade myapp ./chart --reset-values --set image.tag=v2.0

# Reuse all previous values, override with new
helm upgrade myapp ./chart --reuse-values --set image.tag=v2.0
5. Rolling Back a Release
# Rollback to previous revision
helm rollback myapp

# Rollback to specific revision
helm rollback myapp 2

# Rollback with wait
helm rollback myapp 2 --wait --timeout 5m

# Dry run rollback
helm rollback myapp 2 --dry-run
6. Rollback Options
Option Description
--wait Wait for resources to be ready
--timeout Time to wait for rollback
--cleanup-on-fail Delete new resources if rollback fails
--force Force resource updates
--recreate-pods Recreate pods for rollback
7. Upgrade/Rollback Workflow
# 1. Check current release
helm list
helm status myapp

# 2. View current revision
helm history myapp

# 3. Dry run upgrade
helm upgrade myapp ./chart --dry-run --debug

# 4. Perform upgrade
helm upgrade myapp ./chart --wait

# 5. Verify upgrade
helm status myapp
kubectl get pods

# 6. If issues, rollback
helm rollback myapp

# 7. Verify rollback
helm history myapp
8. Revision History Management
# View revision history
helm history myapp

# Limit stored revisions (saves cluster storage)
helm upgrade myapp ./chart --history-max 5

# Each upgrade creates a new revision
# Revision 1: Initial install
# Revision 2: First upgrade
# Revision 3: Second upgrade
# Revision 4: Rollback to revision 2 (creates new revision!)
# Revision 5: Third upgrade
9. Force Upgrade

Use --force when resources need to be recreated:

# Force recreate pods (useful for ConfigMap/Secret changes)
helm upgrade myapp ./chart --force

# This will:
# - Delete existing pods
# - Create new pods with updated configuration
# - May cause downtime!
10. Troubleshooting Upgrades

Issue: Upgrade stuck in pending-upgrade

# Check release status
helm status myapp

# View pods
kubectl get pods -n <namespace>

# If truly stuck, rollback
helm rollback myapp

Issue: Upgrade fails but doesn't rollback

# Use --atomic for automatic rollback
helm upgrade myapp ./chart --atomic

# Or manually rollback
helm rollback myapp

Issue: ConfigMap/Secret changes not applied

# Use --force to recreate pods
helm upgrade myapp ./chart --force

# Or add checksum annotation to force pod restart
# In deployment template:
annotations:
  checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
11. Best Practices
  • Always dry-run first: helm upgrade --dry-run --debug;
  • Use --atomic in production: Automatic rollback on failure;
  • Limit revision history: --history-max 10 to save storage;
  • Wait for readiness: Use --wait to ensure pods are ready;
  • Test rollback procedure: Practice in non-prod environments;
  • Monitor during upgrades: Watch pod status with kubectl get pods -w;
