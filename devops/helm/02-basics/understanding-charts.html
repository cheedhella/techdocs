Understanding Helm Charts

1. What is a Helm Chart?
  • A Helm Chart is a package of pre-configured Kubernetes resources;
  • Think of it as a "blueprint" for deploying an application to Kubernetes;
  • Contains templates, default values, metadata, and dependencies;
  • Can be versioned, shared, and reused across environments;
2. Chart Components
File/Directory Purpose Required?
Chart.yaml Chart metadata (name, version, description) ✅ Yes
values.yaml Default configuration values ❌ No (but recommended)
templates/ Kubernetes manifest templates ✅ Yes
charts/ Dependent charts (subcharts) ❌ No
README.md Human-readable documentation ❌ No (but recommended)
.helmignore Files to exclude when packaging ❌ No
templates/NOTES.txt Post-installation instructions ❌ No (but helpful)
3. Types of Charts

📦 Application Charts

  • Standard charts that deploy applications;
  • Can have dependencies on other charts;
  • Example: WordPress chart that depends on MySQL chart;

📚 Library Charts

  • Provide reusable template helpers;
  • Cannot be installed directly;
  • Used as dependencies by other charts;
  • Defined with type: library in Chart.yaml;
4. Chart Lifecycle
1. Create    → helm create mychart
2. Develop   → Edit templates and values
3. Lint      → helm lint mychart
4. Package   → helm package mychart (creates mychart-0.1.0.tgz)
5. Publish   → Upload to repository
6. Install   → helm install myapp mychart-0.1.0.tgz
7. Upgrade   → helm upgrade myapp mychart-0.2.0.tgz
8. Rollback  → helm rollback myapp 1
9. Uninstall → helm uninstall myapp
5. Chart Naming Conventions
  • Chart name: lowercase, hyphens allowed (e.g., my-app);
  • Directory name: Must match chart name;
  • Package name: chartname-version.tgz (e.g., my-app-1.0.0.tgz);
  • Resource names: Use chart name as prefix for consistency;
6. Chart Versioning
  • Charts use Semantic Versioning (SemVer): MAJOR.MINOR.PATCH;
  • MAJOR: Breaking changes (e.g., 1.0.0 → 2.0.0);
  • MINOR: New features, backward compatible (e.g., 1.0.0 → 1.1.0);
  • PATCH: Bug fixes, backward compatible (e.g., 1.0.0 → 1.0.1);
# Chart.yaml
apiVersion: v2
name: myapp
version: 1.2.3  # Chart version
appVersion: "2.0.1"  # Application version
7. Chart vs Release vs Revision
Term Definition Example
Chart The package/template nginx-1.0.0.tgz
Release Instance of a chart in a cluster my-nginx (installed from nginx chart)
Revision Version of a release (increments on upgrade) Revision 1, 2, 3... 
# One chart can have multiple releases
helm install frontend nginx-1.0.0.tgz
helm install backend nginx-1.0.0.tgz

# Each release can have multiple revisions
helm upgrade frontend nginx-1.1.0.tgz  # Creates revision 2
helm upgrade frontend nginx-1.2.0.tgz  # Creates revision 3
8. Finding Charts

🌐 Artifact Hub (Official)

  • Central hub for Helm charts: artifacthub.io;
  • Search thousands of community charts;

📦 Popular Repositories

# Bitnami (most popular, well-maintained)
helm repo add bitnami https://charts.bitnami.com/bitnami

# Prometheus Community
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts

# Ingress NGINX
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx

# Search for charts
helm search repo mysql
helm search hub wordpress
9. Chart Best Practices
  • Use meaningful names: Chart and resource names should be descriptive;
  • Provide good defaults: Chart should work with minimal configuration;
  • Make it configurable: Expose important settings in values.yaml;
  • Document everything: README.md and NOTES.txt are essential;
  • Test thoroughly: Use helm lint and helm test;
  • Follow SemVer: Version charts correctly;
  • Keep it simple: Don't over-engineer templates;
10. Example: Simple Chart Structure
myapp/
├── Chart.yaml
│   apiVersion: v2
│   name: myapp
│   version: 1.0.0
│   appVersion: "1.0"
│
├── values.yaml
│   replicaCount: 2
│   image:
│     repository: nginx
│     tag: "1.21"
│
└── templates/
    ├── deployment.yaml
    │   apiVersion: apps/v1
    │   kind: Deployment
    │   metadata:
    │     name: {{ .Release.Name }}
    │   spec:
    │     replicas: {{ .Values.replicaCount }}
    │
    └── service.yaml
        apiVersion: v1
        kind: Service
        metadata:
          name: {{ .Release.Name }}
