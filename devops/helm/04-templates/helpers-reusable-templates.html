Helpers and Reusable Templates

1. What is _helpers.tpl?
  • A file in templates/ that contains named template definitions (also called "partials" or "helpers");
  • Files starting with _ are processed by the template engine but do not produce any Kubernetes manifest output on their own;
  • Other templates call these named templates via include or template;
  • Convention: name helpers with the chart name prefix (e.g., myapp.fullname) to avoid collisions with sub-charts;
2. define — Declaring a Named Template
  • Syntax: 
    {{- define "templateName" -}}
  ... template body ...
{{- end -}}
  • The body can contain any valid Go template code — it receives a context (passed when called);
  • Multiple define blocks can exist in the same file;
3. include vs template
  • Both call a named template, but they differ in how the output is handled:
    includetemplate
    ReturnsA stringDirectly inserts output (not a string)
    PipeableYes — can pipe to nindent, quote, etc.No — cannot be piped
    RecommendedYesAvoid — use include instead
  • Example showing why include is preferred: 
    # With include — works: output can be piped to nindent
labels:
  {{- include "myapp.labels" . | nindent 2 }}

# With template — BREAKS: cannot pipe the output
labels:
  {{ template "myapp.labels" . }}
  # output is not indented → invalid YAML
4. Standard Helpers — Chart Name
  • Returns the chart name, optionally overridden via .Values.nameOverride: 
    {{- define "myapp.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}

# Usage:
app.kubernetes.io/name: {{ include "myapp.name" . }}
  • trunc 63 — Kubernetes names are limited to 63 characters;
  • trimSuffix "-" — avoid trailing hyphens after truncation;
5. Standard Helpers — Full Name
  • Generates <release>-<chart>, with override support: 
    {{- define "myapp.fullname" -}}
{{- if .Values.fullnameOverride }}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- $name := default .Chart.Name .Values.nameOverride }}
{{- if contains $name .Release.Name }}
{{- .Release.Name | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" }}
{{- end }}
{{- end }}
{{- end }}

# Usage:
metadata:
  name: {{ include "myapp.fullname" . }}
  • Avoids names like myapp-myapp when the release name already contains the chart name;
6. Standard Helpers — Labels
  • Common labels applied to every resource for identification and management: 
    {{- define "myapp.labels" -}}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" | trunc 63 }}
app.kubernetes.io/name: {{ include "myapp.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}

# Usage in any resource:
metadata:
  labels:
    {{- include "myapp.labels" . | nindent 4 }}
7. Standard Helpers — Selector Labels
  • A subset of labels used for matchLabels in Deployments and Services — must be immutable across upgrades: 
    {{- define "myapp.selectorLabels" -}}
app.kubernetes.io/name: {{ include "myapp.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}

# Usage in Deployment:
spec:
  selector:
    matchLabels:
      {{- include "myapp.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "myapp.selectorLabels" . | nindent 8 }}

# Usage in Service:
spec:
  selector:
    {{- include "myapp.selectorLabels" . | nindent 4 }}
  • Never include version-dependent fields in selector labels — they cannot change after creation;
8. Standard Helpers — Chart Label
  • Identifies the chart version used to create the resource: 
    {{- define "myapp.chart" -}}
{{- printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" | trunc 63 | trimSuffix "-" }}
{{- end }}

# Output: myapp-0.1.0
  • replace "+" "_" — SemVer allows + in build metadata but + is not valid in label values;
9. Standard Helpers — ServiceAccount Name
  • {{- define "myapp.serviceAccountName" -}}
{{- if .Values.serviceAccount.create }}
{{- default (include "myapp.fullname" .) .Values.serviceAccount.name }}
{{- else }}
{{- default "default" .Values.serviceAccount.name }}
{{- end }}
{{- end }}

# values.yaml
serviceAccount:
  create: true
  name: ""       # empty → uses fullname
  # name: "my-sa" # explicit → uses this

# Usage:
serviceAccountName: {{ include "myapp.serviceAccountName" . }}
10. Custom Helpers — Passing Data with dict
  • Pass custom data to a helper using the dict function: 
    # _helpers.tpl
{{- define "myapp.container" -}}
- name: {{ .name }}
  image: "{{ .root.Values.image.registry }}/{{ .image }}:{{ .tag }}"
  ports:
    - containerPort: {{ .port }}
{{- end }}

# deployment.yaml
containers:
  {{- include "myapp.container" (dict
    "root" $
    "name" "app"
    "image" "myapp"
    "tag" .Values.image.tag
    "port" 8080
  ) | nindent 2 }}
11. tpl — Rendering Values as Templates
  • tpl renders a string through the template engine — useful when values.yaml contains Go template expressions: 
    # values.yaml
annotations:
  custom: "release={{ .Release.Name }}"

# template — without tpl, the value is literal text:
annotations:
  custom: {{ .Values.annotations.custom }}
# Output: custom: "release={{ .Release.Name }}"  ← NOT rendered

# template — with tpl, the value is rendered:
annotations:
  custom: {{ tpl .Values.annotations.custom . }}
# Output: custom: release=myrelease  ← rendered correctly
  • Use with caution — allows users to inject arbitrary template code via values;
