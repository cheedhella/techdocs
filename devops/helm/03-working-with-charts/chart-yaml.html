Chart.yaml Explained

1. What is Chart.yaml?
  • The Chart.yaml file is the main descriptor for a Helm chart;
  • Contains metadata about the chart: name, version, description, dependencies;
  • Required for every Helm chart;
  • Must be valid YAML format;
2. Complete Chart.yaml Example
apiVersion: v2
name: myapp
version: 1.2.3
appVersion: "2.0.1"
description: A comprehensive Helm chart for my application
type: application
keywords:
  - web
  - backend
  - microservice
home: https://myapp.example.com
sources:
  - https://github.com/myorg/myapp
  - https://github.com/myorg/myapp-chart
maintainers:
  - name: John Doe
    email: john@example.com
    url: https://github.com/johndoe
  - name: Jane Smith
    email: jane@example.com
icon: https://example.com/images/myapp-icon.png
deprecated: false
kubeVersion: ">=1.20.0 <1.28.0"
dependencies:
  - name: mysql
    version: "9.3.4"
    repository: https://charts.bitnami.com/bitnami
    condition: mysql.enabled
  - name: redis
    version: "17.3.7"
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled
annotations:
  category: ApplicationServer
  licenses: Apache-2.0
3. Required Fields
Field Description Example
apiVersion Chart API version (v2 for Helm 3) v2
name Chart name (must match directory name) myapp
version Chart version (SemVer) 1.0.0
4. Optional Fields
Field Description
appVersion Version of the application being deployed
description One-sentence description of the chart
type application or library
keywords List of keywords for searching
home URL of the project home page
sources List of URLs to source code
maintainers List of maintainers with contact info
icon URL to an SVG or PNG image icon
deprecated Mark chart as deprecated
kubeVersion Compatible Kubernetes versions
dependencies List of chart dependencies
annotations Additional metadata
5. version vs appVersion
  • version: Version of the chart itself (template changes, value changes);
  • appVersion: Version of the application being deployed;
# Example: Updating nginx version
# Chart v1.0.0, App v1.20
version: 1.0.0
appVersion: "1.20"

# Chart unchanged, but app updated
# Chart v1.0.0, App v1.21
version: 1.0.0
appVersion: "1.21"

# Chart template changed, app same
# Chart v1.1.0, App v1.21
version: 1.1.0
appVersion: "1.21"
6. Chart Type

application (default):

  • Standard installable chart;
  • Contains templates that render Kubernetes resources;

library:

  • Provides reusable template helpers;
  • Cannot be installed directly;
  • Used as a dependency by other charts;
# Library chart
apiVersion: v2
name: common-helpers
type: library
version: 1.0.0
7. Kubernetes Version Constraints
# Exact version
kubeVersion: "1.24.0"

# Minimum version
kubeVersion: ">=1.20.0"

# Version range
kubeVersion: ">=1.20.0 <1.28.0"

# Multiple constraints
kubeVersion: ">=1.20.0 <1.28.0 || >=1.29.0"
8. Dependencies
dependencies:
  - name: mysql
    version: "9.3.4"
    repository: https://charts.bitnami.com/bitnami
    condition: mysql.enabled
    tags:
      - database
    import-values:
      - data
    alias: db

  - name: redis
    version: "~17.3.0"
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled
9. Annotations

Custom metadata for tools and repositories:

annotations:
  category: Database
  licenses: Apache-2.0
  artifacthub.io/changes: |
    - kind: added
      description: Support for custom configurations
    - kind: fixed
      description: Fixed service port mapping
  artifacthub.io/links: |
    - name: Documentation
      url: https://docs.example.com
    - name: Support
      url: https://support.example.com
10. Deprecated Charts
apiVersion: v2
name: oldapp
version: 2.0.0
deprecated: true
description: This chart is deprecated. Use newapp instead.
11. Best Practices
  • Use SemVer: Follow semantic versioning for chart versions;
  • Update version on changes: Increment version whenever templates or values change;
  • Keep appVersion in sync: Update appVersion when deploying new application versions;
  • Provide good description: Clear, concise description helps users;
  • Add maintainers: Include contact information for support;
  • Specify kubeVersion: Prevent installation on incompatible clusters;
