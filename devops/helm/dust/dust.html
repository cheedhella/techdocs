Helm is a package manager that also happens to include templating capabilities. 
Unfortunately, a lot of people focus only on the usage of Helm as a template manager and nothing else.
Technically Helm can be used as only a templating engine by stopping the deployment process in the manifest level. 
It is perfectly possible to use Helm only to create plain Kubernetes manifests and then install them on the cluster using the standard methods (such as kubectl). 
But then you miss all the advantages of Helm (especially the application registry aspect).
At the time of writing Helm is the only package manager for Kubernetes, so if you want a way to group your manifests and a registry of your running applications, there are no off-the-shelf alternative apart from Helm.

helm history and rollback
	release statuses
		- pending-install -> manifests are generated, but not sent to k8s yet;
		- deployed -> manifests are sent to k8s and are accepted; k8s started deploying the applicaiton; it doesn't mean the application is ready;
		- pending-upgrade -> upgrade manifests are generated, but not sent to k8s yet;
		- superseded -> status changes to superseded, when the upgrade is completed successfully;
		- pending-rollback -> 
		- uninstalling -> when you uninstall a release, it's status changes immediately to uninstalling, while the process is going on; 		
		- uninstalled -> once uninstall is completed, it's status changes to uninstalled;
		- failed -> status changes to failed, ONLY if k8s rejects the manifest files sent by helm for any operation;

	Say, when the status is failed, if you want to find what went wrong?
		helm history nginx01 	# you can examine all the previous releases
		# since the status is failed, you can either upgrade to another release or rollback to one of the previous releases;
		# rollback
		helm rollback nginx01 1 		# It adds new revision to history
		helm uninstall nginx01 			# it delete the revision history
		helm uninstall nginx01 --keep-history 			# it keeps the history, so that you can revert uninstall as well

Tips useful when installing or upgrading a helm release
	1. auto-generate release name
		If you are running helm through a script like ansible or terraform OR if you are deploying it through CI/CD server like jenkins, you would have
		to generate a unique name for each release;
		Way #1
			One simple way of doing this is: create a random string in bash like this;
			export RELEASE_SUFFIX=$(tr -dc a-z0-9 < /dev/urandom | head -c 13 ; echo)
			helm install nginx-$RELEASE_SUFFIX bitnami/nginx
		Way #2
			Fortunately, helm already has a flag that does exactly same as this;
			helm install bitnami/nginx --generate-name

	2. auto-generate namespace
		If you use a namespace that doesn't exist yet, 
		helm install nginx01 -n apps bitmani/nginx 		# It will fail, as apps namespace doesn't exist;

		Obviously, we can add namespace creation step to the deployment script; But, helm has a shortcut for this;
		helm install nginx01 -n apps bitmani/nginx --create-namespace

	3. install the release or upgrade it if it already exists
		As soon as the developers make their code to the GIT repository, it automatically triggers the appropriate build pipeline;
		After validating the input and doing all relevant tests, build server attempts to deploy the changes to configured environment;
		But, what if this is not the first time the pipeline runs and a release with specified name already exists?
		Fortunately, helm already has a flag for doing this;
			helm upgrade --install nginx01 --set service.port=8080 bitname/nginx

	4. verify that the application is running
		helm marks the release as deployed, it doesn't necessary mean that application is properly running;
		status is still deployed, if the pod fails to run; 
		In the CICD pipeline, it require an extra step to verify that the application is indeed upgraded;
		But, helm has a workaround for it;
		--wait flag not only ensures that API server accepted the mainfest but it also wait until new pods are in running state;
		By default, helm will wait for 300secs or 5 minutes before timing out;
		We can override the timeout value, by passing: --timeout 10s
		Usually pods take some time to be ready due to environment issues such as large image size, slow network etc;
		You are adivsed to set the time out value to a reasonable time period;

	If you install a chart directly using helm install, then it could cause a issue;
	Over the time, any thing could happen to that chart; Over the time, if you decide to move another cloud provider, you may not be able find same chart;

	> helm install <name> ./kube-prometheus-stack 						# Instruct helm to use local chart, not remote chart;

	> touch myvalues.yaml 												# Create a file for overrides;

	> helm upgrade <name> ./kube-prometheus-stack  --values=myvalues.yaml

What is Template?
	Template files are used to specify what resources to be created on the k8s cluster;
	Place holders in the template files are replaced with values in the values.yaml and generated yaml is sent to k8s API server;
	Helm uses text template engine in the GO programming language;

heml template -> This is command is used to generate the yaml spec that is sent to k8s; It doesn't validate the generated yaml with k8s API server;
	helm install/upgrade --dry-run VS helm template
		- dry run validates the syntax and schema of yaml files, where as template command only validates the syntax;
		  For eg, If you remove a brace in one of the yaml files, both dry-run and template catches it;
		          If you remove kind property from one of the yaml files, only dry-run catches it;

Actions
	- They start with {{ and end with }}
	- They are used to define variables, conditional logic, using loops, invoking function etc;
	- Anything outside action is rendered as is to the final yaml file that is sent to k8s API server;
	- {{-  -> is used to remove the leading spaces in the generated text;
	- -}}  -> is used to remove the trailing spaces in the generated text;
	- Examples:
		{{ .Values.autoscaling.enabled }} 			-> Output the values of autoscling.enabled in values.yaml;
		{{ .Chart.Name }} 							-> Name of chart, as defined in Chart.yaml;
		{{ .Release.Name }} 						-> Release name;
		{{ .Release.Namespace }} 					-> namespace;
		{{ .Release.IsInstall }} 					-> Is installation;
		{{ .Release.IsUpgrade }} 					-> Is upgrade;
		{{ .Release.Service }} 						-> Helm;
		{{ .Template.Name }} 						-> Name of template that is currently rendered;
		{{ .Template.BasePath }} 					-> 

pipe
	- It is used chain multiple commands; Output of the command on LHS will be passed to the command on RHS;
	- Eg: 
		{{- include "firstchart.fullname" . | nindent 4 }}

functions

What is Helm?
	It is a package manager for k8s;

What is a Package Manager?
	It enables you to install/upgrade/uninstall a wide range of software packages with a simple command;
	For eg, brew is a package manager for MacOS; yum is a package manager for Linux; npm is the package manager for Node JS applications;

What is Chart?
	In helm world, charts are nothing but packages; Internally, it is a directory containing all files that are needed to install the application in the k8s cluster;

Why Helm?
	Advantage #1:
		Imagine you are working on k8s cluster - doesn't matter if it is running on AWS or minikube and you have been given the job of installing a database in your cluster;
		
		Without helm package manager, you have to find a MySQL docker image, identify the best configuration(like ports, requests, limits etc) for MySQL, write 
		yaml files for Pods, Deployment, stateful sets, daemon set etc; If you are not a MySQL expert and if you feel it difficult, helm offers a solution;

		If you have helm installed, it as simple as running a command: helm install mysql;
		Helm will download a standard set of yaml and that will work as a great starting point for any MySQL installation in k8s;

	Advantage #2:
		As we install and update applications, k8s doesn't maintain any history of resources, unless you maintain history using GitHub;
		Helm maintains a history, it creates a new revision everytime you install/update; It also helps you in getting back to revision you want;

	Advantage #3: Dynamic configuration
		All yaml files created directly by us are static, they don't accept any values;
		Helm chart contains templates and values.yaml, which are used to generate final yaml that will be sent to k8s;
		Helm allows you to override the default specified in values.yaml;

	Advantage #4:
		Helm knows the order in which k8s resources should be created; 

	Advantage #5: Lifecycle hooks
		If there is any work that you want to do during install/upgrade/uninstall time, helm supports lifecycle hooks/events;

Helm Installation
	> brew install helm 		# It is written in GO, which means it is a self executable binary file; It doesn't need any dependencies to work;
								# Having a k8s cluster is a prerequisite to it, as it is intended to work with a k8s cluster; 

How does helm know about the k8s cluster?
	Helm uses the same config file(.kube/config), which kubectl command uses;
	If you don't want helm to use that file, you can always override it by setting KUBECONFIG environment variable;
