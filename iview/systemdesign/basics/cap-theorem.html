1. What is CAP Theorem?
  • Proposed by Eric Brewer, it states that a distributed system can only provide two out of the following three guarantees:
  • C - Consistency: Every read receives the most recent write or an error.
  • A - Availability: Every request receives a (non-error) response, without the guarantee that it contains the most recent write.
  • P - Partition Tolerance: The system continues to operate despite an arbitrary number of messages being dropped (or delayed) by the network between nodes.
2. The Trade-off
  • In a distributed system, network partitions (P) are inevitable. Therefore, you must choose between Consistency (C) and Availability (A).
3. CAP Combinations
  • CP (Consistency + Partition Tolerance): The system returns an error or times out if it cannot guarantee consistency during a partition. (e.g., MongoDB, HBase, Redis).
  • AP (Availability + Partition Tolerance): The system remains available but might return stale data. (e.g., Cassandra, DynamoDB, CouchDB).
  • CA (Consistency + Availability): Possible only in non-distributed systems (single node) where partitions don't happen. (e.g., Traditional RDBMS like MySQL/Postgres on a single server).
4. PACELC Theorem
  • An extension of CAP. If there is a Partition (P), choose between Availability (A) and Consistency (C); Else (E), when the system is running normally, choose between Latency (L) and Consistency (C).
