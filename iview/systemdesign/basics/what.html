1. What is System Design?
  • It is the process of defining how different parts of a software system interact to meet both functional (what it should do) and non-functional (how well it should do it) requirements;
2. Why is System Design Important?
  • Without a deliberate architectural strategy, an application that works for 1,000 users will likely fail under the load of 1,000,000 (a million) users.
  • System design is the process of defining the components, their integration, data model, API of a distributed system, that meets specified functional and non-functional requirements;
Scalability: The ability to handle massive user loads by distributing requests so no single server is overwhelmed. Availability: Ensuring the system remains operational and accessible to users even if some of its components crash. Low latency: Responding to user requests quickly, regardless of their location, to create a fast and responsive experience. Consistency: Making sure data is reliable and accurate across the entire distributed system.
3. System Design Process
  • Requirements Gathering
    1. Identify functional requirements - what the system should do;
    2. Identify non-functional requirements - scalability, availability, latency, consistency etc;
    3. Identify stakeholders - who are the users of the system, who are the developers of the system, who are the operators of the system, who are the maintainers of the system etc;
  • Estimate Scale of the System
    1. Data size (storage requirements)
    2. Queries per second (QPS) or requests per second (RPS)
    3. Bandwidth needs
    4. Number of servers or instances required
  • High Level Design
    1. Main services and their interactions;
    2. External dependencies;
  • Data Design
    1. Once the architecture is clear, move closer to the data and interfaces;
    2. Choose the right database type(s) — relational, NoSQL, time-series, etc;
    3. Define schemas, tables, and relationships to support your use cases
    4. Design APIs for interaction between services (e.g., POST /tweet, GET /timeline).
    • What building blocks the system will use (clients, services, databases, caches, queues, CDNs). How those blocks interact (APIs, communication patterns, data flow). How the system behaves at scale (traffic spikes, failures, slow networks, regional outages). Which trade-offs do we accept (cost vs. reliability, latency vs. consistency, simplicity vs. flexibility)?
  • Detailed Design Zoom into each component and define: Internal logic, caching, and concurrency handling Scaling strategies (horizontal vs vertical scaling) Replication, partitioning, and fault tolerance This is also where you address non-functional requirements (NFRs) like availability, reliability, and latency. In other words, you go from what the system does to how it does it.
  • Scaling Strategy
    1. Horizontal scaling;
    2. Vertical scaling;
    3. Load balancing;
    4. Caching;
    5. Replication;
  • Bottlenecks and Trade-offs No system is perfect. Every choice has trade-offs.
    1. Identify bottlenecks;
    2. Identify trade-offs;
    3. Identify solutions;
  • Single Point of Failure
    1. Identify single points of failure;
    2. Identify solutions;
    3. Identify trade-offs;
  • Latency Issues
    1. Identify latency issues;
    2. Identify solutions;
    3. Identify trade-offs;
  • Cost vs Performance
    1. Identify cost vs performance;
    2. Identify solutions;
    3. Identify trade-offs;
On a high level, system design revolves around answering these 10 big questions: Scalability: How will the system handle a large number of users or requests simultaneously? Latency and Performance: How can we reduce response time and ensure low-latency performance under load? Communication: How do different components of the system interact with each other? Data Management: How should we store, retrieve, and manage data efficiently? Fault Tolerance and Reliability: What happens if a part of the system crashes or becomes unreachable? Security: How do we protect the system against threats such as unauthorized access, data breaches, or denial-of-service attacks? Maintainability and Extensibility: How easy is it to maintain, monitor, debug, and evolve the system over time? Cost Efficiency: How can we balance performance with infrastructure cost? Observability and Monitoring: How do we monitor system health and diagnose issues in production? Compliance and Privacy: Are we complying with relevant laws and regulations (e.g., GDPR, HIPAA)? When building a product or a feature there is no prize for guessing what happens if an individual or team entirely skips the design process or only design at a high level. Sooner or later, they will have to get back to the drawing board and design it again! Some examples of components are Zookeeper, Redis, Kafka, Amazon S3, Azure AI service, etc. These are high-level components of the system being designed. Again based on the system, a load-balancer may be required or not. Other examples of components can be — proxies, cache, rate limiting, databases, messaging systems, etc. If you consider Instagram feed, for example, the availability of a set of feeds when a user opens the app is a key characteristic of Instagram. If the user sees a blank feed or outlines of just 2–3 entries, the engagement drops soon. Likewise, each system has a set of key characteristics and the system designer should keep these in mind when designing the system.
