Problem Statement
	Design a short URL service like TinyURL, Bit.ly;
	They generate short URL for every long URL and store the mappings;
	When user access a short URL, it takes the request, finds the long URL and redirects the user to long URL;

Why is this needed?
	Twitter has a limit on the number of characters in a tweet;
	So, if you shorten a URL that you want to tweet, you will have more space for your tweet;
	-----
	In addition, tiny URL service can provide analytics, like how many times a link has been clicked;

Functional Requirements
	- Convert a long URL to short URL;
	- When an user access short URL, fetch the long URL and redirect the user to long URL;
	- Short URLs could have a expire time, possibly with a system choosen default;

Non-Functional Requirements
	- Fast -> URL redirection should happen in real-time with minimal latency;
	- Scalable -> should be easily scalable, so that it handles ever increasing requests;
	- Highly available -> System should be highly available b/c, if our service is down, all the URL redirections will start failing;

Extended Requirements
	- Allow user to choose custom short URL for a long URL;
	- Expose API for generating short URL for a long URL;
	- Analytics, how many times a redirection happened?

------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Basic functionality is quite straightforward;
	- User enters the long URL in TinyURL service, which shortens it and saves it to the DB(Primary Key -> short URL); User is also provided with the short URL;
	- How does the retrieving works?
		When someone types the short URL such as bit.ly/2UWIXp4, bit.ly takes the request and finds the long URL corresponding to 2UWIXp4 and redirects the user to long URL;
	- So, this is pretty straight forward;

	- We can go with either SQL or NoSQL DB, as the format of data is pretty simple; // Short_URL, Long_URL, Number_Of_Clicks, Expriry;
	  If you use SQL Db, you could use a distributed cache;
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
How is the 7 character shortened URL is generated?
	Short URL could have 7 characters, out of: 0-9, a-z, A-Z; // 10 + 26 + 26 = 62 chars; Eg: 2UWIXp4
	So, you could have 62^7, which is around 3.5 trillion short urls, which is equal to 2^42; So, it could be 42-bit or 7-byte short url;
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
All looks good! But, what if there is massive increase in the number of new short URLs and if you could reach the 3.5 trillion limit?
	Just using a Auto Scaling group is not going to solve the problem, b/c it would end up wrongly having same short URL for 2 different long URLs;

So, this system design is bit different; There are 3 approaches to solve this:
	Approach #1:
		- You could increase the length of the short URL; So, for every byte you increase, you could increase the number of combinations possible;
		- You could use a Randomizer;

	Approach #2:
		input of any length -> Hash Function such as MD5 -> fixed size string;
		It generates one unique output, for every unique input; 2 different strings can't produce same output;
		It produces 128-bit output from an arbitary length string;

		But, size of shorturl is only 42-bit, but MD5s is producing 128-bit;
		Take the first 42-bits of the output, convert it to 7 characters;
		Encode it using base62;

MD5 Hashing Algorithm
	When you send a file over the internet, how do you know that everything arrived in one piece? 
	Should you call the recipient to make sure, and compare the file they received to the one you sent? 
	Thanks to the MD5 hashing algorithm, you don’t have to.

	How it works?
		The MD5 hashing algorithm converts data into a string of 32 characters. 
		For example, the word “frog” always generates this hash: 938c2cc0dcc05f2b68c4287040cfcf71. 
		Similarly, a file of 1.2 GB also generates a hash with the same number of characters. 
		When you send that file to someone, their computer authenticates its hash to ensure it matches the one you sent.
		If you change just one bit in a file, no matter how large the file is, the hash output will be completely and irreversibly changed. 
		Nothing less than an exact copy will pass the MD5 test.

		The MD5 length will always be the same: a 128-bit or 16 bytes or or 32 hexadecimal digits(0-9a-f);
		MD5("The quick brown fox jumps over the lazy dog.") = e4d909c290d0fb1ca068ffaddf22cbd0


		When security isn’t a concern, MD5 is sufficient, and it’s still a great option for data verification.

SHA 
	SHA (Secure Hash Algorithm) addresses MD5’s vulnerabilities, giving new life to the security applications of hash algorithms. 
	SHA outputs a longer string of hexadecimal characters, so you can easily tell the difference between the two types. 
	This is a big reason why SHA is more secure, because a greater number of bits increases complexity exponentially.

	Secure websites usually have an SSL certificate. 
	SSL (Secure Socket Layer) encrypts data moving between you and the website you’re using, and it does so with SHA-256. 
	If you want even greater security and data encryption, use a VPN.

The TinyURL homepage includes a form which is used to submit a long URL for shortening. For each URL entered, the server adds a new alias in its hashed database and returns a short URL. According to the website, the shortened URLs will never expire.

TinyURL offers an API which allows applications to automatically create short URLs. This is done by simply reading the result returned from tinyurl.com/api-create.php?url=URLENCODED_SOURCE_URL.

Short URL aliases are seen as useful because they are easier to write down, remember or distribute. 


Starting in 2008, TinyURL allowed users to create custom, more meaningful aliases. This means that a user can create descriptive URLs rather than a randomly generated address.

SQL vs NoSQL DB
	SQL - RDBMS such as Oracle, Postgres; 
	NoSQL - MongoDB, Cassandra, Redis, Hbase etc;

https://www.educative.io/collection/page/5668639101419520/5649050225344512/5728116278296576/

	SQL databases are vertically scalable, while NoSQL databases are horizontally scalable. SQL databases are table-based, while NoSQL databases are document, key-value, graph, or wide-column stores. SQL databases are better for multi-row transactions, while NoSQL is better for unstructured data like documents or JSON.
	NoSQL database provides a mechanism for storage and retrieval of data that is modelled other than tabular form. 
	It is not limited to storing data in tables, instead, enables the big data to be stored in the structured, unstructured, semi-structured or polymorphic form. 
	Companies like Twitter and Google, with a tremendous amount of data set like the user data of the social platforms, prefer to use NoSQL over any other RDBMS. 

Features of NoSQL
NoSQL has higher scalability than other database management systems
Schema Free: You do not need to define the schema of the database before storing the data onto the system. 
NoSQL allows the distribution of data on more than just one device. 
With NoSQL Database, you do not require specialized or complex hardware or storage solutions.
Does not require data normalization
Simple API for easy user interfaces
Can store unstructured, semi-structured, or structured data. 

Vertically Scalable  (Add resources to increase the capacity of the existing hardware and software).	
Horizontally Scalable (Changing small nodes with larger nodes to increase the capacity of the existing hardware and software).

SQL enables ACID(atomicity, consistency, isolation, and durability) properties	NonSQL follows CAP (consistency, availability, partition tolerance) properties.
