    • SQL Databases
    • Things are simple when we store all our data in a single database machine;
    • But, when a single machine is not enough, we need to introduce more machines and split data between them;
    • This procedure is called Sharding or horizontal Partitioning;
    • Each shard stores a subset of all the data;
    • Because we have several machines, services that talk to the database need to know how many machines exist and which one to pick to store and retrieve the data;
    • We discussed before that, we have processing service that stores data in the database and query service that retrieves data from the database;
    • We could have made both of these services to call every database machine directly;
    • A better option is introduce a light weight proxy server that knows about all database servers and routes traffic to the correct shard;
    • Now, both processing and query services can talk to proxy only; They don't need to know about each and every database machine anymore; But, cluster proxy has to know;
    • Moreover, proxy needs to know when some shard dies or become unavailable due to network partition;
    • If a new shard has been added to database cluster, proxy need to know about it;
    • How do we achieve it?
    • We introduce a new component called configuration-service;
    • configuration-service maintains a health check connection to all shards; So, it always knows what database machines are available;
    • So, cluster proxy calls a particular shard;
    • Instead of calling database instance directly, we can introduce one more proxy - shard-proxy, that sits in front of the database;
    • Shard proxy will help us in many different ways: it can cache query results, monitor database instance health, publish metrics, terminate queries that take too long to return data and many more;
    • Great! This setup will help us to address requirements such as: scalability and performance;
    • But, availability is not yet addressed;
    • What if database shard is dies? How to make sure data is not lost?
    • Answer is replicate the data;
    • Let's call each existing shard a master shard or a leader;
    • For every master shard, we introduce a copy of it, called replica or follower or read replica;
    • We call it read replica b/c writes still go through a master shard, but reads may go through both master or follower;
    • We also put some replicas to a different datacenter than the master shard, so that if the whole data center goes down, we still have a copy of the data available;
    • So, when store data request comes, based on the information provided by configuration-service, cluster proxy sends data a shard;
    • Data is either synchronously or asynchronously replicated to a corresponding read replica;
    • When read data request comes, cluster proxy may retrieve data either from a master or replica;

    • Push or Pull?
    • Push means other service sends the events synchronously to the processing service;
    • Pull means processing service pull events from some temporary storage;
    • Although, the answer is that, both options are totally valid, and we can make both work, pull option has more advantages;
    • As it provides better support for fault-tolerant, and easier to scale;
    • For eg, we have 2 users opening 2 different videos A and B;
    • processing-service updates the counter in-memory and returns successful response back to the clients and the machine crashes without sending this data to the database; Data is lost!
    • In case of pull approach, events generated are stored in a temporary storage first;
    • processing-service machine pulls the events and updates in-memory counters; If the machine crashes, we still have events in the storage and can re-process them;
    • Checkpointing
    • Here we have temporary storage and as you may see, I intentionally draw it as a queue;
    • Because, when events arrive, we put them into storage in order, one by one;
    • Fixed order allows us to assign an offset for each event in the storage;
    • This offset indicates event position in the sequence;
    • Events are consumed always sequentially;
    • Everytime an event is read from the storage, the current offset moves forward;
    • After we processed several events and successfully stored them in the database, we write checkpoint to some persistent storage;
    • If processign service machine fails, it will be replaced with another one and this new machine will resume processing where the failed machine left off;
    • It is very important concept in stream data processing;
    • Partitioning
    • We already discussed it when we talked about databases;
    • Main idea remains same when applied to stream data processing;
    • Instead of putting all events in a single queue, let's have several queues;
    • Each queue is independant from the others;
    • Every queue physically lives on it's own machine and stores a subset of all the events;
    • For eg, we compute a hash based on video identifier and use this hash number to pick a queue;
    • As you may see, partitioning allows us to parallelize events processing;
    • More the events we get, we create more partitions;
    • Processign Service

    • To achieve this we use a cache that stores unique event identifiers, for say last 10 minutes;
    • If several identical messages arrive within 10 minutes interval, only one of them(the first one) will be processed;

    • Periodically, we stop writing to the current hashtable and create a new one;
    • A new hashtable keeps accumulating incoming data;
    • While old hashtable is no longer counting any data and each counter from the old hashtable is sent to the internal queue for further processing;

    • blocking vs non-blocking IO
    • When client makes a request to the server, server processes the request and sends back a response;
    • Client intiates the connection by using sockets;
    • When client makes a request, socket that handles the connection on the server side is blocked;
    • This happens within a single execution thread;
    • So, the thread that handles that connection is blocked as well;
    • When another client sends a request at the same time, we need to create one more thread to process that request;
    • This is how blocking systems work;
    • They create one thread per connection;
    • Modern multi-core machines can handle hundreds of concurrent connections each;
    • But, let's say server starts to experience a slow down and number of active connections and thread increases.
    • When this happens, machines can go into death spiral and the whole cluster of machines may die;
    • Remember, we designed rate limiter in one of the previous videos;
    • This is exactly why we need rate limiting solution, to help to keep the systems stable during traffic peeks;
    • Alternative to blocking IO is non-blocking IO;
    • When we can use a single thread on the server side to handle multiple concurrent connections;
    • Server just queues the request and the actual IO is processed at some point later;
    • Piling up requests in the queue are far less expensive than piling up threads;
    • Non-blocking systems are more efficient and as a result has high throughput;
    • You may be wondering, if non-blocking systems are so great, why we still have so many blocking systems out there?
    • Because, everythign has a price!
    • The price of non-blocking systems increased complexity of operations;
    • Blocking systems are easy to debug and this is a big deal!
    • In blocking systems we have a thread per request, and we can easily track progress of the request, by looking into the thread stack;
    • Exceptions pop up the stack and it is easy to catch and handle them!
    • We can use thread local variables in blocking systems;
    • All these familar concepts either don't work at all OR work differently in non-blcoking world;
    • Moving on to batching and buffering, there are thousands of video events happening on youtube every second;
    • To process all these requests, API gateway has to be big in size; thousands of machines;
    • If we then pass each individual event to the paritioner service, partiioner service cluster of machines has to be big as well;
    • This is not efficient!
    • we somehow combine events together and send several of them in a single request to the partitioner service;
    • This is what batching is about!
    • Instead of sending each event individually, we first put events into a buffer.
    • We can then wait upto several seconds before sending buffer's content or until batch fills up, whichever comes first;
    • There are many benefits of batching:
    • It increases throughput and it helps to save on cost, request compression is more effective;
    • But, there are drawbacks as well!
    • It introduces some complexity both on the client and server side;
    • For eg, think of a scenario when a partitioner service processes a batch request and several events from the batch fail, while other succeed;
    • Should we resend the whole batch? or only failed events? what do you think?
    • The next concept is timeouts!
    • Timeouts define how much time a client is willing to wait for a response from the server;
    • We have 2 timeouts: connection timeout and request timeout;
    • Connection timeout defines how much time a client is willing to wait a connection to establish;
    • Usually this value is relatively small, tens of milliseconds;
    • Because, we only try to establish a connection, no heavy request processing is happening just yet;
    • Request timeout happens when request processing takes too much time, and a client is not willing to wait any longer;
    • To choose a request timeout value, we need to analyze latency percentiles;
    • For eg, we measure latency of 1% of the slowest requests in the system and set this value as a request timeout;
    • It means that about 1% of requests in the system will timeout;
    • What should we do with these failed requests?
    • Let's retry them;
    • May be we just hit a bad server machien with the first request;
    • The second attempt may hit a different machine, increasing our chances to succeed;
    • But, we shold be smart when we retry!
    • Because, if all clients retry at the same time or do it aggressively, we may create a so-called retry strom event and overload the server with too many requests;
    • To prevent this, we should use exponential backoff and jitter algorithms;
    • exponential backoff algorithm increases the waiting time between retries upto a maximum backoff time;
    • We retry requests several times, but wait a bit longer with every retry attempt;
    • and jitter adds randomness to retry intervals to spread out the load;
    • If we don't add jitter, backoff algorithm will retry the requests at the same time;
    • Jitter helps to spread out the retries;
    • Using exponential backoff and jitter, we may still be in the danger of too many retries;
    • For eg, when the paritioner service is down or degraded, and majority of the requests are retried;
    • The circuit breaker pattern stops a cilent from repeatedly trying to execute an operation, that is likely to fail;
    • we simply calculate howmany requests have failed recently and if the error threshold is exceeded we stop calling a downstream service;
    • Some time later, limited number of requests from the client are allowed to pass through and invoke the operation;
    • If these requests are successful, it's assumed that the fault that was previously causing the failure has been fixed;
    • We allow all requests at this point and and start counting failed requests from scratch; The loop completes;
    • The circuit breaker pattern also has drawbacks;
    • It makes the system more difficult to test;
    • It may be hard to properly set error threshold and timers;

    • None of these concepts are a silver bullet!
    • This is true for almost all concepts in distributed systems;

    • Let's now talk about load balancing!
    • Load balancing is a big topic, we will consider only selected concepts;
    • As you know, load balancers distribute data traffic between multiple servers;
    • There are 2 types of load balancers: hardware and software;
    • Hardware load balancers are network devices that we buy from known organizations;
    • These are powerful machiens with many CPU cores, memory and they are optimized to handle very high throughput;
    • Millions of requests per second;
    • Software load balancer is only software that we install on hardware we choose;
    • We don't need big fancy machines, and many software load balancers are open source;
    • Load balancers are provided by public clouds(for eg ELB from AWS);
    • Another gradation of software load balancers is what traffic they sever: TCP or HTTP;
    • It is a bit more complicated than that, but I don't want to overload you with terminology too much;
    • Let's keep things simple for now!
    • TCP load balancers are simply forward network packets without inspecting the content of the packets;
    • Think of it as if we established a single end-to-end TCP connection between a client and a server;
    • This allows TCP load balancers to be super fast and handle millions of requests per second;
    • HTTP load balancers, on contrast, terminate the connection;
    • Load balancer gets an HTTP request from a client, establishes a connection to the server and sends the request to this server;
    • HTTP load balancer can look inside a message and make a load balancing decision based on the content of the message;
    • For eg, based on the cookie information or a header;
    • Load balancers may use several algorithms to distribute the load;
    • Round robin algorithm distributes requests in order across the list of servers;
    • Least connections algorithm sends requests to the server with the lowest number of active connections;
    • Least response time algorithm sends requests to the server with fastest response time;
    • Hash based algorithms distributes requests based on a key we define, such as client IP address or URL;
    • Ok, you got it, there are many benefits of using load balancers;
    • How does partitioning service client knows about load balancer?
    • How does load balancer knows about partitioner service machines?
    • How does load balancer guarantee high availability? Because, it look like a single point of failure;
    • Here is where we should recall DNS, domain naming system;
    • DNS is like a phone book for the internet;
    • It maintains a directory of domain names and translates them into IP addresses;
    • We register our partitioner service in DNS, specify domain name, for example, partitionerservice.domain.com;
    • and associate it with IP address of the load balancer device;
    • So, when client hits domain name, requests are forwarded to the load balancer device;
    • So, when clients hit domain name, requests are forwarded to the load balancer device;
    • For the load balancer to know about partitioner service machines, we need to explicitly tell the load balancer the IP address of the each machine;
    • Both software and hardware load balancers provide APIs to register and unregister servers;
    • Load balancers need to know which server from the registerd list are healthy and which are unavailable at the moment;
    • This way load balancers ensure that traffic is routed to healthy servers only;
    • Load balancer pings each server periodically and if unhealthy server is identified, load balancer stops to send traffic to it;
    • It will then resume routing traffic to that server when it detects that the server is healthy again;
    • As for the high availability of load balancers, they utilize a concept of primary and secondary nodes;
    • The primary load balancer accepts connections and serves requests, while the secondary load balancer monitors the primary;
    • If, for any reason, the primary load balancer is unable to accept connections, the secondary one takes over;
    • Primary and secondary also live in different data centers, in case one data center goes.

    • But, what are partitions? Partition is also a webservice, that gets messages and stores them on disk in the form of append-only log file;
    • So, we have a totally ordered sequence of messages ordered by time;
    • This is not a single very large file, but a set of log files of the predefined size;
    • Paritioner service has to use some rule, partition strategy, that defines which partition gets what messages;
    • A simple strategy is to calculate a hash function based on some key, let's say video idnetifier and choose a machine based on this hash;
    • This simple strategy does not work very well with large scale;
    • As it may lead some thing called hot partitions;
    • For eg, when we have a very popular video or set of videos and all view events for them go to same partition;
    • One approach to deal with hot partitions is to include event time, for example in minutes, into partition key;
    • All video events within the current minute interval are forwarded to some partition;
    • Next minute, all events go to a different partition;
    • Within one minute interval, a single partition gets lot of data, but over several minutes data is spread more evenly among partitions;
    • Another solution to hot partitions problem is to split the hot partition into 2 new parttitions;
    • To get an idea how this approach works, remember consistent hashing algorithm and how adding a new node to the consistent hashing ring splits a range of keys into 2 new ranges;
    • and if to push this idea of partition split even further, we may explicitly allocate dedicated partitions for some popular video channels;
    • All video view events from such channels go to their allocated partitions;
    • and view events from other channels never go to those partitions;
    • These are the powerful techniques and there is little information on hot partitions topic on the internet;

    • Next important concept is replication;
    • We must not lose events when we store them in parittions;
    • So, when event is persisted in a partition, we need to replicate it;
    • If the partition machine goes down, events are not lost;
    • There are 3 main approaches to replication: single leader replication, multi leader replication, leaderless replication;

    • And only mention right now that multi leader replication is mostly used to replicate between several data centers;
    • So, which approach should we choose for partitions?
    • Lets go with single leader replciation; Each partition will have a leader and several followers;
    • We always write events and read them from the leader only;
    • While a leader stays alive, all followers copy events from their leader;
    • And if the leader dies, we choose a new leader from its followers;
    • The leader keeps track of it's followers: checks whether followers are alive and whether any of the followers are too far behind;
    • If a follower dies, gets struck, or falls behind, the leader will remove it from the list of it's followers;
    • Do you remember the concept of quorum write in cassandra?
    • We consider a write to be successful, when predefined number of replicas acknowledgement the write;
    • Similar concept applies to partitions;
    • When the parititoner service makes a call to partition, we may send response back as soon as leader partition persisted the message;
    • or only when a message was replicated to a specified number of replicas;
    • When we write to a leader only, we may still lose data if leader goes down before replication really happened;
    • When we wait for the repilcation to complete, we increase the durability of the system, but latency will increase;
    • Plus, if the required number of replicas are not available at the moment, availability will suffer;
    • Tradeoffs, as usual;
    • Next topic is the last topic: Lets talk about messge formats;
    • We an use either texual or binary formats for messages;
    • Popular textual formats are XML, CSV, JSON;
    • Popular binary formats are Thrift, Protocol, Buffers, Avro;
    • What's great about message format - they are human readable;
    • They are well known, widely supported and heavily used by many distributed systems;
    • But, for large scale real-time processing systems, biinary formats provide much more benefits;
    • Messages in binary format are more compact and faster to parse; and why is this?
    • As mentioned before, messages contain several attributes, such as video identifier, timestamp, user related information etc;
    • When represened in JSON format, for example, every message contains field names, which greatly increases total message size;
    • Binary formats are smarter;
    • Formats we mentioend before require a schema;
    • When schema is defined, we no longer need to keep field names;
    • For eg, apache thrift and protocol buffers use field tags instead of field names;
    • Tags are just numbers and they act like aliases for fields;
    • Tags occupy less space when encoded;
    • Schemas are crucial for binary formats;
    • Message produceers or clients need to know the schema to serialize the data;
    • Message consumers(processing service in our case) requires the schema to deserialize the message;
    • So, schemas are usually stored in some shared database where both producers and consumers can retrieve them;
    • Important to metnion: schemas may change over time;
    • We may want to add more attributes into messages and use them later for counting or filtering;
    • Apache Avro is a good choice for our countign system;
