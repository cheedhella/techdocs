What is Log Aggregation?

    The application consists of multiple services and service instances that are running on multiple machines. Requests often span multiple service instances. Each service instance generates writes information about what it is doing to a log file in a standardized format. The log file contains errors, warnings, information and debug messages. Use a centralized logging service that aggregates logs from each service instance. The users can search and analyze the logs. They can configure alerts that are triggered when certain messages appear in the logs.

ELK Stack

  • ELK -> Elasticsearch + Logstash + Kibana;
  • Elasticsearch -> It is NoSQL database based on Lucene search engine, which helps us to store the logs;
  • Logstash -> It is a pipeline tool that accepts logs from various sources and exports data to various targets;
  • Kibana -> It is a visualization layer, which helps the user to monitor application logs;
  • Logs Flow -> Logstash takes the logs and process it to Elasticsearch; End user can browse/search the logs using Kibana;

  • How does Kibana talk to Elasticsearch? By default, Elasticsearch runs on https://localhost:9200
  • Kibana: http://localhost:5601

  • Add this to your application: src/main/resources/application.yml: logging: file: file-path/file.log
  • Start the application and check if logs are saved to above file;

  • Now, we need to tell logstash about the location of above log file;
  • Create and open logstash-library/bin/logstash.conf -> update the path of log file, in input -> file -> path section;
  • How does logstash knows about Elasticsearch? check output -> elasticsearch -> hosts section in bin/logstash.conf file;

  • How does Kibana knows about Elasticsearch?
  • http://localhost:9200/_cat/indices -> displays all our indices used by Elasticsearch;
  • http://localhost:9200//_search -> used to search log specific index;
  • That index is internally created by logstash; If you want to create your own logstash file, specify in bin/logstash.conf file;

How to make log aggregator fail-safe? There can be instances when the logging service (log aggregator) goes down, and it becomes a single point of failure for our analysis and debugging needs. We do not want to miss out on any logs that were generated during that outage. So, we need to develop an alternate mechanism that stores those logs until our aggregator is back online. Journalbeat - Similar to filebeat, this is an agent which exclusively pushes system logs. *-exporter - The purpose of any exporter is to expose the metrics in a form which Prometheus can understand. Prometheus exporter - Pusher is a piece of software which pulls metrics from a local Prometheus and pushes it to Sauron's PushGateway. PushGateway - Prometheus works predominantly based on pull model. However to add a push model support, PushGateway was introduced where Prometheus Pusher can push metrics into a PushGateway and Sauron's Prometheus will scrape(pull) metrics from PushGateway instead of coming inside our data center to collect mertics.
