What and Why SOLID principles?

  • It is a set of guidelines, that helps you in writing better code that is easier to extend, test and maintain;
  • Consequently, as our applications grow in size, we can reduce their complexity and save ourselves a lot of headaches further down the road!

Single Responsbility Principle

  • What is it?
    • A class should have one and only one responsibility; It means a class should have only one reason to change;
    • For eg, a class that handles both authentication and authorization will have 2 reasons to change: if the authentication process changes, or if the authorization process changes;
  • Why is it Important?
    • Testing – A class with one responsibility will have far fewer test cases;
    • Lower coupling – Less functionality in a single class will have fewer dependencies;

Open-Closed

  • What is it?
    • Classes should be open for extension but closed for modification;
    • It means you should be able to extend the functionality of a class, without having to modify the class itself;

    • For eg,
      • Let's say our appliction currently supports only login with registered mail address;
      • Say, you got new requirement to support single sign in with Google login;
      • In this case, you shouldn't touch original login code to add support for Google login;
      • In fact, we should anticipate this when writing our mail login function and write it with good abstraction;
  • Why is it Important?
    • By following this, we can prevent regressions, in an otherwise happy application;
    • One exception to the rule is when fixing bugs in existing code;

Liskov Substitution

  • What is it?
    • Subtypes must be substitutable for their base types;
    • It means you should be able to use a derived class in place of a base class, without breaking the application;
  • Why is it Important?
    • For eg,
      • You have a Car interface, with 3 implementations: DieselCar, PetrolCar, ElectricCar;
      • Say, you have written an API which accepts Car as input; It should work whatever is car object passed;

Interface Segregation

  • What is it?
    • Interfaces should be split into smaller ones;
    • By doing so, Client should only depend on the methods that it needs, and it should not be forced to depend on methods it doesn't use;
    • It is closely related to Single Responsibility Principle;

Dependency Inversion

  • What is it?
    • It means your code should depend on abstractions (interfaces), not on concrete implementations; This will make your code more maintainable and extensible;
