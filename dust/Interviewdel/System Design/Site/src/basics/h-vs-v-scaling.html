What is Vertical Scaling?

  • Scale by adding more power(CPU/RAM/Storage etc) to existing node, as the traffic increases;

  • Problem #1: Scaling up/down takes time;
  • When a CPU utilization of a server reaches it's MAX, ALB can procure a new server with better capacity; Once procured, ALB can switch to the new server;
  • Your applciation can experience downtime, during the switching time;

  • Problem #2: Not cost effective;
  • Once you procure a server with high capacity, what if the traffic goes down?
  • Your CPU utilization is low, but still you have to pay for the bigger server;
  • You don't want to keep switching from smaller server to bigger and vice versa;

  • Problem #3: There is a limit on it;
  • There is a limit to the vertical scaling; You can't keep on adding CPU/memory to the server;
  • So, for a distributed system to be massively scalable, vertical scaling is not an option;

What is Horizontal Scaling?

  • When the traffic increases, insead of moving to a more powerful server, spin up another server;
  • There is no transition or cut off period; The moement traffic increases, load balancer spawns another instance;
  • It is faster to scale up/down, as needed;
  • Massively scalable;
  • It is cost effetive;
  • All real world distributed systems use Horizontal scaling;
  • Note: You need to refactor your legacy code; If you try to scale your legacy monolithic application with horizontal scaling, you end up paying more;

Horizontal vs Vertical Scaling

Examples

  • Cassandra and MongoDB systems can scale horizontally, by adding more machines to meet growing needs;
  • MySQL supports vertical scaling, by switching from small to bigger machines; However, this process often involves downtime;

How can you make your application scalable for a big traffic day?

  • Average Answer
    • Put your ec2 nodes/VMs in a auto scaling group and use a elastic load balancer; 3 years back, there is nothing wrong with this answer!
    • But, if you are recuited for solutions architect today, there is a better answer!

  • Better Answer
    • Put your ec2 nodes in a auto scaling group and use a elastic load balancer;
    • But, in a big traffic day, traffic burst is very high;
    • ELB scales up naturally, with the high rate of traffic;
    • I will also utilize a Scheduled Scaling in addition to auto scaling based on cpu/memory;
    • Scheduled scaling already have multiple ec2 instances up and running to handle huge amount of traffic;
    • In addition to that I will ensure that the AMI(Application Machine Image) is light-weight;
    • More the number of libraries and packages you put on your AMI, the longer the time it takes to spin up new ec2 nodes in the event of auto scaling;

    • If my applicaiton is connecting to a database, I will utilize the database proxy, called RDS proxy;
    • Sometimes applications will make rapid new connection to the database and when the program stop querying the database for that particular instance, the connection will stay open;
    • So when another traffic invocation comes, instead of reusing that lingering or foreign connection, it will create another new connection;
    • So this results in a lot of open database connections, taking up precious compute from your database;
    • Using RDS proxy, we will eliminate that; RDS proxy will maintain the database connection pool;

    • On top that, run IEM(Infrastructure Event Management), to ensure that it can handle high traffic;
    • IEM scales up the load balancer, ec2 and passes high traffic to ensure that it can handle it;

    • Also, check your AWS account settings;
    • For eg, there is a limit on the number of ec2 instances that you can spwan;
    • You can request AWS to increase certain limits and quotas;
    • So one strategy that customers adopt is they will separate heavy eating APIs into multiple account and regions;

    • In addition to it, let's talk about splitting the application into microservices;
    • With microservices, one heavy hitting API can scale up a lot more without impacting the other microservices;

  • Another Answer
    • Let the k8s or serverless handle it; This is not true, because all of them have scaling limits;
    • You have to tweak certain things in each technology to ensure that it can handle high traffic;

    • So, for serverless scaling, before the big traffic day, ensure the Provisioning Concurrency is enabled;
    • Provisioning concurrency will pre warm certain number of lambdas, so that it can handle the burst traffic;
    • Provisioning concurrency can be done in a auto scaling way or scheduled way;

    • Also, optimize lambda code using x-ray; optimize lambda configurations using cloudwatch insights;

    • For API gateway, enable API caching;
    • Check the account limit for Amazon API Gateway concurrent connection limits, How many at lambda you can spin up and request AWS team to increase those limits;

Scaling in AWS

  • Scaling differs from one AWS service(such as ec2, lambda, containers) to another;

  • We have already seen horizontal and vertical scaling of ec2 instances;

  • Lambdas support only horizontal scaling;
  • For each new request, a new instance of lambda spins up; There is not Auto Scaling Group here!

  • Now, let's see k8s containers scaling;
  • At somepoint, using Horizontal Auto Pod scaler, another pod(not container) gets created, on the same EC2 node;
  • What happens if ec2 fills up? At some point, we need to scale the ec2 nodes;
  • We call it cluster auto scaler;

  • How does fargate scale?
  • With fargate, there is no ec2 node; All you see is a pod;
  • With increasing traffic, more pods are created; there is cluster auto scaler in this case;
  • Fargate manages everything else under the hood;
