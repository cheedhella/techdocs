What is a Rate Limiter?

  • Imagine we have a service which is receiving a huge number of requests, but it can only serve a limited number of requests per second;
  • To handle this problem, we would need some kind of throttling or rate limiting mechanism, that would allow only a certain number of requests, so our service can respond to all of them;
  • In general, a rate limiter caps how many requests a sender can issue in a specific time window;
  • Once the cap reached, It blocks the requests by returning HTTP '429 - Too many requests' response;
  • For example
    • A user can send only one message per second;
    • A user is allowed only three failed credit card transactions per day;
    • A single IP can only create twenty accounts per day;

Why do we need a Rate Limiter?

  • It protects the service against Denial-of-service (DOS) attacks, brute-force password attempts etc;
  • These attacks are usually a barrage of HTTP requests, which may look like they are coming from real users, but are typically generated by machines (or bots);
  • As a result, these attacks are often harder to detect and can easily bring down the service;

Requirements

  • Functional
    • Limit the number of requests that an entity can send to an API within a time window;
  • Non-Functional
    • As it is called for every request, it shouldn't introduce any substantial latency;
    • It should be highly available;

Types of Throttling

  • Hard Throttling
    • Number of requests per specified duration are strictly limited to specified limit;
  • Soft Throttling
    • In this type, we can set the API request limit to exceed a certain percentage;
    • For example, if we have rate-limit of 100 messages a minute and 10% exceed-limit, our rate limiter will allow up to 110 messages per minute;
  • Elastic or Dynamic Throttling
    • Under Elastic throttling, the number of requests can go beyond the threshold, if the system has some resources available;

Types of Throttling Algorithms

  • Fixed Window Algorithm
    • In this algorithm, the time window is considered from the start of the time-unit to the end of the time-unit;
  • Rolling Window Algorithm
    • In this algorithm, the time window is considered from the fraction of the time at which the request is made plus the time window length;

High Level Design

  • For every incoming request, webserver first asks the Rate Limiter to decide if it will be served or throttled;
  • Rate Limiter is responsible for deciding whether to a throttle a request or serve it;
  • If the request is not throttled, then it'll be passed to the API servers;

Rate Limiter with Fixed Window Algorithm

  • Take a Map<User, <count, startTime>>; windowSize=60;
  • For each incoming request:
    • Identify the user who sent the request;
    • If there is no entry is present in the Map for that user, insert record with count 1, current timestamp and allow the request;
    • If there is an entry,
      • If currentTime - startTime > windowSize, set startTime to currentTime, count to 1 and allow the request;
      • else
        • If count < windowSize, increment the count and allow the request;
        • else, throttle the request;

Rate Limiter with Sliding Window Algorithm

  • Take a Map<User, SortedSet<Time>>; windowSize=60;
  • For each incoming request:
    • Identify the user who sent the request;
    • If there is no entry is present in the Map for that user, insert a sorted set with current timestamp and allow the request;
    • If there is an entry,
      • Remove all the timestamps that are older than currentTime - windowSize;
      • If no of requests in the SortedSet are < limit, add currentTime and allow the request;
      • else, throttle the request;
