1. What is SNMP?
  • It is used to monitor(health and performance metrics) and configure network devices such as routers, switches, servers, printers, wireless access points, firewalls, IoT devices(such as smartwatches, fitness trackers, smart locks etc);
2. New Terms
  • SNMP Agent
    • It is a software that is installed on the network device;
  • SNMP Manager or NMS(Network Mangement System)
    • The system that asks for info or sends SNMP commands;
  • MIB - Management Information Base;
    • It is a structured database of information about a network device, such as: CPU usage, Iface status, number of packets transmitted;
  • OID - Object Identifier;
    • It is a path, which uniquely identifies a metric OR setting in MIB tree;
    • Examples:
      • .1.3.6.1.2.1.1.1.0 → sysDescr (device description)
      • .1.3.6.1.2.1.1.3.0 → sysUpTime (time since last reboot)
      • 1.3.6.1.2.1.2.2.1.2.X → ifDescr (interface name, where X = interface index)
      • .1.3.6.1.2.1.2.2.1.8.X → ifOperStatus (interface up/down status)
    • Instead of raw numbers, managers can use human readable names; Eg: iso.org.dod.internet.mgmt.mib-2.system.sysDescr.0;
3. How SNMP works?
  • SNMP Polling
    • Manager sends a request: For eg, Hey router, what's your CPU usage?
    • Agent replies with the requested data;
  • SNMP Traps
    • Sometimes, Agent sends alerts(called traps) to manager without asking; For eg, CPU utilization on a device exceeded 80 percent for one minute;
4. SNMP Versions
  • SNMPv1 - Simple;
  • SNMPv2c - Added lot of performance improvments; But, still insecure(uses community strings);
  • SNMPv3 - Added support for authentication and encryption; Most secure;
SNMP managers can use a Set command to change configurations on a managed device. It works in a client-server model: SNMP Manager → The client, which requests information. SNMP Agent → The server, running on the managed device, which provides the information. It is used to retrieve the value of a specific piece of information (object) from an SNMP agent. The information is defined in a MIB (Management Information Base), where each parameter is identified by an OID (Object Identifier). 
Example of MIB tree:
iso (1)
 └─ org (3)
      └─ dod (6)
           └─ internet (1)
                ├─ directory (1)
                ├─ mgmt (2)
                │    └─ mib-2 (1)
                │         ├─ system (1)
                │         ├─ interfaces (2)
                │         └─ ip (4)
                ├─ private (4)
                └─ experimental (3)

Each node has a number → OID is just the sequence of numbers from root to that node.
Example: 1.3.6.1.2.1.1.5
   Breakdown:
   1 → iso
   3 → org
   6 → dod
   1 → internet
   2 → mgmt
   1 → mib-2
   1 → system
   5 → sysName (the name of the device)
2. Type of MIBs?
  • Standard MIBs - Defined by standards (RFCs). E.g., MIB-II
  • Private MIBs - Defined by vendors for their devices. E.g., Cisco, HP
  • Experimental MIBs - For testing or new features
2. SNMP operations
  • GET - It is used to retrieve a single object;
    • SNMP Manager sends a GET request to an SNMP Agent, asking for the value of a specific OID;
    • SNMP Agent looks up the requested OID in its MIB; Agent responds with the current value of that object;
    • For eg, If manager want to know the uptime of a router, it sends a GET request with OID 1.3.6.1.2.1.1.3.0 and Agent responds with "1234567" (number of timeticks since last reboot);
  • GET-NEXT - It is used to retrieve next OID in the MIB tree; It allows you to walk through all objects in the MIB tree;
    • Manager sends a GET-NEXT request with a OID; Agent responds with the next valid OID and its value;
  • GET-BULK - Give me the next N OIDs in one response(supported in SNMP v2 and v3);
    • It’s used to retrieve large amounts of data in fewer requests, especially when walking tables (like interface lists, routing tables etc);
    • GET-BULK request has 2 key parameters:
      • non-repeaters
        • Number of OIDs in the request that should be treated as simple GET-NEXT (only one value returned);
        • Useful for scalar objects (like sysUpTime)
      • max-repetitions
        • The number of "next OIDs" you want for the repeating part;
        • Determines how many rows of table data you’ll fetch at once;
          • Non-repeaters: Specifies the number of variables to retrieve using simple GetNext operations. Max-repetitions: Indicates maximum iterations for repeating variables. https://www.dpstele.com/blog/what-is-a-snmp-getbulk-request.php
  • SET
    • Manager sends a SET request to AGENT, specifying OID and new value;
    • Agent checks if OID is writable; If valid, Agent updates the value and responds with confirmation;
    • It is useful for: updating configuration, resetting counters, changing system description or names etc;
    • Many devices disable SET by default or allow it only with strong authentication(SNMPv3 with encryption);
    • Older SNMP versions (v1/v2c) relied on simple community strings like "private" (default write access), which is insecure;
  • TRAP
    • It allows the devices to alert the manager without waiting to be polled;
    • Eg: Interface going down/up, device rebooted, High CPU or memory usage, security alerts etc;
    • In case of any event, agent sends a trap to the manager's trap listener(usually on UDP port 162);
  • LISTEN
    • It is like a trap, but requires an acknowledgment from the manager (more reliable);
GET – Manager asks the agent for a value (e.g., “What’s the CPU usage?”). SET – Manager changes a value on the agent (e.g., “Shut down this interface”). GETNEXT – Manager retrieves the next variable in the MIB tree. GETBULK – Retrieve large blocks of data efficiently (SNMPv2+). TRAP – Agent sends an unsolicited alert to the manager (e.g., “Link down!”). INFORM – Like a trap, but requires acknowledgment from the manager. SNMP (Simple Network Management Protocol) works using a client-server model where an SNMP Manager (the client) communicates with SNMP Agents (servers) running on network devices like routers and printers to monitor and control them. Agents collect device information, store it in a Management Information Base (MIB), and respond to manager requests or send unsolicited notifications called traps to the manager to report events. This process allows network administrators to collect data, detect faults, and optimize performance from a single, centralized platform.
2. goroutine VS OS/Java threads?
  • Small Initial stack and resizable
    • A goroutine starts with a very small stack (about 2 KB) and it grows or shrinks dynamically as needed by the workload; Where as regular OS threads starts with a large fixed stack (often 1 MB);
  • User space scheduling and M:N modeling
    • goroutines are scheduled in the user space(rather than kernel space) by go runtime;
      So, swiching b/w goroutines is faster - as there is no need to enter kernel mode, only minimal state(like program counter, stack pointer etc) needs to be saved/restored;
    • Goroutines are multiplexed onto OS threads - It means thousands of goroutines can run on just a handful of threads, thus taking less memory and CPU;
  • Efficient communication via channels
    • Instead of shared memory and locks, Goroutines use channels to communicate(exchange data) with each other;

package main

import (
	"fmt"
	"log"

	g "github.com/gosnmp/gosnmp"
)

func main() {
	// Configure the SNMP client
	snmp := &g.GoSNMP{
		Target:    "192.168.1.1", // Replace with your device IP
		Port:      161,
		Community: "public",      // SNMP community string (like a password)
		Version:   g.Version2c,   // Can be Version1, Version2c, or Version3
		Timeout:   g.Default.Timeout,
		Retries:   1,
	}
	
	// Connect to the SNMP agent
	err := snmp.Connect()
	if err != nil {
		log.Fatalf("Error connecting: %v", err)
	}
	defer snmp.Conn.Close()

	// Example OID: sysDescr.0 (device description)
	oid := ".1.3.6.1.2.1.1.1.0"  

	// Perform GET
	result, err := snmp.Get([]string{oid})
	if err != nil {
		log.Fatalf("SNMP GET error: %v", err)
	}

	// Print results
	for _, variable := range result.Variables {
		switch variable.Type {
		case g.OctetString:
			fmt.Printf("%s: %s\n", variable.Name, string(variable.Value.([]byte)))
		default:
			fmt.Printf("%s: %v\n", variable.Name, variable.Value)
		}
	}
}
